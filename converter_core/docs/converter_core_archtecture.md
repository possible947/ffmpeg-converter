Данный документ описывает архитектуру программы ffmpeg-converter (далее конвертер). Программа конвертер является системой обработки видео файлов, опирающаяся на три «кита»:
1. Специально подготовленный для программы ffmpeg.
2. Внешний проект hq-converter (далее hq), который подготавливает видеодорожку для использования программой конвертер.
3. Предварительно настроенная система обработки аудио дорожек для музыкальных видеоклипов.

Сама программа конвертер, по сути, является системой управления для процесса обработки видео файлов с акцентом на музыкальные видео. Основной функционал программы включает в себя:
1. Обработку видео дорожки с возможностью копирования из исходного файла, кодирования программными энкодерами ProRes и ProRes_ks из состава ffmpeg.
2. Обработку видео дорожки с использованием аппаратных энкодеров, определенных для используемой платформы.
3. Обработку аудио дорожки с использованием настроенных алгоритмов нормализации громкости и выходных параметров для энкодеров аудио.
4. Вызов, управление процессом hq, и последующее использование результата hq.
5. Продвинутые возможности сборки итогового файла в несколько поддерживаемых контейнеров.
6. В будущем планируется добавить поддержку использования различных видео фильтров.

Исторически программа развивалась от простого к сложному путем добавления нового функционала, но текущее положение разработки уже не допускает простого расширения программы конвертер из за нагромождения старого кода и многочисленных «заплаток» нового функционала. Как пример, интеграция hq потребовала выполнить рефакторинг кодовой базы, сопоставимый по обьему с полной версией программы конвертер. И все равно результат является сборными слоями разных реализаций. Как итог я планирую разработать и реализовать новую модель архитектуры перед этапом реализации поддержки фильтров, с учетом накопленного опыта и необходимых для интеграции фильтров условий. 

На текущем этапе программа написана на C. Состоит из ядра конвертера, cli, и двух вариантов gui: gtk4 для Linux, наитивный для macOS. Оба варианта gui полностью готовы и могут быть использованы в дальнейшем. Оба содержат полный набор интеграций для конечной реализации программы. Тоже касается cli. Эта утилита готова и потребует минимальной переделки для дальнейшего использования. Описываемая здесь архитектура будет касаться только ядра конвертера. Новая архитектура будет кардинально отличатся от текущей в том, что она будет базироваться на следующих принципах:
1. Использование объектно - ориентированной модели программирования 
2. Использования модели предварительно определенных правил обработки без анализа и сложной бизнес - логики.
3. Использования принципа конвейера обработки с фиксированными этапами без проверок их необходимости.
4. Использование принципа атомарности каждого объекта и каждого этапа. Каждый этап использует свой объект. Каждый из объектов инкапсулируют в себе все необходимое для выполнения данного этапа.
5. Использование предопределенных логических полей как критериев выбора.
6. Использование одного объекта верхнего уровня, который будет является владельцем очереди обработки списка файлов и очереди обработки каждого файла.

Конвертер использует строгие правила как для среды выполнения, так и для самого процесса обработки. На уровне среды выполнения правила следующие:
1. Использование только встроенных ffmpeg и ffprobe.
2. Обязательное наличие в встроенных ffmpeg и ffprobe энкодеров ProRes, prores_ks, fdk_aac, декодера rav1d, фильтра soxr.
3. Обязательное наличие в системе mkvmerge и mp4box.
4. В случае macOS обязательная поддержка aac_at для встроенного ffmpeg.
5. По умолчанию программа рассчитана на использование ffmpeg 9+ версии, хотя исторически программа конвертер может использовать ffmpeg 8.1.

На уровне процесса обработки правил больше и они образуют стройную логическую модель, которая является одним из камней преткновения в разработке. Сам набор правил можно разделить на группы, которые опираются на определенную модель параметров, которая описывает три уровня видео и аудио обработки. 
Видео обработка описывается моделью codec - encoder - preset. При этом codec описывает группу возможностей, не обязательно являющихся энкодеров, но выполняющих обработку видео. На этом уровне вводится понятие входной видеодорожки и первое концептуальное отличие новой архитектуры - ВХОДНАЯ ДОРОЖКА НЕ ОБЯЗАНА БЫТЬ ЧАСТЬЮ ВХОДНОГО ФАЙЛА ФИЗИЧЕСКИ. Это правила крайне тяжело реализуемо в рамках старой архитектуры конвертер, ориентированной на использование одного прохода обработки для выходного файла. 

Список возможных значений codec начнем с software. Как понятно из названию это набор из нескольких программных энкодеров. Допустимые значения для software это ProRes, prores_ks, x264. Для каждого из энкодеров группы software определен свой набор пресетов. Для ProRes это lt, standard, hq. Для prores_ks это lt, standard, hq, 4444. Для x264 это lossless. Отличительной особенностью этой группы является legacy поведение энкодеров, которое определяет возможность выполнения кодирования в основном процессе обработки без необходимого промежуточного этапа. Дополнительным правилом данного набора является определение выходного формата итогового видеофайла - это mov для ProRes энкодеров, и mkv для x264.

Продолжает список возможных значений codec это video toolbox. Это macOS специфичный набор, который включает в себя три энкодера - ProRes, h264, hevc. Набор пресетов ProRes - lt, standard, hq, 4444. Набор пресетов h264 и hevc - default, low, balance, hq. Выходные контейнеры итогового видео mov для ProRes или mp4 для h264 и hevc. Также могут использовать legacy поведение и обрабатывать видео дорожку в основном процессе обработки без необходимости промежуточного этапа.

Следующие варианты codec это hwaccel аппаратные энкодеры, доступные в средах windows или Linux. Набор возможных значений определен как: vaapi, nvenc, qsv. Набор энкодеров для nvenc и qsv это h264, hevc, hevc_10bit, av1, av1￼_10bit. Набор пресетов для указанных энкодеров подобен video toolbox - это default, low, balanced, hq. Несколько особняком находится codec - vaapi. Все дело в двух отличительных особенностях Linux стека vaapi. Во первых, он включает в себя все доступные энкодеры в системе без разделения по архитектурам видеокарт. Во вторых, в случае наличия двух разных адаптеров, необходим механизм определения используемого адаптера. Что, в свою очередь, требует механизм определения доступных энкодеров для выбранного адаптера. Текущая реализация этого codec работает плохо и я принял решение оставить codec vaapi только для систем Linux с видиекартами Radeon без поддержки amf. Тогда наборы энкодеров и пресетов становятся аналогичными nvenc / qsv. Общим отличием всех hwaccel codec вариантов является возможность выбора используемого видео адаптера. Все hwaccel codec варианты определяют использование mkv в качестве выходного контейнера. Также могут использовать legacy поведение и обрабатывать видео дорожку в основном процессе обработки без необходимости промежуточного этапа.

Следующий вариант codec это Vulcan. По концепции он похож на другие hwaccel codec варианты, но сегодня подтверждено только использование энкодера ProRes и только на видеокартах Nvidia. В связи с тем, что именно Vulcan ProRes энкодер будет необходим в будущем, я реализовываю готовую политику его использования как энкодера общего назначения. То есть цепочка codec - Vulcan, encoder - ProRes, presents - Lt, standard, hq, 4444. Выходной контейнер mov. Возможен выбор используемого видео адаптера. Также могут использовать legacy поведение и обрабатывать видео дорожку в основном процессе обработки без необходимости промежуточного этапа.

На этом список энкодеров видео заканчивается и начинается список программно эмулируемых codec’s. Их отличием является использование дополнительных проходов в случае обработки видео. Именно сюда логически может быть добавлена обработка видео сложным фильтром, недопустимо трудная или невозможная в одном проходе обработки.
На первом месте стоит mux. Это один из «китов» дополнительного функционала программы конвертер. Это крайне важный компонент, необходимый как для сборки финального файла, так и для интеграции hq и будущей системы фильтров. Именно mux инкапсулирует новую концепцию ВИДЕО ДОРОЖКИ. Группа codec - mux включает в себя следующие варианты encoder’s: copy, mkv, mov, m4v. Пресет у всех encoder’s на данном этапе один - default. Как понятно из названия, энкодер определяет контейнер для выходного видео файла. Но также пресет определяет источник входной видео дорожки, что неочевидно и вносит путаницу. Концепция mux это ВСЕГДА ИСПОЛЬЗОВАНИЕ ГОТОВОЙ ВИДЕО ДОРОЖКИ без ее обработки. Из входного файла в случае copy, и внешней в остальных. Для copy выходной контейнер mkv и правила используются для mkv варианта mux. Назначений у codec mux несколько. Это и обработка аудио дорожки без перекодирования видео. И замена исходной видео дорожки на обработанную внешней программой. И смешанное для обоих случаев. Также еще одним неочевидным назначением codec mux является пост обработка выходного файла, когда это необходимо. Например, в случае когда определено добавить к выходному файлу главы, субтитры, метаданные. Сейчас это делается на этапе кодирования или на этапе сборки, что порождает дублирование кода, двойные проверки файлов и не гарантирует результата из за отличий реализации ffmpeg / mkvmerge / mp4box алгоритмов. В новой архитектуре сущности обработки и сборки будут разделены и разрабатываются отдельно.

На втором месте программно эмулируемых codec’s находится hq, но на самом деле это просто частный случай mux. Внешняя библиотека hq связана с системой кодирования видео и она возвращает видео дорожку в формате ts / mkv / mov в зависимости от выбранного encoder. Правила выбора выходного контейнера ПОСЛЕ mux два - mov для ProRes и mkv для всех остальных. Система hq использует свой набор пресетов, который должен быть импортирован в набор пресетов программы конвертер на этапе запуска программы если hq определен как доступный. Hq не работает в среде windows и не доступен в windows, но доступен в среде wsl. Система hq является «черным ящиком» для конвертер и все взаимодействие это вызов библиотеки с определенными параметрами, получения статуса / прогресса, получение готового файла. После окончания обработки hq выполняется стандартный процесс mux с определенными для mux правилами и входной видео дорожкой от hq.

На этом описание видео группы завершено и я перехожу к аудио группе.

Аудио обработка имеет несколько особенностей, которые необходимо учитывать в процессе разработки. Это возможность использования предварительного прохода для анализа аудио дорожки. Это необходимость учитывать жанр для loudness нормализации. Это зависимость выходного формата от выходного контейнера. 
Аудио обработка описывается моделью normalization - genre - output format. Для normalization определенны следующие варианты: none, peak, peak_2pass, loudness, loudness_2pass. Genre доступен только для варианта loudness_2pass и включает следующие варианты: none, edm, rock, hiphop, classical, podcast. Набор output format полностью включает в себя copy, pcm, aac, aac_ac3. Доступность выходных форматов вариативна и зависит от набора параметров видео группы, точнее от выходного контейнера. Контейнер mov разрешает только pcm. Контейнер mkv разрешает все варианты. Контейнеры mp4 и m4v разрешают aac и aac_ac3. Так как mux - copy использует mkv в качестве выходного контейнера, то output format использует правила для mkv. В случае codec hq-converter output format подчиняется правилам определения выходного контейнера для hq, как описано выше. Еще одно правило касается выбора используемой аудио дорожки в случае если исходный файл содержит несколько. Только output format - copy копирует ВСЕ аудио дорожки из входного файла в выходной. Во всех остальных случаях используется ПЕРВАЯ АУДИО ДОРОЖКА из входного файла.

На этом этапе описание аудио обработки завершено и я перехожу к еще одному частному случаю использования mux. Это специальный программный блок с названием Apple m4v c4eator. Как следует из названия это специальный программный режим, который конвертирует файлы mkv, содержащие совместимые видео дорожки (h264, hevc) в apple совместимые файлы m4v. При этом режим вызывает дополнительное окно с параметрами, в котором можно определить какую аудио дорожку использовать, язык для аудио, копировать ли главы и субтитры из входного видео в выходное. Блок проверяет совместимость компонентов исходного файла, выполняет конвертацию при необходимости и собирает правильный выходной файл, используя ￼mp4box.

На этом описание программы ffmpeg-converter, ее текущей реализации, закончено и я перехожу к описанию архитектуры ядра программы.

Ключевыми особенностями новой архитектуры конвертер являются:

1. Converter core это библиотека, реализующая полный цикл обработки видео файлов. 
2. Библиотека инкапсулирует внутри себя все правила и определения процесса обработки. Никакого доступа снаружи к конвейеру не предусмотрено. Никакой внешней бизнес - логики не предусмотрено.
3. В соответствии с пунктом 2 библиотека также инкапсулирует внутри себя доступ ко всем файлам - наборам параметров. Это и доступ к общему реестру конвертер. И доступ к пресетам hq. И доступ к пресетам фильтров.
4. Таким образом взаимодействие с библиотекой становиться достаточно простым. Для запуска очереди обработки достаточно предоставить список входных файлов, выходную папку, набор параметров из предопределенного библиотекой списка. В дальнейшем внешний клиент может только отслеживать прогресс выполнения обработки и передавать команды из определенного набора.
5. Для удобства взаимодействия с пользователем библиотека имеет возможность отдать списки допустимых для текущей среды компонентов и список допустимых наборов параметров обработки. Эти списки несут информационную нагрузку и не могут быть переопределены.
6. Библиотека выполняет валидацию всех параметров, полученных от внешнего клиента и может отказать в выполнении запрошенной обработки всего задания или отдельного файла с передачей информационного сообщения с причиной отказа. (Пример - hq требует, чтобы путь к его временной папке был не длиннее 103 символов и, корректное на первый взгляд задание получит отказ с сообщением недопустимости длинного пути к выходной папке задания). Второй пример это cli - пользователь ОБЯЗАН правильно определить параметры задания с учетом условий среды исполнения.
7. Converter core реализует принцип предопределенных правил поведения, основанных на крупном реестре доступных возможностей. Но на этапе инициализации converter core происходит формирование runtime реестра возможностей, доступных в данной сессии.
8. Тоже самое относится к реестру параметров обработки. Он формируется и проверяется динамически в соответствии с runtime реестра доступных возможностей и выбором пользователя.
9. Runtime конвейер определяется один раз на этапе разработки и состоит из шагов, каждый из которых задан базовым классом, который по умолчанию не делает ничего. Это так называемый dry - run режим прохода конвейера, очень удобный для последовательной разработки. Каждый из базовых классов может быть переопределен его потомком, который реализует необходимый функционал в рамках правил, определенных для его родителя.
10. Каждый из базовых классов runtime конвейера не имеет никакой связи с другими классами. Он всегда атомарный и инкапсулирует в себе поведение полностью. Это правило позволяет разрабатывать каждый из классов - потомков отдельно, опираясь на base class API.
11. Все взаимодействие между классами реализуется полями общего класса TQuenue.JobOptions. Каждый класс конвейера может определять значения полей этого класса, любых доступных для изменения полей. Это значительно упрощает разработку и реализацию логики принятия решений для обработки. Это позволяет скрыть особенности реализации какого либо этапа обработки от других его членов. Это позволяет скрыть особенности среды от классов - членов runtime конвейера.
12. Класс TQuenue и его член TQuenue.JobOptions являются единственными источниками истины для принятия решений о процессе обработки и состояния процесса обработки. При этом каждый класс на своем шаге получает определенное состояние процесса и не выполняет проверок того что было до. Класс выполняет только необходимые для его этапа проверки и возвращает только определенный результат.
13. Предыдущие пункты определяют как следствие то, что недопустимы неопределенные состояния любого из классов - членов runtime конвертер. Отказ любого этапа - это отказ процесса для конкретного файла с выводом сообщения и переходом к следующему файлу очереди
14. Cli использует простую модель взаимодействия с converter core в один проход. Пользователь определил набор параметров - cli инициализировал converter core и заполняет поля TConverterParameters полученными от пользователя значениями и в конце спрашивает о том, что набор валиден. 2. выполяется PlatformDetection
    данный класс выполняет проверку доступности обязательных бинарных инструментов, наличия во встроенном ffmpeg обязательных компонентов, детектирует доступные в текущей среде платформы и формирует класс PlatformList, который возвращает, и статус среды PlatformDtection.Allowed: bool.

            linux_nvenc7(ID=6)
            linux_qsv_dgx1
            linux_vulkan_nvidia(ID=8)

        TPlatformDetection является исключительно механизмом определения состояния среды выполнения.

        TPlatformDetection не определяет политику доступности encoder/preset, не выбирает реализации и не интерпретирует числовые Platform ID Registry.

4. Выполняется TReestr. 
    Класс TTReestr принимает в качестве параметров вызова экземпляр класса TPlatformList.
    Одним из базовых компонентов является реестр параметров программы конвертер. Он содержит наборы доступных компонентов для среды выполнения - это верхний уровень. И массив конкретных строк для ffmpeg - это нижний уровень. Его задача - определить наборы компонентов, параметров и строки реализации, и передать полученные значения в converter core для дальнейшего использования. После этого реестр больше не используется. То есть политика «один раз определили что доступно и работаем с этим» выполняется в полном объеме. Также в реестре отображена базовая основа бизнес - логики ядра конвертер, которая дает основу модели поведения ядра. В описании к реестру определено, что правила из реестра являются «истиной» для режима времени выполнения. Это нововведение позволяет значительно упростить обработку логики поведения ядра и, зачастую, убрать блоки логики к из компонентов конвейера. Если данных от реестра достаточно для однозначного определения поведения компонента ядра то в данном компоненте не будет представлен блок логики. Это помогает клиентам библиотеки ядра оперировать набором параметров в интерактивном режиме,так как клиентам и самому ядру есть на что отпираться. Фактически достигнутой целью является определенное состояние ядра сразу после запуска без необходимости выполнять дополнительные этапы проверок, которые в любом случае приведут к платформенным зависимостям, отображенным в реестре в полной мере.
    Полное описание класса реестра представлено в отдельном документе TReestr_descriptiton.md.
    Класс TTReestr возвращает класс TTReestrOptions, который содержит окончательный результат определения глобальных возможностей текущей среды. Повторное определение возможностей среды и повторное разрешение platform-specific реализаций после этого этапа не допускаются.
    Далее инвариант Registry
        TTReestr является единственной точкой преобразования обнаруженного состояния среды в глобальную capability model converter core.
        Результатом его работы является TTReestrOptions.
        После формирования TConverterOptions данные TTReestrOptions больше не используются, а повторное обращение к Registry в runtime запрещено.
5.  Создается класс TConverterOptions.
    Класс TConverterOptions - сердце текущей сессии. Он включает в себя разрешенные параметры и правила выполнения для текущей сессии, и ползовательские параметры для текущей сессии. Этот класс в дальнейшем исползуется на всех этапах как источник правил выполнения сессии. Инициализация класса TConverterOptions включает следующие этапы:
        На основе данных класса TTReestrOptions формируется список video codec group.
        Для каждой video codec group на основе данных класса TTReestrOptions формируется список encoder.
        Для каждого video encoder group - encoder на основе данных класса TTReestrOptions формирется список preset, который включает в себя правила и команды для TFFmpegExecutor.
        Формируется списки audio normalization и genre.
        Формируется список audio output, который также получает команды для TFFmpecExecutor из класса TReesrOptions. На основе данных класса TTReestrOptions задаются правила поведение для audio output (пример платформа darwin - энкодер aac по умолчания aac_at вместо fdk_aac).
        На данном этапе filter group создается пустой. Ее реализация это следующий этап развития converter core.
        Класс TTReestrOptions удаляется.
        На данном этапе инизиализация TConverterOptions заканчивается. Его состояние описывает сессию по умолчанию. Все runtime параметры и значения определены. Выбор video group опреден в реестре. Выбор audio group определен как audio normalization - none, genre - edm, audio output - pcm. Статус сессии - create session.
6.  Создается кдасс TSessionFileList.
    Класс TSessionFileList содержит список файлов для текущей сессии и рабочие папки. Выходная папка по умолчанию - ~/ffmpeg-converter в unix средах. c:/users/{current user}/ffmpeg-converter в среде windows. Класс TSessionFileList обязан проверять доступ на запись для каждой выходной папки. Если список video codec group включает hq-converter, то TSessionFileList обязан проверить, что длина полного пути выходной папки не превышает 103 символа (ограничения pascal socket). Если правило не выполнено, то в текущей сессии HQ становиться не доступным. В лог помещается сообщение об соответсвующей ошибке. На этапе добавления файлов в список класс TSessionFileList должен проверить, что каждый файл доступен на чтение и нормализовать путь к файлу до ffmpeg совместимого. Класс TSessionFileList должен содержать поле RequiredSize, которое будет содержать примерный размер свободного места, требуемого для выполнение сессии. Оно установлено как удвоенный размер суммы размеров всех входных файлов. Класс TSessionFileList должен содержать поле AvailableSize, которое будет содержать размер свободного места, доступного на выходном устройстве. Это поля будет использоатся runtime conveyer для определения возможности выполнения сессии. 
7.  Инициализация библиотеки закончена и она готова к работе. Ее классы TConverterOptions и TSessionFileList является публичным. Через эти классы происходит взаимодействие с библиотекой. Далее список инвариантов:
    Инвариант TConverterOptions и состояния сессии
    После завершения инициализации TConverterOptions является единственным источником истины о наборе компонентов, параметров, правил и реализаций, доступных текущему экземпляру converter core.
    Возможность, отсутствующая или запрещённая в TConverterOptions, не может быть сделана доступной ни одним последующим этапом.
    Наличие возможности в TConverterOptions означает, что библиотека поддерживает её в текущей среде выполнения, но не гарантирует возможность её использования в каждой конкретной сессии.
    При формировании и валидации сессии converter core имеет право уменьшать эффективную доступность компонентов и параметров на основании параметров конкретной сессии, списка файлов, путей, доступного дискового пространства и других session-specific условий.
    Session validation не изменяет глобальные возможности TConverterOptions. Она определяет только эффективную доступность этих возможностей для текущей сессии.
    Возможность, запрещённая TConverterOptions, не может быть разрешена session validation.
    Таким образом:
        TConverterOptions = что библиотека умеет в текущей среде.
        Session state = что из этого разрешено и применимо для конкретной сессии.
    TConverterOptions описывает конфигурацию и правила сессии. TQuenue.JobOptions не является состоянием сессии и не заменяет TConverterOptions. Он является runtime-состоянием выполнения конкретного файла внутри runtime conveyor.
    Ни session validation, ни runtime conveyor не выполняют повторное определение возможностей среды и не могут добавить возможность, отсутствующую в TConverterOptions.
    Последующие этапы имеют право только ограничивать использование существующих возможностей в контексте конкретной сессии или конкретного файла.

После этого модель использования converter core зависит от от того, что ее использует.
 В случае cli-type клиента происходит заполнение полей TConverterOptions пользовательскими параметрами сессии, используя разрешенные методы, и заполнение полей TSessionFileList списком файлов для сессии и выходной папки, используя разрешенные методы. Далее клиент запрашивает TConverterOptions выполнить вылидацию сессии и в случае успеха стартует выполнение задания. Также cli клиент может использовать снимок сессии для отображение пользователю доступных компонентов и параметров.
 В случае gui-type клиента клиент взаимодействует с converter core, использую разрешенные методы для установки параметров. Для получения тукещего состояния сессии клиент запрашивает статус сессии, который возвращает снимок полного состояния сессии. На основе полученного снимка gui клиент изменяет данные для отображения пользователю. После того, как пользователь запросит выполнение задания, gui клиент заполняет поля TSessionFileList списком файлов для сессии и выходной папки, используя разрешенные методы. Далее gui клиент запрашивает TConverterOptions выполнить вылидацию сессии и в случае успеха стартует выполнение задания.
В обоих случаях определены следующие правила:
    Клиент converter core не имеет доступа на запись к полям TConverterOptions иначе, как использую get/set методы.
    Клиент converter core не имеет доступа на запись к полям TSessionFileList иначе, как использую get/set методы.
    Клиенту разрешено прямое чтение значения поля, используя get метод. Но предпочитаемый способом получения состояния сессии является метод получения снимка состояния сессии. Обьяснением является тот факт, что изменение значения одного поля может повлечь за собой изменения списка доступных значений или статуса других полей, что не будет явно получено клиентом в случае чтения только одного поля. Это может привести к тому, что явный статус сессии и отображаемый статус сессии окажутся не синхронизированными, и запуск сессии будет с другими праметрами, отличными от ожидаемых. Важно подчеркнуть, что корректность отображаемых пользователю данных - это ответственность клиента. Задача библиотеки находится в другой плоскости.
    Запрос на валидацию сессии является опциональным, но предпочитаемым. converter core в любом случае выполнит его и, если сессия не пройдет проверку, остановит выполненние с сообщением об ошибке. Логично выполнить проверку до старта сессии. Особенно это касается cli клиента, для которого пользователь может запросить валидацию без выполнения, что бы проверить возможность выполнить сессию до ее старта. Также этот запрос включает в себя проверки TConverterOptions и TSessionFileList. Это позволяет проверить возможность системы хранения данных выполнить сессию.
8.  На этом этапе начинается runtime выполнение задания сессии. Здесь надо внести несколько фактов:
    класс TConverterOptions "живет" все время жизни converter core. runtime класс TQuenue живет только во время выполнения, и после окончания очереди уничтожается. Причин этому нескольно. Данные TConverterOptions могут переиспользованы между заданиями разных сессий, данные TQuenue не могут быть переиспользованы никак. Например, повторная обработка того же файла с тем же набором параметров приведет к коллизии перезаписи файла, результат которой определяется параметром TSessinFileList.ReWrite. Если он true, файл будет перезаписан. Иначе пропущен. Никакой возможности повторного использования уже существующего файла, иначе как входного для новой сессии не предусмотено. Также некоторые режимы используют разное количество проходов выполнения. После выполнения задания для файла его промежуточные данные удаляются, независимо от результата, и не могут быть использованы повторно. Для недопустимости различных коллизий класс TQuenue уничтожается после остановки сессии с очисткой всех промежуточных данных, независимо от результата.
    Выполнение задания каждого файла является атомарным. Сбой в одном файле не останавливает очередь. Очередь продолжается со следующего файла. В лог помещается сообщение об ошибке.
    Класс TQuenue определяет сущности session и job. session это все задание текущей сессии, job это задание одного файла. Таким образом session - это набор jobs.
    Инвариант Session и Job
        Session является полным заданием обработки, созданным на основании TConverterOptions и TSessionFileList, и содержит очередь Job.
        Job является атомарным заданием обработки одного файла из очереди Session.
        В каждый момент времени TQuenue выполняет не более одного текущего Job.
        Ошибка или остановка текущего Job не завершает Session. После cleanup текущего Job TQuenue ереходит к следующему Job очереди.
        Остановка Session прекращает текущий Job и всю очередь. Последующие Job не запускаются.
        TQuenue принадлежит Session и существует в течение runtime-жизни всей Session. Завершение, ошибка или остановка отдельного Job не уничтожает TQuenue. TQuenue уничтожается после завершения всей Session либо выполнения session stop.
    В рамках данного документа используется определение сессия для session, и задание для job.
    Поля session status/progress/message описывают состояние всей Session. Поля current file/status/progress/message описывают состояние текущего Job.
    Класс TQuenue обязан предоставлять информацию определенного формата для внешних клиентов, которая должна содержать статус выполнения сессии, прогресс задания сессии, статус текущего задания, прогресс текущего задания, лог с диагностическими сообщениями (опционально). Определены следующие поля:
        files count
        current file
        session status
        session progress
        session message
        job status
        job progress
        job message
    назначение поля files count требует пояснений. это поле отображает количество заданий в очереди, но оно может отличать от ожидаемого пользователем если часть файлов не прошли проверку TSessionFileList. По этой причине введено поле files.
    Кkасс TQuenue принимает определенный набор комманд от клиента:
        session pause
        session continue
        session stop
        job stop
    Команда session pause останавливает конвейер после окончания текущего шага, его выполнение может быть продолжено командой session continue. Команда session stop останавливает конвейер незамедлительно, выполняемое задание признается ошибочным и удаляются все его промежуточные файловые артефакты. TQuenue уничтожается. converter core переходит в режим создания сессии. Команда job stop незамедлительно останавливает выполнение текущего задания, выполняемое задание признается ошибочным и удаляются все его промежуточные файловые артефакты. Конвейнер продолжает выполнение со следующего задания. Здесь нужно важное уточнение относительно hq-converter - этапа анализа. Остановка данного этапа не предусмотрена архитектурой hq-converter и может быть осуществлена только путем принудиьельной остановки segmentator процесса. В текущей версии программы поведение остановки этапа анализа hq-converter определено как недопустимое, остановка происходит после окончания анализа. этап кодирования hq-converter позволяет выполнить и паузу и остановку этапа. 
    На этом описание взаимодействия runtime TQuenue с клиентом закончено.
9.  Создается экземпляр класса TQuenue.
    Класс TQuenue получает ссылки на классы TConverterOptions и TSesiionFileList.
    Класс TQuenue создает экземпляр класса TQuenue.JobOptions.
    Класс TQuenue создает экземпляр класса TVideoCore.
    Класс TQuenue создает экземпляр класса TFilterCore.
    Класс TQuenue создает экземпляр класса TAudioCore.
    Класс TQuenue создает экземпляр класса TMuxCore.
    Класс TQuenue создает экземпляр класса TFFmpegExecutor.
    Класс TQuenue создает экземпляр класса THQCore.
    Их назначение далее:
        класс TQuenue.JobOptions - реестр выполнения задания.
        класс TVideoCore - формирует часть команды ffmpeg для обработки видео. имеет метод Execute, который вызывается для выполнения задач класса. Работает с TQuenue.Otions.
        класс TAudioCore - формирует часть команды ffmpeg для обработки аудио. имеет метод Execute, который вызывается для выполнения задач класса. Может выполнить отдельный проход для определения параметров нормализации громкости аудио. Работает с TQuenue.Otions.
        класс TFilterCore - формирует часть команды ffmpeg для реализации фильтров. имеет метод Execute, который вызывается для выполнения задач класса. Может запросить отдельный проход TFFmpegExecutor. Работает с TQuenue.Otions.
        класс TFFmpegExecutor - выполняет сборку команды ffmpeg и выпоняет обработку. Для сборки команды использует данные из TQuenue.JobOptions.
        класс TMuxCore - один из столпов converter core. Выполняет функции диспетчера реестра выполнения задания. Может выполнять анализ входных файлов. Может переопределять поля других классов в реестре выполнения задания. Отвечает за сборку конечного файла. Отвечает за политики сборки выходного файла.
        класс THQCore - выполняет hq-converter обработку. Является посредником между hq connector и TQuenue.JobOptions.
    Все классы работают с полями TQuenue.JobOptions. Назначение каждого класса можно описать так: взять относящиеся к классу поля и назначить новые значения полей, если это необходимо. Если необходимо и разрешено, выполнить процесс, заданный классом. Если для данного экземпляра и этапа задание не определено, ничего не делать. 
    Детальное описание классов будет во внешнем документе TQuenue_description.md. Здесь только описание архитектуры.
10. Начинается выполнение сессии. Это цикл, который обрабатывает каждый файл из списка файлов сессии. Его этапы с описанием далее:
    1.  извлечения пути к входному файлу из TSessionFileList и передача его в TQuenue.JobOptions.
    2.  извлечение параметров из TConverterOptions и передача их в TQuenue.JobOptions.
    3.  выполнение TVideoCore.Execute
    4.  выполнение THQCore.Execute
    5.  выполнение TFilterCore.Execute
    6.  выполнение TFFmpegExecutor.Execute
    7.  выполнение TMuxCore.PrePass
    8.  выполнение TFFmpegExecutor.Execute
    9.  выполнение TMuxCore.PostPass
    10. финализация этапа, переход к следующему заданию.
11. После окончания выполнения сессии TQuenue уничтожает все созданные им классы и возвращает управление converter core.
12. converter core уничтожает экземпляр TQuenue. Сообщает клиенту что выпонение сессии закончено. Вывывает метод TSessionFileList.Clean. Ожидает дальнейших команд от клиента.
