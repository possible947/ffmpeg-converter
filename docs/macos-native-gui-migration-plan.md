# План перехода macOS GUI на нативный интерфейс (AppKit/Swift)

Дата: 2026-03-16

## 1. Цель и рамки

Цель: заменить macOS GUI-слой на нативную реализацию (AppKit/Swift), сохранив текущую бизнес-логику конвертации в C-ядре и не изменяя поведение обработки медиа.

Рамки:
- Linux GUI остается на GTK4 без функциональных изменений.
- macOS GUI переводится на нативный UI-слой.
- C-ядро и CLI продолжают работать как эталон поведения.

## 2. Обязательные условия проекта (инварианты)

Эти условия обязательны на всех этапах миграции и при приемке:

1. Неизменность логики обработки видео и аудио
- Запрещено менять алгоритмы и правила в C-ядре конвертации.
- Нельзя менять существующие ffmpeg-пайплайны, профильные правила и нормализацию, если это не отдельная задача по ядру.
- Источник истины: текущий C-слой в `src/converter/*` и поведение CLI.

2. Обязательное условие папки вывода по умолчанию
- Если пользователь не выбрал путь, приложение обязано использовать папку по умолчанию внутри home-каталога.
- Должно совпадать с текущим согласованным поведением проекта (`~/ffmpeg_converter`), включая попытку автосоздания/валидации, если это уже реализовано в ядре/утилитах.

3. Поведение перезаписи
- Состояние флага перезаписи в UI должно строго транслироваться в C-опции (`overwrite=1/0`).
- При включении перезаписи должно использоваться поведение принудительной перезаписи (`-y` на уровне ffmpeg-команды).
- При отключении перезаписи должно использоваться поведение без перезаписи (`-n`) с ожидаемым skip/ошибкой по существующему файлу.

## 3. Предпосылки и входные условия

Перед стартом реализации должны быть выполнены предпосылки:

1. Технические
- На macOS установлен Xcode + Command Line Tools.
- Доступен `swiftc` и/или xcodebuild-инструментарий.
- CMake-проект собирается в текущем состоянии (baseline зафиксирован).
- Есть рабочий бинарник CLI для сравнения поведения.
- Для Pascal GUI (Apple M4V модуль): установлен GPAC (`sudo port install gpac`).
  MP4Box и его dylib-зависимости бандлируются в `.app` автоматически скриптом
  `fpc/build/package_macos_app.sh`. На машине сборки GPAC обязателен.

2. Архитектурные
- C API конвертера стабилен и документирован в `src/converter/converter.h`.
- Определен контракт вызова из UI: инициализация, опции, запуск, прогресс, завершение, stop.

3. Процессные
- Зафиксированы критерии приемки (см. раздел 8).
- Определен формат логов для диагностики (без переполнения UI).
- Принято решение о двух независимых UI-ветках: Linux GTK4 + macOS Native.

## 4. Целевая архитектура

1. Общий слой (без изменений логики)
- `src/converter/*` — остается единым движком для всех платформ.
- CLI остается контрольным сценарием и регрессионным эталоном.

2. Linux UI слой
- Текущий `src/gui` (GTK4) остается для Linux.

3. macOS UI слой (новый)
- Новый каталог, например: `src/gui_macos_native/`
- Состав:
  - `AppDelegate`/`NSWindowController`/`ViewController` (UI)
  - `ConverterBridge` (Swift<->C bridge)
  - `ConversionViewModel` (состояние и orchestration)

4. Сборка
- CMake условно собирает:
  - Linux: GTK4 GUI target
  - macOS: native GUI target
- Исключается смешение зависимостей GTK в macOS native target.

## 5. Детальный пошаговый план выполнения

### Шаг 0. Подготовка baseline

1. Зафиксировать эталонные сценарии текущего поведения (CLI + текущий GUI):
- Конвертация без перезаписи при существующем файле.
- Конвертация с перезаписью.
- Папка по умолчанию при пустом output path.
- Нормализация аудио (все режимы из UI).
- Остановка процесса (Stop).

2. Сохранить эталонные артефакты:
- Логи CLI/GUI.
- Проверочные выходные файлы.
- Времена выполнения (грубо, для smoke).

Результат шага: набор baseline-кейсов для регрессионного сравнения.

### Шаг 1. Разделение сборочных веток UI

1. В CMake добавить условные target-ветки:
- `if(APPLE)` — macOS native GUI target.
- `if(UNIX AND NOT APPLE)` — Linux GTK4 GUI target.

2. Исключить сборку GTK4 macOS GUI в native-конфигурации.

3. Проверить, что CLI продолжает собираться на macOS и Linux.

Результат шага: независимая сборочная конфигурация UI по платформам.

### Шаг 2. Каркас нативного macOS GUI

1. Создать минимальное окно нативного приложения:
- поля/контролы, соответствующие текущим опциям;
- список файлов;
- выбор output folder;
- кнопки Start/Stop;
- прогресс + статус.

2. Без запуска конвертации убедиться, что UI lifecycle стабилен:
- открытие/закрытие без падений;
- корректная работа dropdown/combobox/selectors.

Результат шага: стабильный нативный UI-каркас без интеграции с движком.

### Шаг 3. C bridge и модель опций

1. Реализовать bridge слой:
- маппинг UI-полей в `ConvertOptions`.
- подготовка списка входных файлов (`char**`).

2. В bridge зафиксировать обязательные инварианты:
- output_dir по умолчанию = `~/ffmpeg_converter`, если поле пустое.
- overwrite строго соответствует состоянию чекбокса.

3. Добавить unit/smoke-проверки bridge-мэппинга.

Результат шага: корректная передача опций из нативного UI в C API.

### Шаг 4. Интеграция запуска и callbacks

1. Подключить запуск `converter_process_files` в background execution.

2. Привязать callbacks к UI:
- on_file_begin/on_file_end;
- on_stage;
- on_progress_encode/on_progress_analysis;
- on_message/on_error;
- on_complete.

3. Гарантировать обновление UI только на main thread.

4. Реализовать Stop через `converter_stop`.

Результат шага: рабочий end-to-end поток конвертации в нативном UI.

### Шаг 5. Стабильное завершение приложения

1. На close/shutdown:
- отправить stop активной операции (если идет);
- дождаться безопасного завершения worker;
- освободить ресурсы bridge/контекста.

2. Проверить сценарии:
- выход в idle;
- выход во время конвертации;
- выход после ошибки конвертации.

Результат шага: безаварийный shutdown без segfault и утечек.

### Шаг 6. UX-паритет с текущим GUI

1. Восстановить поведение зависимых опций (codec/profile/deblock/audio norm/genre).

2. Сохранить семантику кнопок и статусов.

3. Ограничить длину лог-линий в UI (никаких сверхдлинных сообщений, ломающих layout).

Результат шага: функциональный и поведенческий паритет с текущим UX.

### Шаг 7. Регрессионная валидация инвариантов

Проверить обязательно:

1. Логика аудио/видео не изменилась
- Сравнение с CLI на одинаковых входах и опциях.
- Сопоставление ключевых параметров ffmpeg-команд/выходов.

2. Папка по умолчанию
- При пустом output путь = `~/ffmpeg_converter`.
- Папка создается/валидируется согласно текущим правилам.

3. Перезапись
- overwrite ON -> `-y` поведение.
- overwrite OFF -> `-n` поведение.

4. Стабильность
- Нет crash при закрытии.
- Нет блокировок UI.

Результат шага: подтверждение соответствия обязательным условиям.

### Шаг 8. Упаковка и документация

1. Обновить сборочную документацию:
- как собрать Linux GTK4 GUI;
- как собрать macOS native GUI.

2. Обновить README/документы по архитектуре:
- dual-UI стратегия;
- единый C-core.

3. Добавить Known Differences (если остаются).

4. **Зависимости Pascal GUI (macOS app bundle)**
   - `ffmpeg` и `ffprobe` — статические бинарники kладутся в корень проекта;
     скрипт `package_macos_app.sh` копирует их в `Contents/Resources/bin/`.
   - `MP4Box` (GPAC) — системная установка через MacPorts (`sudo port install gpac`).
     Скрипт бандлирует `MP4Box` и все его dylib-зависимости в:
     - `Contents/Resources/bin/MP4Box`
     - `Contents/Resources/lib/*.dylib`
     Rpath в бандловом `MP4Box` патчится на `@executable_path/../lib`.
     Резолюция `MP4Box` из кода — через `TToolPaths.Mp4BoxBin` (функция
     `ResolveMp4BoxBin` в `tool_paths.pas`), которая сначала проверяет
     `Contents/Resources/bin/MP4Box`, затем системные пути.

Результат шага: воспроизводимая сборка и понятная документация.

## 6. Условия остановки/блокеры

Работы временно останавливаются, если:

1. Обнаружено расхождение аудио/видео-логики с CLI, требующее изменения C-ядра.
2. Не удается обеспечить инвариант output default folder.
3. Не удается обеспечить корректное overwrite-поведение.
4. Есть нестабильность shutdown, требующая архитектурной переработки ядра.

В каждом блокере оформляется короткий технический отчет с вариантами решения.

## 7. Риски и меры снижения

1. Риск: расхождение поведения UI и CLI
- Мера: baseline + регрессионные кейсы после каждого этапа.

2. Риск: ошибки thread-safety в callbacks
- Мера: строгая модель main-thread UI updates + isolate bridge.

3. Риск: рост сложности CMake
- Мера: отдельные target-файлы/секции для платформ.

4. Риск: скрытые изменения логики при “косметических” правках
- Мера: запрет изменений в `src/converter/*` в рамках UI-миграции.
5. Риск: отсутствие GPAC/MP4Box на машине сборки Pascal GUI
- Мера: `package_macos_app.sh` выводит WARNING и продолжает; Apple M4V
  не будет работать в бандле без MP4Box, но остальные функции сохраняются.
  На машине сборки обязателен `sudo port install gpac`.
## 8. Критерии готовности (Definition of Done)

Переход считается завершенным, если одновременно выполнены все пункты:

1. macOS GUI работает на нативном интерфейсе без GTK runtime.
2. Linux GUI продолжает работать на GTK4.
3. Инварианты соблюдены:
- логика аудио/видео неизменна;
- папка по умолчанию соблюдена;
- перезапись ведет себя строго по требованиям.
4. Нет crash при закрытии приложения.
5. Документация сборки и архитектуры обновлена.

2. День 2: Шаги 2-3 (UI каркас + bridge).
3. День 3: Шаг 4 (callbacks + start/stop).
4. День 4: Шаги 5-7 (shutdown + регрессия + инварианты).

## 10. Стартовые технические правила реализации

1. Не менять код ядра конвертации без отдельной согласованной задачи.
2. Любое изменение UI-мэппинга опций сопровождается smoke-проверкой.
3. Любой crash на exit считается blocking issue до исправления.
4. Для macOS UI использовать только main-thread операции с виджетами.
5. Для длинных технических сообщений использовать компактный лог-формат в UI.
