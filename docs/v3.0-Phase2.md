# Version 3.0 — Phase 2: Extended Codec and Preset Catalog

## 1. Goal

Extend the codec/preset catalog established in Phase 1:

1. Add **AMF AV1** codec with 4 presets (`default`/`speed`/`balance`/`quality`),
   and define real presets for the existing AMF H.264/HEVC codecs (which today
   have **no encoder parameters at all**).
2. Add three **Vulkan encoders** (H.264, HEVC, AV1) with the same 4-preset set.
3. Extend **existing hardware codecs** (VAAPI, NVENC, QSV) with
   `speed`/`balance`/`quality` presets in addition to their `default`.

Phase 2 is mostly **data work** (preset JSON entries) plus **runtime probing**
for the new encoders — thanks to the Phase 1 architecture, no command-builder
redesign is needed.

---

## 2. Naming Decision

The request used the names `amf_h264`, `vulkan_h264`, etc. The codebase and
ffmpeg both use the **codec_backend** order. Phase 2 keeps the existing
convention to avoid a rename across C, Pascal, CLI, GUI and docs:

| Requested name | Adopted name (= ffmpeg encoder name) |
|---|---|
| `amf_h264` | `h264_amf` (already in codebase) |
| `amf_hevc` | `hevc_amf` (already in codebase) |
| `amf_av1` | `av1_amf` (new) |
| `vulkan_h264` | `h264_vulkan` (new) |
| `vulkan_hevc` | `hevc_vulkan` (new) |
| `vulkan_av1` | `av1_vulkan` (new) |

Optional: accept `amf_h264`-style spellings as CLI aliases only (not as
canonical names). Default recommendation: **no aliases**.

## 5. Preset Parameter Design

All values below are **recommended starting points**. Every value must be
validated on real hardware (Section 10) before release. Values live in
`presets.json`, so tuning after release requires no code change.

### 5.1 AMF (`h264_amf`, `hevc_amf`, `av1_amf`)

AMF has a native quality knob: `-quality speed|balanced|quality`.

| Preset | h264_amf / hevc_amf | av1_amf |
|---|---|---|
| `default` | `-c:v h264_amf` (unchanged from today; AMF driver default = balanced) | `-c:v av1_amf` |
| `speed` | `-c:v h264_amf -quality speed` | `-c:v av1_amf -quality speed` |
| `balance` | `-c:v h264_amf -quality balanced` | `-c:v av1_amf -quality balanced` |
| `quality` | `-c:v h264_amf -quality quality` | `-c:v av1_amf -quality quality` |

Notes:
- `default` preserves current behavior byte-for-byte (zero regression).
- `av1_amf` requires **RDNA3+ (RX 7000 series)**; on older GPUs the encoder
  exists in ffmpeg but the one-frame probe fails → codec hidden.
- AMF on **Linux** requires the proprietary `amdgpu-pro` AMF component and is
  rarely present (HEVC limited to RX 5xxx/6xxx). The probe handles this —
  codecs simply do not appear in the menu.

### 5.2 Vulkan (`h264_vulkan`, `hevc_vulkan`, `av1_vulkan`)

Common pipeline (same as existing `prores_ks_vulkan`):

```
-init_hw_device vulkan=vk:{vk_device} -filter_hw_device vk   (pre-input)
-vf format=nv12,hwupload                                     (h264/hevc/av1, 8-bit)
```

Rate control: CQP (`-qp`) — deterministic and driver-agnostic. The encoder
option `-quality N` (quality levels) is driver-reported and most drivers
expose only level 0, so it is **not** used in Phase 2.

H.264/HEVC (QP range 0–51; ffmpeg's own fallback default is QP 18):

| Preset | h264_vulkan / hevc_vulkan |
|---|---|
| `default` | `-c:v h264_vulkan -qp 18` (matches current ffmpeg default behavior) |
| `speed` | `-c:v h264_vulkan -qp 28` |
| `balance` | `-c:v h264_vulkan -qp 23` |
| `quality` | `-c:v h264_vulkan -qp 18` |

AV1 uses a **QIndex 0–255** (different scale from H.264/HEVC QP):

| Preset | av1_vulkan |
|---|---|
| `default` | `-c:v av1_vulkan -qp 60` |
| `speed` | `-c:v av1_vulkan -qp 120` |
| `balance` | `-c:v av1_vulkan -qp 90` |
| `quality` | `-c:v av1_vulkan -qp 60` |

Notes:
- The `{vk_device}` placeholder is the same probed Vulkan adapter index used
  by `prores_ks_vulkan` (one `--vk_device` option for all `*_vulkan` codecs).
- `av1_vulkan` default must set an explicit `-qp`: without it some ffmpeg
  builds fall back to the **minimum** QIndex (near-lossless, huge files).
- All QP/QIndex values are starting points pending hardware validation.

### 5.3 VAAPI (`h264_vaapi`, `hevc_vaapi`)

Constraint discovered during Phase-1-era testing: **radeonsi rejects ICQ**
("supported modes: CQP, CBR, VBR"). Quality tiers therefore use CQP.

| Preset | Parameters |
|---|---|
| `default` | `-c:v h264_vaapi -rc_mode auto` (unchanged) |
| `speed` | `-c:v h264_vaapi -rc_mode CQP -qp 28` |
| `balance` | `-c:v h264_vaapi -rc_mode CQP -qp 24` |
| `quality` | `-c:v h264_vaapi -rc_mode CQP -qp 20` |

(HEVC analog: same `-rc_mode`/`-qp` values with `hevc_vaapi`.)

### 5.4 NVENC (`h264_nvenc`, `hevc_nvenc`)

Speed/quality trade-off via the preset ladder (`p1` fastest … `p7` slowest)
and lookahead.

`h264_nvenc` (current default: `-preset p7 -qp 22 -spatial_aq 1 -temporal_aq 1`):

| Preset | Parameters |
|---|---|
| `default` | unchanged |
| `speed` | `-c:v h264_nvenc -preset p1 -qp 22 -spatial_aq 1 -temporal_aq 1` |
| `balance` | `-c:v h264_nvenc -preset p4 -qp 22 -spatial_aq 1 -temporal_aq 1` |
| `quality` | `-c:v h264_nvenc -preset p7 -qp 22 -spatial_aq 1 -temporal_aq 1` (= default) |

`hevc_nvenc` (current default: `-preset hq -cq 25 -lookahead_level auto`):

| Preset | Parameters |
|---|---|
| `default` | unchanged |
| `speed` | `-c:v hevc_nvenc -preset p1 -cq 25 -lookahead_level 0` |
| `balance` | `-c:v hevc_nvenc -preset p4 -cq 25 -lookahead_level auto` |
| `quality` | `-c:v hevc_nvenc -preset p7 -cq 25 -lookahead_level auto` |

### 5.5 QSV (`h264_qsv`, `hevc_qsv`)

Speed/quality trade-off via `-preset` ladder and lookahead.

`h264_qsv` (current default: `-global_quality 22 -preset slower -look_ahead 1 -look_ahead_depth 40 -extbrc 1`):

| Preset | Parameters |
|---|---|
| `default` | unchanged |
| `speed` | `-c:v h264_qsv -global_quality 22 -preset veryfast -extbrc 1` (no lookahead) |
| `balance` | `-c:v h264_qsv -global_quality 22 -preset medium -look_ahead 1 -look_ahead_depth 40 -extbrc 1` |
| `quality` | unchanged (= default) |

`hevc_qsv` (current default: `-global_quality 25 -preset slow -g 240 -bf 4 -look_ahead 1 -look_ahead_depth 60 -extbrc 1`):

| Preset | Parameters |
|---|---|
| `default` | unchanged |
| `speed` | `-c:v hevc_qsv -global_quality 25 -preset fast -g 240 -bf 4` (no lookahead) |
| `balance` | `-c:v hevc_qsv -global_quality 25 -preset medium -g 240 -bf 4 -look_ahead 1 -look_ahead_depth 60 -extbrc 1` |
| `quality` | unchanged (= default) |

## 6. System Requirements for AMF/Vulkan Codecs

> A codec being **listed in `ffmpeg -encoders` does not mean it works** — the
> encoder must be present in the ffmpeg build **and** have a working runtime +
> GPU on the target system. The program's probe checks both; codecs that fail
> the one-frame encode probe are hidden from the menus.

### 6.1 AMF (`h264_amf`, `hevc_amf`, `av1_amf`)

**ffmpeg build:**
- compiled with `--enable-amf` (requires the AMF SDK headers at build time)

**Runtime:**
- AMF runtime library must be present:
  - Linux: `libamfrt64.so.1` — ships with the proprietary **AMDGPU-PRO** driver; Mesa does **not** provide it
  - Windows: `amfrt64.dll` — ships with the AMD driver
- `--enable-amf` at compile time only links the SDK headers. Without the
  runtime the encoder fails at initialization with
  `DLL libamfrt64.so.1 failed to open` and the probe hides the codec.

**GPU:**
- Windows: any AMD GPU supported by the current driver (GCN+ for H.264/HEVC);
  AV1 needs **RDNA3+ (RX 7000)**
- Linux: HEVC — **RX 5xxx/6xxx only**; AV1 — **RDNA3+**; Vega/GCN is not
  supported for AMF encode on Linux
- macOS: n/a

**Verification:**
```bash
ffmpeg -hide_banner -encoders | grep amf        # 1. encoder in build
ffmpeg -v error -f lavfi -i color=size=1920x1080:rate=1 \
  -frames:v 1 -c:v h264_amf -f null -           # 2. runtime + GPU probe
```
- `DLL libamfrt64.so.1 failed to open` → runtime missing (install AMDGPU-PRO)
- Other failure → GPU outside the supported range or driver problem

### 6.2 Vulkan (`h264_vulkan`, `hevc_vulkan`, `av1_vulkan`)

**ffmpeg build:**
- compiled with `--enable-vulkan` plus a shader compiler
  (`--enable-libshaderc` or `--enable-libglslang`)
- minimum versions: `h264_vulkan`/`hevc_vulkan` ≥ 7.1, `av1_vulkan` ≥ 8.0
  (bundled ffmpeg 8.1 satisfies all three)

**Runtime/driver** (requires the Vulkan Video encode extensions
`VK_KHR_video_encode_queue` + the codec-specific encode extension):
- Linux: Mesa **RADV** — encode on **RDNA3+** (RX 7000); ANV (Intel Arc) —
  experimental, known `VK_ERROR_DEVICE_LOST` reports; **llvmpipe** (software)
  never works
- Windows: NVIDIA proprietary driver, **Turing (RTX 20) or newer**; AMD's
  Windows driver does not expose Vulkan video encode
- macOS: n/a (MoltenVK has no video encode)

**Verification:**
```bash
ffmpeg -hide_banner -encoders | grep vulkan     # 1. encoder in build
vulkaninfo | grep -i video_encode               # 2. device capabilities
ffmpeg -v error -init_hw_device vulkan=vk:0 -filter_hw_device vk \
  -f lavfi -i color=size=1920x1080:rate=1 -frames:v 1 \
  -vf format=nv12,hwupload -c:v h264_vulkan -f null -   # 3. one-frame probe
```
- `Device does not support the VK_KHR_video_encode_queue extension!` →
  GPU/driver lacks Vulkan video encode

### 6.3 Reference test box (this system) — expected result

The reference system (AMD **Vega 20** / Radeon Pro VII, RADV driver) shows
**no** AMF or Vulkan codecs in the program menu. This is correct behavior:

| Codec family | Reason it is hidden |
|---|---|
| AMF | `libamfrt64.so.1` not installed; additionally Vega 20 is outside the AMF-on-Linux supported range |
| Vulkan encode | RADV on Vega 20 does not implement `VK_KHR_video_encode_queue` (RDNA3+ only) |

### 6.4 `prores_ks_vulkan` — practical reality

`prores_ks_vulkan` is a compute-shader ProRes encoder, not a hardware
codec — it must be probed and reported separately from the hardware
Vulkan encoders above.

Practical status today (per real-world testing):

| Platform / GPU | Result |
|---|---|
| **Windows + NVIDIA** | **The only working combination** |
| Linux/Windows + AMD | Works but unusably slow (compute-based, no ASIC) |
| Linux/Windows + Intel (ANV) | Corrupted video output |
| Linux + RADV | Not viable on current hardware |

So on this reference box (Vega 20 / RADV) the absence of
`prores_ks_vulkan` is **correct and expected** — it would not be usable
even if the encoder were present in the build.

**Why the encoder disappeared from the bundled ffmpeg 8.1** (CHANGELOG,
known issues 2026-08-20): unclear, but the only Vulkan-related change
between the previous ffmpeg bundle and the new one was switching from the
**LunarG Vulkan SDK** to the **system Vulkan SDK**. The re-enable work
must therefore verify not just the build flag but the Vulkan SDK
provenance, and confirm the encoder works via a real one-frame probe on a
Windows/NVIDIA box before shipping.

## 8. Runtime Probing Changes

### 8.1 New capability flags (`converter_platform.h`)

```c
#define PLAT_CAP_AMF_AV1      (1 << 14)
#define PLAT_CAP_VULKAN_H264  (1 << 15)
#define PLAT_CAP_VULKAN_HEVC  (1 << 16)
#define PLAT_CAP_VULKAN_AV1   (1 << 17)
```

### 8.2 Linux (`runtime_probe.c`)

- `LinuxCodecSupport`: add `has_av1_amf`, `has_h264_vulkan`, `has_hevc_vulkan`,
  `has_av1_vulkan` (+ working-device mask/count for the Vulkan family).
- `av1_amf`: reuse `probe_simple_encoder()` (no device path needed).
- New `probe_vulkan_encoder(ffmpeg_bin, encoder_name, ...)` modeled on
  `probe_vulkan_prores()`: scan `vk:0..7`, one-frame encode with
  `-vf format=nv12,hwupload`, same early-exit heuristic.
- **Fix the known llvmpipe issue** (CHANGELOG 2026-08-20): parse ffmpeg's
  `GPU listing:` and skip devices tagged `(software)` before probing. This is
  mandatory — without it a CPU-only box can report a "working" Vulkan encoder.
- **Performance optimization (recommended):** pre-filter with
  `ffmpeg -encoders` text scan (as Windows already does) before running
  one-frame probes. Adds 4+ new potential one-frame encodes otherwise; the
  pre-filter keeps startup time flat on systems without the hardware.

### 8.3 Windows (`platform_detect_gpu_support`)

Extend the existing `-encoders` text scan:

```c
if (strstr(line, " av1_amf"))       caps |= PLAT_CAP_AMF_AV1;
if (strstr(line, " h264_vulkan"))   caps |= PLAT_CAP_VULKAN_H264;
if (strstr(line, " hevc_vulkan"))   caps |= PLAT_CAP_VULKAN_HEVC;
if (strstr(line, " av1_vulkan"))    caps |= PLAT_CAP_VULKAN_AV1;
```

Note: text scan confirms encoder *presence*, not hardware support. Acceptable
for Windows (consistent with current behavior for NVENC/AMF/QSV); the real
conversion will surface a clear ffmpeg error if the GPU cannot encode.

### 8.4 Pascal mirror

`fpc/platform/linux_probe.pas` and the Windows probe mirror all new fields and
logic (per AGENTS.md sync requirement).

## 12. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Vulkan encode driver immaturity (known `VK_ERROR_DEVICE_LOST` reports on ANV/Mesa) | One-frame probe per device; unavailable/failed codecs hidden; clear ffmpeg error surfaced on conversion failure |
| Vulkan probe counts `llvmpipe` software device as a GPU (known issue) | Parse `GPU listing:` and exclude `(software)` entries — part of work item 3 |
| Bundled ffmpeg lost `prores_ks_vulkan` in the 8.1 rebuild; likely tied to the switch from LunarG to the system Vulkan SDK | Re-enable in build config (work item 7), verify Vulkan SDK provenance, and confirm the encoder via a one-frame probe on the only working platform (Windows/NVIDIA) before shipping |
| `prores_ks_vulkan` is practically unusable except on Windows/NVIDIA | Probe-gated menu handles it — on AMD (slow) and Intel (corrupted output) the codec is simply not offered; document the limited support explicitly (Section 6.4) |
| `av1_amf` needs RDNA3+; AMF on Linux needs proprietary drivers | Probe-gated menu — codecs simply don't appear |
| AV1 QIndex scale (0–255) differs from H.264/HEVC QP (0–51) | Separate values for `av1_vulkan` in Section 5.2; explicit `-qp` always set (avoids minimum-QIndex fallback in some builds) |
| radeonsi rejects ICQ rate control | VAAPI presets use CQP only (lesson from Phase-1-era testing) |
| Startup time growth from 4+ new one-frame probes | `-encoders` text pre-filter before one-frame confirmation |
| Naming mismatch (requested `amf_h264` vs codebase `h264_amf`) | Keep ffmpeg-consistent names (Section 2); optional CLI aliases only if explicitly requested |
| Windows text-scan probe confirms presence, not hardware capability | Accepted (matches existing NVENC/AMF/QSV behavior); runtime errors surface clearly |

## 13. Recommendations

1. **Keep `codec_backend` naming** (`h264_amf`, `av1_amf`, `h264_vulkan`, …) —
   consistent with ffmpeg encoder names, `PLAT_CAP_*` flags, and all existing
   code. Do not introduce `amf_h264`-style canonical names.
2. **Fix the two known Vulkan issues in Phase 2, not later:** llvmpipe
   software-device exclusion and the missing `prores_ks_vulkan` in the bundled
   ffmpeg. Both are cheap and both block a clean Phase 2 release.
3. **Investigate the `prores_ks_vulkan` build regression**: the only Vulkan
   change in the new ffmpeg bundle was switching from the LunarG Vulkan SDK
   to the system Vulkan SDK. Verify SDK provenance (headers, `vulkan.h`
   version, shader compiler) when re-enabling the encoder, and test on
   Windows/NVIDIA — the only combination where it is actually usable.
3. **Use CQP for all quality-tier presets** of VAAPI and Vulkan encoders —
   deterministic, driver-agnostic, and avoids ICQ driver rejections.
4. **Keep `default` = today's byte-for-byte strings.** Quality tiers are
   additive; no regression risk for existing users.
5. **Add the `-encoders` text pre-filter to Linux probing** before adding new
   one-frame probes (Windows already works this way).
6. **Reuse one probed Vulkan device index** (`--vk_device` / auto-detected)
   across all `*_vulkan` codecs including `prores_ks_vulkan`.
7. **Store all quality-tier numbers in `presets.json`** so post-release tuning
   (after user feedback on real hardware) requires no code change.
8. **Treat Section 5 values as starting points**; the validation work item
   (item 1) exists precisely to adjust them before release.
9. **AV1 output container: `.mkv`** (default branch of `make_output_name`) —
   no naming logic change needed.
10. **Document `prores_ks_vulkan` as Windows/NVIDIA-only in the user manual** —
    real-world testing shows it is unusable elsewhere (slow on AMD, corrupted
    output on Intel); the probe hides it on other platforms.
11. **Phase 3 candidates** that become nearly free after Phase 2: `av1_vaapi`,
    `av1_nvenc`, `av1_qsv` (same probe/preset pattern, mostly JSON data), and
    `hevc_videotoolbox` quality tiers for macOS.
