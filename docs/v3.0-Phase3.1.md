**Status:** Current Technical Specification — source-grounded

## 1. Purpose

Integrate the existing HQ Converter Library into ffmpeg-converter's native C/CMake implementation as a new video encoding backend named `hq_converter`.

**Architectural model:**

```
hq_converter = automatic Add Track video source
```

HQ Converter Library produces an external video track. After the track path is obtained, HQ-specific processing ends. The track is passed to the exact existing `add_track_execute()` pipeline, which handles audio processing, subtitle/chapter handling, metadata, container assembly, and final muxing.

## 2. Current Completed Architecture

The following components are complete and authoritative. They must **not** be reimplemented by the HQ integration.

### 2.1 Add Track Convergence Point

`add_track_execute()` is the mandatory convergence point for all Add Track flows.

**Function signature** (from `src/add_track/add_track.h`):

```c
ConverterError add_track_execute(
    Converter *converter,
    const AddTrackRequest *request,
    AddTrackResult *result
);
```

**Caller-owned lifecycle:** `add_track_execute()` does NOT create or destroy the `Converter`. All three interfaces (CLI, Linux GUI, macOS GUI) create and destroy the `Converter`; the pipeline uses the same instance and its callbacks.

**Contract:**
- Single file: processes exactly one `source_file`.
- Synchronous: blocks until conversion and mux complete.
- Thread-neutral: may be called from any thread.
- `ConverterCallbacks` must already be set on `converter`.

**Error contract:**
- Returns `ConverterError` (`ERR_OK` on success).
- Emits user-visible messages via the converter's `Callbacks`.
- If converter fails, mux is NOT called; error returned immediately.
- If mux fails, error returned; `output_file` in result is empty.

## 3. Non-Negotiable Architecture Invariants

### 3.1 HQ Produces Only an External Video Track

The only media-processing responsibility added by HQ integration is producing a video track path. After `video_track.path` is obtained, HQ-specific processing ends.

### 3.2 Mandatory Convergence with add_track_execute()

```
Manual Add Track -> user-selected video track -> add_track_execute()

HQ Converter -> HQ Library -> video_track path -> add_track_execute()
```

Both paths converge at `add_track_execute()`. No HQ-specific audio, mux, subtitle, chapter, attachment, metadata, or output-path logic is permitted.

### 3.3 No HQ-Specific Audio Engine

All HQ jobs use the existing Audio Orchestrator through `add_track_execute()`.

### 3.4 No HQ-Specific Mux Engine

The exact existing `mux_run_postprocess_for_preset()` is used.

### 3.5 One Shared Runtime HQ Catalog Provider

One provider loads the packaged HQ preset catalog at startup and serves both CLI and GUI. No hard-coded HQ codec/preset strings, no separate CLI/GUI catalogs, no copies into `presets.json.in`.

### 3.6 Working Directory Ownership

For queue item N: `<OutputDirectory>/task_N`. ffmpeg-converter owns the full lifecycle — creates, validates, passes to HQ, keeps until `add_track_execute()` returns, removes after completion.

### 3.7 No Additional Directory Layer

HQ Library uses `work_dir` directly. No integration-owned subdirectory is created inside `task_N`.

### 3.8 Final Output Isolation

`task_N` is temporary workspace. Final output is outside `task_N`. Removing `task_N` never affects the final output.

### 3.9 No New Ownership or Recovery Model

No persistent HQ job directories, session recovery, resume, retry, or stale-artifact reuse.

## 5. Actual HQ Public ABI Contract

**Source:** `HQ_converter/modules/library/include/hq_converter_library.h` (verified 2026-10-10)

### 5.1 Handle

```c
typedef struct hqclib_handle_s hqclib_handle_t;
hqclib_handle_t *hqclib_create_handle(void);
void hqclib_destroy_handle(hqclib_handle_t *handle);
```

Thread model: one `RunJob` at a time per handle; `request_stop`/`request_kill` from another thread; callbacks run on the `RunJob` thread.

### 5.2 Job Execution

```c
int32_t hqclib_run_job(
    hqclib_handle_t *handle,
    const char *input_file_utf8,     /* absolute path */
    const char *work_dir_utf8,       /* absolute path */
    const char *codec_utf8,          /* codec identifier from HQ catalog */
    const char *preset_utf8,         /* preset identifier from HQ catalog */
    hqclib_status_callback_t callback, /* may be NULL */
    void *user_context               /* passed through to callback */
);
```

**Synchronous.** Returns one of the result codes below.

### 5.3 Result Codes

| Code | Value | Meaning |
|------|-------|---------|
| `HQCLIB_RESULT_OK` | 0 | Success |
| `HQCLIB_RESULT_CANCELLED` | 1 | Cancelled by stop/kill |

| `HQCLIB_RESULT_INVALID_ARGUMENT` | 3 | Bad input parameters |
| `HQCLIB_RESULT_INVALID_UTF8` | 4 | Non-UTF-8 input path |
| `HQCLIB_RESULT_INVALID_STATE` | 5 | Library in wrong state |
| `HQCLIB_RESULT_IO_ERROR` | 6 | File system error |
| `HQCLIB_RESULT_CONTROL_ERROR` | 7 | Stop/kill forwarding failed |
| `HQCLIB_RESULT_INTERNAL_ERROR` | 8 | Internal error |
| `HQCLIB_RESULT_NOT_RUNNING` | 9 | Control action while idle |

### 5.4 Stop and Kill


During Segmentator: stop is deferred until Segmentator returns.

On success (`HQCLIB_RESULT_OK`), returns `0` and sets error to empty string.

### 5.7 Session Files — Input and Result

The HQ Library produces **two** session files in `task_N`. They serve different purposes and must not be confused.

#### Input Session (configuration)

```
<work_dir>/job.<codec>.<preset>.json
```

Created earlier by the HQ workflow (typically via `session_create_wizard`). Contains configuration parameters, requested output names, and session parameters. **ffmpeg-converter does not read this file for results.**

#### Result Session (authoritative output)

```
<work_dir>/job.<codec>.<preset>.eov2.session.json
```

Generated by the encoder orchestrator after successful encoding. This is the **authoritative result file** used by ffmpeg-converter.

**JSON structure** (verified from a real generated session):

```json
{
  "schema_version": "v1",
  "module": "encoder_orchestrator_v2",
  "job_id": "job-<timestamp>",
  "run_id": "run-<timestamp>",
  "session_params": {
    "encoder_type": "<codec>",
    "policy": "<policy>",
    "work_dir": "<absolute_work_dir>",
    "job_path": "<absolute_path_to_job_json>"
  },
  "artifacts": {
    "outputs": {
      "video_track": {
        "path": "/absolute/path/to/output.<ext>",
        "container": "unknown",
        "state": "ready"
      }
    }
  }
}
```

**Verified path behavior:** The path in `artifacts.outputs.video_track.path` is **absolute**. Current verified HQ releases provide an absolute video track path. If future HQ releases change this behavior, the path resolution policy must be explicitly revised.

**Result retrieval rules:**
- ffmpeg-converter reads the eov2 session file **only** after documented HQ success (`HQCLIB_RESULT_OK`).
- ffmpeg-converter does **not** scan `task_N` for candidate files.
- ffmpeg-converter does **not** infer output names from file discovery.
- ffmpeg-converter does **not** guess filenames.
- ffmpeg-converter does **not** read the session file after failure or cancellation.
- Failure and cancellation are never overridden by existing files.
- No callback-schema extension is required.
- No new library getter is required.

## 6. Authoritative Runtime-Root Resolution Model

### 6.1 Rule: Single Resolved Root

The application resolves exactly one absolute HQ runtime root path at startup. All HQ paths are derived from it. No component independently guesses paths.

### 6.2 Rule: No Current-Working-Directory Dependence

The current working directory is **never** an authoritative runtime root. Applications must start correctly when launched outside the source tree or installation directory.

### 6.3 Rule: `third_party/hq_converter` Is a Build Input, Not an Installed Location

After CMake copies the release, the application uses the copied location, not `third_party/`.

---

### 6.4 Complete Runtime Layout Preservation

**The complete prepared HQ release directory structure must be preserved.**

Partial copying, flattening, selective extraction, or reconstruction of the runtime tree is prohibited. The implementation must assume the runtime layout is authoritative.

The library resolves preset paths by reading `toolchain_runtime.ini` from within `modules/encoder_orchestrator_v2/config/`, then resolving binary paths relative to that location. Any disruption to this structure breaks resource discovery.

### 6.5 Authoritative Runtime Root

The application resolves exactly one absolute HQ runtime root path at startup. All HQ paths are derived from that root.

**Linux (local build, installed application, AppImage):**

```
<executable_dir>/hq_converter/
```

**macOS (`.app` bundle):**

```
<Application>.app/Contents/Resources/hq_converter/
```

**macOS (standalone CLI):**

```
<executable_dir>/hq_converter/
```

**No HQ component independently resolves alternate runtime roots.** No current-working-directory logic. No source-tree dependency. No `third_party` dependency after build or packaging.

No component in ffmpeg-converter independently guesses paths.

### 6.9 Path Resolution Rules

1. The current working directory is never an authoritative runtime root.
2. Source-tree paths are never used after installation or packaging.
3. `third_party/hq_converter` is a build input, not an installed runtime location.
4. CMake copies the complete prepared release to the authoritative output location.
5. The application resolves one absolute HQ runtime root.
6. All library, catalog, configuration, and runtime paths are derived from that root.
7. The resolved path must be normalized and validated before use.
8. Linux and macOS path logic may differ internally but implement the same runtime-root contract.
9. Environment-variable overrides are development/diagnostic overrides only.
10. Environment-variable overrides must not be required for normal packaged execution.

12. A path override must refer to the prepared runtime root or to an explicitly documented file.

14. Missing runtime resources must fail only HQ availability, not unrelated backends.
15. ffmpeg-converter must not repair, rewrite, or regenerate the packaged HQ runtime at startup.

## 7. Environment Variable Policy

**Source inspection results** (from `hq_library_core.pas` and `session_create_wizard.pas`):

### 7.1 `HQ_PROJECT_ROOT` (ffmpeg-converter sets this)

- **Owner:** ffmpeg-converter (set internally at startup)
- **Purpose:** Guide the HQ Library to the correct `modules/` directory for preset catalog and toolchain discovery
- **Value:** `<runtime_root>` (the runtime root itself, **not** `<runtime_root>/modules/`)
- **Required:** Yes — set by the application at startup; not a user-facing requirement
- **Why the runtime root:** `DetectProjectRootFromExecutable` in `hq_library_core.pas` checks
  `DirectoryExists(HQ_PROJECT_ROOT + 'modules')`. The value must be a directory whose child
  `modules/` exists. Setting it to `<runtime_root>/modules/` would cause the library to look
  for `<runtime_root>/modules/modules/` which does not exist.
- **Set before dlopen:** Environment variables consumed by the Pascal HQ Library must be set
  before `dlopen()`. Setting them after `dlopen()` is unreliable because the Pascal RTL
  reads environment variables at library initialization.
- **Additional env var:** `HQ_SEGMENTATOR_TOOLCHAIN_INI` is also set to the absolute path
  of `<runtime_root>/modules/segmentator/config/toolchain_runtime.ini`. The segmentator
  has its own path resolution via relative traversal from `ParamStr(0)` which fails in
  packaged deployments. The override provides the exact absolute path.
- **Development override:** Not required
- **Packaged execution:** Set internally by the application
- **User-facing:** No. Packaged applications set it internally. Users must not be required to define it.
- **Only HQ-specific env var ffmpeg-converter sets:** `HQ_PROJECT_ROOT` and `HQ_SEGMENTATOR_TOOLCHAIN_INI` are the two HQ-specific environment variables that ffmpeg-converter sets. Both are internal, not user-facing. All other environment variables (`FFMPEG_BIN`, `FFPROBE_BIN`, etc.) are handled by existing tool discovery mechanisms.

### 7.2 `PRESETS_PATH` (ffmpeg-converter internal)

- **Owner:** ffmpeg-converter (preset_loader.c)
- **Purpose:** Override the location of `presets.json`
- **Required:** No — resolves via exe dir, config dir, or built-in fallback
- **ffmpeg-converter sets it:** Yes (from GUI code when `PRESETS_PATH` is set by the environment)
- **Development override:** Yes
- **Packaged execution:** Not required

### 7.3 `FFMPEG_BIN`, `FFPROBE_BIN`, `MKVMERGE_BIN`, `MP4BOX_BIN`

- **Owner:** ffmpeg-converter tool discovery
- **Purpose:** Override tool locations
- **Required:** No — falls back to PATH
- **ffmpeg-converter sets them:** Yes (when bundled tools are found)
- **Development override:** Yes
- **Packaged execution:** Set by the application to bundled tool paths

### 7.4 `HQ_CONVERTER_ENABLED` (CMake feature flag)

- **Owner:** CMake → presets.json → application runtime
- **Purpose:** Feature availability flag (true when HQ release is present at build time)
- **Required:** Yes for HQ availability
- **ffmpeg-converter reads it:** From generated `presets.json` at startup
- **Not an environment variable at runtime**

### 7.5 Variables NOT Required by HQ

The following are **not** required by the current HQ Library:

- `LD_LIBRARY_PATH` overrides for HQ dependencies
- `HQ_LIBRARY_PATH` (not used by the library)
- `HQ_WORK_DIR` (passed explicitly to `hqclib_run_job`)
- Any path to the HQ source checkout

## 8. Build-Time Availability

### 8.1 CMake Detection

CMake validates the prepared release at `third_party/hq_converter` during `cmake` configure:
- Checks required paths (library, preset catalog).
- Copies the complete release to the executable-adjacent runtime location.
- Sets `features.hq_converter` to `true` in generated `presets.json` when the release passes validation.
- Windows builds always generate `false`.

### 8.2 Runtime Catalog

The application loads actual HQ codec and preset identifiers from the packaged HQ preset catalog **at startup**.

**Discovery process:**
1. The HQ preset catalog is discovered using the packaged HQ runtime layout and `HQ_PROJECT_ROOT`.
2. `HQ_PROJECT_ROOT` is set to `<runtime_root>/modules/`.
3. The library reads `toolchain_runtime.ini` from `<HQ_PROJECT_ROOT>/encoder_orchestrator_v2/config/`.
4. The `preset_path` entry (`presets/encoder_presets_v2.json`) is resolved relative to the `toolchain_runtime.ini` directory.
5. The final catalog path is `<runtime_root>/modules/encoder_orchestrator_v2/config/presets/encoder_presets_v2.json`.

**No source-tree location is used after packaging.** The application reads the catalog from the copied runtime tree, not from `third_party/` or the source checkout.

The feature flag (`features.hq_converter`) controls whether HQ is exposed. The flag is **not** a copy of the catalog content.

**One shared runtime provider.** One provider loads the packaged HQ preset catalog at startup and serves both CLI and GUI. No separate GUI catalog. No copied preset database. No preset regeneration at runtime. No hard-coded HQ codec or preset strings.

## 10. task_N Ownership and Lifecycle

### 10.1 Directory Assignment

For queue item N: `<OutputDirectory>/task_N`.

### 10.2 Lifecycle

1. **Creation:** ffmpeg-converter creates `task_N` and validates read/write access and free space (≥ input file size × 2).
2. **Pass to HQ:** The absolute `task_N` path is passed to `hqclib_run_job()` as `work_dir_utf8`.
3. **HQ writes directly:** HQ writes the session file, segment artifacts, and video track directly into `task_N`. No additional subdirectory layer.
4. **Read result:** After library success, ffmpeg-converter reads the eov2 session file `job.<codec>.<preset>.eov2.session.json` to obtain `artifacts.outputs.video_track.path`.
5. **Handoff to add_track_execute():** The video track path is passed to `add_track_execute()`.
6. **Cleanup:** After `add_track_execute()` returns (success or failure), `task_N` is removed recursively.

### 10.3 Cleanup Timing

`task_N` must NOT be removed until `add_track_execute()` returns and no active processing still needs the HQ video track. The final user-visible output must remain outside `task_N`.

### 10.4 Failure Scenarios

Cleanup of `task_N` occurs in every scenario:
- HQ success + successful final assembly
- HQ failure
- Cancellation
- Add Track failure
- Audio processing failure
- Mux failure
- Final output failure

```c
    work_dir_path,     /* absolute path to task_N */
    codec,             /* HQ codec identifier from catalog (e.g., "x264") */
    preset,            /* HQ preset identifier from catalog (e.g., "youtube4k") */
    status_callback,   /* progress bridge (may be NULL) */
    user_context       /* may be NULL */
);
```

### 11.2 Invocation Flow

1. Create handle: `hqclib_create_handle()`.
2. Optionally register callback via a wrapper (the callback is passed directly to `hqclib_run_job`).
3. Call `hqclib_run_job()`.
4. On success (`HQCLIB_RESULT_OK`): read the eov2 session file `job.<codec>.<preset>.eov2.session.json` to obtain `video_track.path`.
5. On failure: call `hqclib_get_last_error()` to obtain error text.
6. Destroy handle: `hqclib_destroy_handle()`.

### 11.3 Synchronous Execution

The call blocks until HQ completes or is cancelled. The active queue item is blocked during this time.

## 14. Direct Handoff to add_track_execute()

### 14.1 Integration Contract

After `artifacts.outputs.video_track.path` is obtained from the eov2 session file:

**HQ-specific processing ends immediately.**

The next and only operation is:

```
add_track_execute()
```

### 14.2 No HQ-Specific Post-Processing

After the video track path is obtained:
- No HQ-specific audio processing.
- No HQ-specific mux processing.
- No HQ-specific assembly phase.
- No HQ-specific container logic.
- No HQ-specific output-path logic.

All remaining operations use the exact existing Add Track pipeline:
- Audio-track selection (Audio Orchestrator).
- Audio copy or encoding.
- Audio-filter application.
- Subtitle handling.
- Chapter handling.
- Attachment handling.
- Global-tag and track-tag handling.
- Metadata handling.
- Container selection and assembly (Mux).
- Output-path selection.

### 14.3 Minimal Adapter

The HQ integration adapter:
1. Obtains `video_track.path` from the eov2 session file.
2. Sets `convert_options->video_track_path` to the obtained path.
3. Creates an `AddTrackRequest` with:
   - `source_file` = the original input file path.
   - `convert_options` = the existing `ConvertOptions` with `video_track_path` set.
4. Calls `add_track_execute(converter, &request, &result)` directly.
5. Waits for it to return.
6. Cleans up `task_N` after the call returns.

**No wrapper.** No wrapper between HQ and `add_track_execute()`. The adapter is thin: it prepares the request, calls the function, and cleans up.

### 14.4 AddTrackRequest Unchanged

**No AddTrackRequest modifications are required.** The existing two fields (`source_file`, `convert_options`) are sufficient. `convert_options->video_track_path` is already present in `ConvertOptions` for the exact purpose of carrying an external video track path.

## 16. Stop and Cancellation

### 16.1 Active HQ Job

```
converter_stop() -> wrapper detects active HQ handle -> hqclib_request_stop(handle)
```

### 16.2 Stop During Segmentator

During Segmentator: stop is deferred until Segmentator returns, then the job is cancelled. No session file is created.

### 16.3 Stop During Encoder

During Encoder: stop is forwarded through `encoder_orchestrator_api_adapter`. The job completes with `HQCLIB_RESULT_CANCELLED`.

### 16.4 Stop Before HQ Handle Exists

If `converter_stop()` arrives before the HQ handle is created: the stop flag is recorded on the converter. After HQ returns success, the flag is checked before calling `add_track_execute()`. If stopped, `add_track_execute()` is not called; the item is skipped.

### 16.5 Stop After HQ Success

After HQ returns success and the video track is passed to `add_track_execute()`: existing Add Track and Mux cancellation behavior is authoritative. The HQ session file and video track remain valid during `add_track_execute()`.

### 16.6 Cancel During Add Track

If cancellation occurs while `add_track_execute()` is running: existing cancellation behavior applies. No HQ resources need cleanup (HQ handle was already destroyed).

### 16.7 Cleanup on Cancel

On cancellation: `task_N` is removed. No HQ result is used. The session file is not read.

## 17. Error Handling

### 17.1 HQ Error Scope

An HQ error affects only the current queue item. It does NOT affect unrelated backends or later queue items.

### 17.2 Error Text

On failure: call `hqclib_get_last_error()` to obtain the library's error text. Include it in the user-visible message.

### 17.3 Error Examples

```
movie.mkv - HQ failed
movie.mkv - codec/preset not found
movie.mkv - HQ runtime unavailable
movie.mkv - HQ catalog unavailable
movie.mkv - insufficient free space
movie.mkv - working directory unavailable
movie.mkv - cancelled
```

### 17.4 Error Recovery

After any HQ error:
- Do NOT start Add Track or Mux for the current item.
- Do NOT use partial HQ results.
- Do NOT reuse stale files from `task_N`.
- Do NOT attempt HQ session recovery.
- Do NOT select an alternate codec or preset automatically.
- Release HQ resources.
- Remove `task_N`.
- Continue according to existing queue behavior.

## 18. Cleanup and Final-Output Isolation

### 18.1 Cleanup

After the queue item finishes (any outcome):

```
<OutputDirectory>/task_N   ← remove recursively
```

Cleanup is limited to `task_N` and does not follow external symbolic links.

### 18.2 Final-Output Isolation

The final user-visible output is at the normal ffmpeg-converter destination, determined by the existing output workflow. It is outside `task_N`. Removing `task_N` never affects the final output.

## 19. Queue Behavior

A failed or cancelled HQ item does NOT terminate processing of unrelated later queue items. The existing queue model is authoritative. No new persistent queue, resume, recovery, or retry system.

## 26. Runtime Path Resolution — Problems and Solutions

### 26.1 Problem Statement

The HQ Library is a Pascal shared library. During implementation, two path resolution
failures were encountered that required changes to the implementation beyond the original
specification. The failures were caused by **when** environment variables were set relative
to library load and **which** components read environment variables at initialization time.

### 26.2 Problem 1: Environment Variables Set After dlopen

**Symptom:** Setting `HQ_PROJECT_ROOT` after `dlopen()` was unreliable. The HQ Library's
Pascal runtime may cache environment variable values at library load time (when the shared
object is mapped into the process). Variables set after `dlopen()` were not seen by the
library.

**Root cause:** The Pascal RTL reads `GetEnvironmentString` / `GetEnvironmentVariable`
at library initialization. The exact point of initialization depends on `dlopen()`
implementation (lazy binding, thread-safe init) and the library's own initialization
order. Setting the variable after `dlopen()` but before the first call that uses it is
not guaranteed to work.

**Solution:** Set all required environment variables **before** `dlopen()` in
`load_hq_library()`:

```c
static int load_hq_library(void)
{
    runtime_root = hq_resolve_runtime_root();
    if (!runtime_root)
        return 0;

    /* Set HQ_PROJECT_ROOT BEFORE dlopen.
     * The Pascal runtime may cache environment variable values at load
     * time. Setting them afterwards is unreliable. */
    setenv("HQ_PROJECT_ROOT", runtime_root, 1);

    /* Set segmentator override */
    char seg_ini[4096];
    snprintf(seg_ini, sizeof(seg_ini),
             "%s/modules/segmentator/config/toolchain_runtime.ini",
             runtime_root);
    setenv("HQ_SEGMENTATOR_TOOLCHAIN_INI", seg_ini, 1);

    /* NOW dlopen */
    g_hq_lib_handle = dlopen(lib_path, RTLD_NOW);
    ...
}
```

**Contract:** All environment variables consumed by the HQ Library must be set before
`dlopen()`. No environment variable may be set after `dlopen()` in the expectation that
the library will see it.

### 26.3 Problem 2: HQ_PROJECT_ROOT Value Mismatch

**Symptom:** Setting `HQ_PROJECT_ROOT` to `<runtime_root>/modules/` (the value
documented in the original specification) failed with:

```
ERROR: toolchain config file not found: /home/viktor/modules/encoder_orchestrator_v2/config/toolchain_runtime.ini
```

The error path showed the variable was being used as a base for path concatenation
without the expected `/modules/` suffix — i.e., the value was being used as the
runtime root itself.

**Root cause:** In `hq_library_core.pas` (verified source), the Pascal function
`DetectProjectRootFromExecutable` checks:

```pascal
if DirectoryExists(HQ_PROJECT_ROOT + 'modules')
```

This means `HQ_PROJECT_ROOT` must be a directory whose **child** `modules/` exists.
The original specification stated the value should be `<runtime_root>/modules/`, but
the library code concatenates `modules` to whatever value is set.

**Solution:** Set `HQ_PROJECT_ROOT` to the **runtime root itself** (not the `modules/`
subdirectory):

```c
setenv("HQ_PROJECT_ROOT", runtime_root, 1);
// runtime_root = <exe_dir>/hq_converter/
// Check: <runtime_root>/modules/ exists ✓
```

### 26.4 Problem 3: Segmentator Path Resolution

**Symptom:** The segmentator (a separate Pascal component used by the HQ Library for
input file processing) could not find `toolchain_runtime.ini`:

```
ERROR: toolchain config file not found: /home/viktor/modules/encoder_orchestrator_v2/config/toolchain_runtime.ini
```

**Root cause:** The segmentator uses `DetectSegmentatorProjectRoot` which resolves paths
via **relative traversal** from `ParamStr(0)` (the executable path):

```pascal
function DetectSegmentatorProjectRoot: string;
var
  I: Integer;
begin
  for I := 0 to 10 do
  begin
    if FileExists(IncludeTrailingPathDelimiter(Result) + 'config/toolchain_runtime.ini')
      then Exit(Result);
    Result := IncludeTrailingPathDelimiter(ExtractFileDir(Result));
  end;
  Result := '';
end;
```

This relative traversal works in the original HQ project tree but **fails in any packaged
deployment** where the executable is in `<exe_dir>/` and the `modules/` tree is in
`<exe_dir>/hq_converter/modules/`. The traversal depth doesn't align with the installed
layout.

**Solution:** Set `HQ_SEGMENTATOR_TOOLCHAIN_INI` — an override recognized by the segmentator
that provides the absolute path directly:

```c
char seg_ini[4096];
snprintf(seg_ini, sizeof(seg_ini),
         "%s/modules/segmentator/config/toolchain_runtime.ini",
         runtime_root);
setenv("HQ_SEGMENTATOR_TOOLCHAIN_INI", seg_ini, 1);
```

### 26.5 Problem 4: HQ Library Requires Absolute Input Path

**Symptom:** HQ returned the error:

```
HQ failed: input_file must be an absolute path
```

when the CLI received a relative input path (e.g., `test.mkv` from the repository root).

**Root cause:** `hqclib_run_job()` validates that `input_file_utf8` is an absolute path.
The CLI passes file arguments as-is without canonicalization.

**Solution:** Resolve the input path to an absolute path before calling `hqclib_run_job()`:

```c
char abs_input_path[PATH_MAX];
if (realpath(files[fi], abs_input_path) == NULL) {
    /* Fallback: prepend CWD */
    char cwd[PATH_MAX];
    if (getcwd(cwd, sizeof(cwd)))
        snprintf(abs_input_path, sizeof(abs_input_path), "%s/%s", cwd, files[fi]);
}
```

### 26.6 Verified Runtime Layout

After the fixes above, the runtime layout that works is:

```
<executable_dir>/
    ffmpeg_converter          (CLI binary)
    hq_converter/             (complete copied tree from third_party/hq_converter/)
        modules/
            library/
                bin/
                    libhq_converter.so
            encoder_orchestrator_v2/
                config/
                    toolchain_runtime.ini
            segmentator/
                config/
                    toolchain_runtime.ini
```

The required environment variables are:

| Variable | Value | Set By |
|----------|-------|--------|
| `HQ_PROJECT_ROOT` | `<exe_dir>/hq_converter/` (the runtime root) | ffmpeg-converter, before dlopen |
| `HQ_SEGMENTATOR_TOOLCHAIN_INI` | `<exe_dir>/hq_converter/modules/segmentator/config/toolchain_runtime.ini` | ffmpeg-converter, before dlopen |

### 26.7 Impact on Existing Specification Sections

- **Section 7.1** — The value for `HQ_PROJECT_ROOT` is corrected from
  `<runtime_root>/modules/` to `<runtime_root>`. The purpose and ownership rules
  remain unchanged.
- **Section 7** — `HQ_SEGMENTATOR_TOOLCHAIN_INI` is a new environment variable that
  ffmpeg-converter sets (in addition to `HQ_PROJECT_ROOT`). It is internal, not
  user-facing.
- **Section 6.9** — The path override rules remain valid. The segmentator override is
  an additional override specific to the segmentator's path resolution mechanism.
- **Section 24** — Items 4 (HQ Library dynamic dependencies) and 5 (HQ preset catalog
  exact path) are now **verified** through end-to-end testing.

### 26.8 General Rule

**The Pascal RTL inside the HQ Library reads environment variables at library init time,
not on every access. Environment variables must be set before `dlopen()`. Any environment
variable that is set after `dlopen()` depends on the specific library's implementation
details and is not guaranteed to be observed.**

This rule applies to all future shared-library integrations with the Pascal runtime as well.

## 28. Code Review Findings and Fixes (Post-Implementation Verification)

This section records the results of an independent code review of the unpushed
HQ Converter integration + refactor commits, the bug reports that triggered it,
the fixes applied, and the live test results that verified them. It supersedes
Section 27's open items where they overlap.

### 28.1 Original Symptom

Reported behavior with HQ + mux (ProRes HQ encoder, mkvmerge mux postprocess):
with a queue of 2+ source files, the first file converted successfully; the
second file's HQ encode completed, but the program exited (CLI) or hung/was
force-closed (GUI) before the mux step ran. A stray `task_N` working directory
was left behind in the output folder.

### 28.2 Findings and Fixes

1. **ProRes HQ `.mov` container mismatch** (`src/add_track/add_track.c`).
   `add_track_execute()` didn't recognize HQ's `hw_device`/`preset` field
   semantics (real encoder id / encoder preset name, not a container
   keyword), so `converter_make_output_name()` and
   `mux_run_postprocess_for_preset()` picked the wrong container/preset for
   ProRes HQ jobs. Fixed by detecting the ProRes-HQ case via
   `hq_catalog_is_prores_codec()` and substituting `codec="prores_ks"` /
   `preset="mov"` locally (without mutating the caller's `ConvertOptions`)
   before calling those two functions.

2. **Intermediate file left on disk after ProRes HQ + mux** (same file).
   When the HQ-encoded intermediate (`*_converted.mkv`) and the final muxed
   output (`*.mov`) are different files (the ProRes case), mkvmerge writes a
   new final file rather than overwriting the intermediate in place, leaving
   the intermediate behind. Fixed with a `platform_unlink(intermediate_file)`
   call guarded by `strcmp(intermediate_file, final_file) != 0`, so the
   common non-ProRes case (where mkvmerge overwrites the intermediate path
   directly) is left untouched.

3. **CLI rejected HQ queues of more than one file** (`src/cli/main.c`). A
   leftover `if (file_count != 1) { ...; goto cleanup; }` guard blocked
   multi-file HQ jobs entirely; a second guard used `goto cleanup` instead of
   `continue` on a per-file directory-creation failure, aborting the whole
   queue on one bad file. Both removed/fixed so the CLI HQ path iterates the
   full file queue like the non-HQ paths already did.

4. **GUI HQ path was never architected for queues** (`src/gui/gui_callbacks.c`,
   `src/gui_macos_native/converter_bridge.m`). Unlike the CLI, the GTK and
   Cocoa GUIs' HQ code paths only ever handled `file_list[0]` — there was no
   per-file loop, no per-file `task_N` directory, and an explicit
   `fileCount != 1` early-reject. Rewrote both to loop over the full queue
   (mirroring the CLI's per-file `task_N` creation / `hq_run_job()` /
   `add_track_execute()` / cleanup sequence), reusing one `HqAdapter` across
   all files in the run.

5. **No Stop/Cancel wiring for HQ jobs in either GUI** (`src/gui/gui_window.h`,
   `src/gui/gui_callbacks.c`, `src/gui_macos_native/converter_bridge.m`).
   `stop_conversion()`/`shutdown_conversion()` (GTK) and the Cocoa stop path
   only ever called `converter_stop()`, which the HQ worker process doesn't
   observe. Added a `current_hq_adapter`/`_hqAdapter` field (mirroring the
   existing `current_converter` pattern, same mutex/`@synchronized` guard)
   and call `hq_request_stop_from_converter()` on it from both stop paths.

### 28.3 GUI-Specific Hang: fork() in a Multi-Threaded Process

After fixes #3–5 above, CLI multi-file HQ+mux queues passed cleanly, but the
GUI (GTK) still exhibited the original symptom on a 2-file queue: first file's
HQ job completed, second file's HQ job hung after encoding, before the mux
handoff, leaving its `task_N` directory on disk.

**Root cause:** `hq_run_job()` (`src/hq/hq_adapter.c`) executes each HQ job in
a `fork()`ed worker process for crash isolation, but the original
implementation continued running non-async-signal-safe code in the forked
child — `dlopen()`-resolved library calls, `malloc()`, `pthread_create()` —
before `_exit()`. `fork()`ing from a multi-threaded process (the GTK GUI
always has at least a main thread and a background conversion-worker thread,
plus a hardware-probe thread) risks inheriting glibc's malloc-arena lock in a
permanently-locked state if another thread held it at the instant of
`fork()`; the forked child then deadlocks on its first `malloc()`, since no
thread exists in the child to release the lock. This is a well-documented
POSIX `fork()` hazard. It does not affect the CLI (single-threaded, so
immune), and its odds compound with each subsequent `hq_run_job()` call in
the same run — consistent with the observed "first file OK, second file
hangs" pattern and the orphaned `task_N` directory (the child never reaches
`_exit()`, so the parent's `waitpid()`/frame-read loop never completes and
the cleanup step is never reached).

**Fix:** The forked child now immediately `execve()`s a new, dedicated helper
binary (`hq_worker`, built from the new `src/hq/hq_worker_main.c`) instead of
continuing to run inline. A freshly exec'd process image has its own
pristine, single-threaded C runtime and malloc state, so no lock can be
inherited in a locked state regardless of what the parent's other threads
were doing at fork time. Implementation details:

- `hq_adapter.c` gained `hq_exec_worker_or_exit()` (resolves the sibling
  `hq_worker` binary's path via the existing `resolve_exe_dir()`, builds argv
  with the pipe fd numbers plus job parameters, calls `execve()` — using only
  stack buffers, no `malloc()`/`dlopen()`) and `hq_worker_main_entry()` (the
  new worker process's actual entry point: loads the HQ library fresh in
  this process, then runs the job exactly as before).
- Pipe fds survive both `fork()` and `execve()` unchanged (no `O_CLOEXEC` by
  default), so no `dup2()` juggling is needed — fd numbers are simply passed
  as decimal-string argv.
- `execve()` (not `execvp()`) is used deliberately: `execvp()`'s `$PATH`
  search allocates memory internally, which would reintroduce the same race
  before the image is actually replaced.
- Build wiring: `hq_worker` is a new executable target in
  `src/hq/CMakeLists.txt`, placed in the same output directory as each
  platform's main binary (`linux_cli`/`linux_gui`: `CMAKE_BINARY_DIR/bin`;
  `macos_cli`/`macos_gui_native`: explicit `POST_BUILD` copy next to the
  target, since those don't share `hq_worker`'s `RUNTIME_OUTPUT_DIRECTORY`),
  with `add_dependencies()` ensuring it builds alongside each main target.

**Verification:** A standalone harness reproducing the GUI's threading model
(a thread continuously allocating/freeing memory concurrently with a second
thread driving `hq_run_job()` through a real 2-file ProRes HQ+mux queue,
linked against the actual built `hq_adapter`/`converter`/`platform` static
libraries) ran 5/5 consecutive times without a hang, after previously having
no live GUI reproduction available in this sandbox (no Xvfb/broadway/
automation tooling was viable here) to directly capture the race. The real
CLI 2-file ProRes HQ+mux queue was also re-verified end-to-end after the fix:
both files completed, correct `.mov` outputs, no leftover `task_N`
directories, exit code 0.

### 28.5 Known Remaining Gaps / Not Fully Verified

  pass before relying on it for production use.

  invariant 5; this review only verified ffmpeg-converter's client-side

  presets per 28.4) is out of scope and was not independently audited here.
