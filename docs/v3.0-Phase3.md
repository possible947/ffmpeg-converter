# Version 3.0 — Phase 3: HQ Converter Integration via HQ Library

**Status:** Final Technical Specification  
**Integration boundary:** HQ Converter Library C ABI  
**Supported platforms:** Linux and macOS  
**Excluded platform:** Native Windows; WSL is outside the ffmpeg-converter integration scope

---

## 1. Goal

Integrate HQ Converter into ffmpeg-converter as a first-class high-quality video encoding backend:

```text
hq_converter
```

The integration uses the production-validated HQ Converter Library as the sole boundary between the two projects.

The resulting user workflow is:

```text
Input file
    ↓
ffmpeg-converter audio processing
    ↓
HQ Library segmented video encoding
    ↓
ffmpeg-converter final mux
    ↓
Final media file
```

The user selects only:

```text
hq_converter
+ HQ Codec
+ HQ Preset
```

No HQ processing parameters or overrides are exposed by ffmpeg-converter.

Phase 3 depends on the codec-to-preset model and dynamic preset menus introduced in Phase 1. Phase 2 remains orthogonal.

---

## 2. Governing Architecture

The normative integration chain is:

```text
ffmpeg-converter
        ↓
HQ Converter Library
        ↓
Segmentator
        ↓
Encoder Orchestrator v2
```

HQ Converter Library is the only supported integration boundary.

ffmpeg-converter must not directly:

- invoke Segmentator;
- invoke Encoder Orchestrator v2;
- connect to Encoder Orchestrator control sockets;
- generate HQ jobs or sessions;
- inspect or modify HQ session state;
- validate HQ artifacts;
- reconstruct an HQ execution queue;
- aggregate QP data;
- interpret HQ preset contents;
- implement HQ recovery logic;
- calculate HQ FPS or ETA;
- duplicate any HQ business logic.

The integration must use the public C ABI exported by HQ Converter Library.

---

## 3. Responsibility Boundaries

### 3.1 ffmpeg-converter owns

- the live application queue;
- user interaction and preset selection;
- availability discovery of the bundled HQ release;
- free-space preflight;
- audio processing;
- final container assembly;
- progress and status presentation;
- per-file success or failure handling;
- cleanup after successful final assembly;
- continuation with the next queued file.

### 3.2 HQ Converter Library owns

- validation of the requested HQ Codec + Preset pair;
- creation of a unique HQ session directory;
- Segmentator execution;
- canonical HQ job and session creation;
- Encoder Orchestrator execution;
- HQ runtime progress and messages;
- stop and kill forwarding;
- creation of the final encoded video track;
- production of the Encoder Orchestrator report identifying that track.

### 3.3 Authoritative HQ components remain

```text
modules/segmentator
modules/encoder_orchestrator_v2
HQ preset system
```

Their decisions are final. Neither ffmpeg-converter nor its HQ integration layer may reinterpret them.

---

## 4. HQ Availability and Release Discovery

The `hq_converter` backend is available only when a complete HQ Converter release has been included in the ffmpeg-converter distribution and is accessible at runtime.

If no valid HQ release is available:

- `hq_converter` is not registered as an available codec;
- the HQ preset menu is not displayed;
- existing ffmpeg-converter functionality continues normally;
- the absence of HQ is not a fatal application startup error.

Availability requires at least:

- the HQ Converter shared library for the current platform;
- the public HQ Library ABI expected by ffmpeg-converter;
- the authoritative HQ preset catalog;
- HQ runtime configuration files;
- Segmentator runtime components;
- Encoder Orchestrator runtime components;
- the component binaries and shared libraries required by the HQ release.

Availability checks are limited to integration-level presence, readability, executability where applicable, and compatible library loading. ffmpeg-converter must not validate the internal correctness of HQ configuration or runtime components.

---

## 5. Build-Time HQ Release Dependency

HQ Converter is a versioned external runtime dependency.

ffmpeg-converter does not build or reconstruct HQ Converter. It consumes a release that has already been built and validated by the HQ Converter project.

The ffmpeg-converter build and packaging system must support an explicit parameter equivalent to:

```text
HQ_CONVERTER_DIR=<path-to-complete-hq-release>
```

The exact command-line syntax may follow the conventions of the active build system.

When the parameter is provided, the build or packaging process must:

1. verify that the supplied path identifies a complete HQ release tree;
2. verify the presence of the required library, preset catalog, runtime configuration and required runtime subtrees;
3. copy the HQ release into the ffmpeg-converter distribution without flattening or restructuring it;
4. record HQ availability in the ffmpeg-converter runtime configuration;
5. record the installed HQ release location relative to the ffmpeg-converter distribution where appropriate.

If the parameter is absent or the HQ release is unavailable, the normal ffmpeg-converter build may continue without HQ support, unless an explicit strict packaging option requires HQ.

The source HQ release path is a build-time input only. Runtime execution must use the copied release inside the ffmpeg-converter distribution, not the original development-tree path.

---

## 6. HQ Release Tree and Runtime Ownership

The HQ release tree is an opaque, relocatable runtime dependency owned by HQ Converter.

It must be copied as one complete subtree. The integration must not:

- split the release across unrelated directories;
- flatten its directory structure;
- rewrite HQ runtime configuration;
- replace selected HQ binaries;
- replace selected HQ shared libraries;
- substitute ffmpeg-converter binaries for HQ binaries;
- reconstruct an HQ release from individual repository files.

HQ runtime component selection is defined by the HQ release configuration, including its runtime INI files.

HQ Converter refuses execution when required configured components are unavailable. ffmpeg-converter must relay that failure and must not attempt to repair or bypass the HQ runtime configuration.

---

## 7. Independent FFmpeg Runtime Stacks

ffmpeg-converter and HQ Converter intentionally maintain independent runtime toolchains.

For example:

```text
ffmpeg-converter runtime → FFmpeg 9.x
HQ production runtime    → FFmpeg 8.x
```

The exact versions are owned by their respective projects and may change independently.

This separation is mandatory because HQ native analysis components are built and validated against the FFmpeg and libav components bundled in the HQ release.

### 7.1 ffmpeg-converter runtime

ffmpeg-converter uses its own bundled or configured components for:

- audio processing;
- input probing performed by ffmpeg-converter;
- standard ffmpeg-converter codec backends;
- final container assembly through existing ffmpeg-converter logic.

### 7.2 HQ runtime

HQ Converter Library uses the components resolved by the HQ release configuration for:

- source analysis;
- segmentation;
- HQ probing;
- segment encoding;
- HQ video-track assembly;
- HQ artifact validation.

### 7.3 No cross-substitution

ffmpeg-converter must not force HQ to use the ffmpeg-converter FFmpeg, FFprobe or libav components.

HQ must not replace the components used by normal ffmpeg-converter processing.

A fallback permitted by HQ runtime configuration may execute successfully, but only the complete bundled HQ release is the production-validated configuration. ffmpeg-converter must not rely on fallback operation as its packaging model.

---

## 8. Preset Catalog and User Selection

### 8.1 Catalog source

The HQ preset catalog is read at runtime from the authoritative preset file contained in the bundled HQ release:

```text
modules/encoder_orchestrator_v2/config/presets/encoder_presets_v2.json
```

No HQ codec or preset list may be hardcoded in ffmpeg-converter.

### 8.2 Scope of catalog reading

ffmpeg-converter reads only the information required to populate its selection model:

- HQ codec names;
- preset names belonging to each codec;
- optional display ordering or default markers already present in the catalog.

ffmpeg-converter must not:

- interpret preset parameters;
- apply preset fields;
- duplicate preset defaults;
- implement preset-specific overrides;
- validate processing semantics.

The selected Codec + Preset pair is passed unchanged to HQ Converter Library. The library performs the authoritative validation.

### 8.3 Selection model

The external codec remains:

```text
hq_converter
```

The HQ configuration identity is:

```text
HQ Codec + HQ Preset
```

Examples:

```text
x264 + youtube4k
x265 + Medium
svt-hevc + balanced_4k
svt-av1 + balanced
ffmpeg-prores + standard
ffmpeg-prores_ks + hq
```

The UI may display a combined identifier such as:

```text
x265/Medium
```

but it must retain and pass Codec and Preset as two distinct values to the library.

The ffmpeg-converter default selection is:

```text
x264 + youtube4k
```

The default is applied only when the user has not selected another available HQ pair.

## 9. HQ Library Invocation

For each input file selected for `hq_converter`, ffmpeg-converter invokes the public HQ Library C ABI.

The logical call is equivalent to:

```text
RunJob(
    InputFile,
    OutputRootDirectory,
    Codec,
    Preset
)
```

Where:

- `InputFile` is the current original source file from the queue;
- `OutputRootDirectory` is the current ffmpeg-converter output directory;
- `Codec` is the selected HQ codec;
- `Preset` is the selected preset within that codec.

The call is synchronous. It must run in the existing worker/execution context so the UI remains responsive.

The expected public operations are equivalent to:

```text
hqclib_create_handle
hqclib_run_job
hqclib_request_stop
hqclib_request_kill
hqclib_get_last_error
hqclib_destroy_handle
```

The implementation must use the actual public header shipped with the integrated HQ release. It must not redeclare an incompatible private ABI.

---

## 10. HQ Session Directory

ffmpeg-converter passes its current output directory to HQ Converter Library as the output root.

For every job, HQ Converter Library creates a separate uniquely named session directory inside that root:

```text
<OutputRootDirectory>/hq_<unique-id>/
```

The exact unique-name format is owned by HQ Converter Library.

ffmpeg-converter must not create the internal HQ session structure itself.

All HQ artifacts belong to that unique session directory, including:

- `segment_report.txt`;
- segment files;
- frame-level QP files;
- canonical job and state files;
- Encoder Orchestrator artifacts;
- runtime reports;
- encoded segment artifacts;
- the assembled HQ video track.

The short and library-controlled session name also avoids dependence on user file names for internal socket and artifact paths.

---

## 11. Free-Space Preflight

Before invoking HQ Converter Library, ffmpeg-converter must check free space on the filesystem containing the selected output root.

The minimum required free space is:

```text
input file size × 2
```

If the available space is below this threshold:

- HQ processing is not started;
- the current queue item fails with a clear diagnostic;
- the queue continues according to normal ffmpeg-converter behavior.

This check is infrastructure-only. ffmpeg-converter must not perform additional HQ artifact sizing, session validation or recovery decisions.

The system temporary directory may be supported as an explicit user choice, but it is not the default because its capacity and cleanup policy may be unsuitable for large HQ jobs.

---

## 12. Runtime Status and Progress

HQ Converter Library publishes its normative runtime payload through the public callback:

```json
{
  "job_id": "job-identifier",
  "stage": "encoding",
  "progress_percent": 62.5,
  "fps": 184.3,
  "remaining_time_sec": 97.0,
  "message": "encoding"
}
```

ffmpeg-converter must consume the payload without recalculating or reinterpreting HQ values.

### 12.1 UI mapping

| HQ field | ffmpeg-converter presentation |
|---|---|
| `stage` | current HQ stage text |
| `progress_percent` | progress bar |
| `fps` | FPS field when non-null |
| `remaining_time_sec` | remaining-time/status field when non-null |
| `message` | console/log output, preserved verbatim |

### 12.2 Public stage mapping

```text
preparing  → HQ preparing
analyzing  → HQ segmentation
encoding   → HQ encoding
completed  → HQ completed
failed     → HQ failed
cancelled  → HQ cancelled
```

ffmpeg-converter must not:

- estimate Segmentator progress;
- calculate its own HQ ETA;
- aggregate Encoder FPS again;
- replace module messages with generic text;
- parse `message` as structured state.

A separate UI-level overall pipeline indicator may compose the audio, HQ and mux phases, but it must not alter the meaning of the HQ-provided fields.

---

## 13. Cancellation and Control

The user-facing control model remains:

```text
run
cancel
```

When the current HQ job is cancelled:

```text
converter_stop()
    ↓
hqclib_request_stop(handle)
```

ffmpeg-converter must not:

- connect to Encoder Orchestrator sockets;
- terminate Encoder workers directly;
- edit HQ session state;
- implement its own HQ recovery or shutdown sequence.

HQ Library stop semantics remain authoritative:

- during Segmentator execution, stop is deferred until the Segmentator call returns, after which session creation and Encoder execution do not begin;
- during Encoder execution, stop is forwarded through the authoritative Encoder Orchestrator adapter.

`kill` may remain available internally for exceptional shutdown, but normal user cancellation uses `stop`.

A cancelled current file is handled through the existing ffmpeg-converter skip/cancel result without terminating the remaining queue unless the application itself is being closed.

---

## 14. Successful HQ Completion and Output Track

HQ success is accepted only when HQ Converter Library reports successful completion according to its contract.

The final encoded video track is created in the root of the unique HQ session directory. Its default filename is:

```text
<Preset>.<encoder-output-extension>
```

The full canonical output path is obtained from the Encoder Orchestrator report stored in the root of the HQ session directory after successful encoding and track assembly.

ffmpeg-converter may read the documented output-path field from that report only after successful library completion.

It must not:

- treat file existence as a success signal;
- scan the directory for likely output files;
- infer the result by extension;
- parse internal session state;
- select between multiple candidate artifacts;
- use partial output after failed or cancelled execution.

The Encoder Orchestrator report is the authoritative source for the completed track path.

---

## 15. Conversion Flow

For each queue item using `hq_converter`, ffmpeg-converter performs the following flow.

### 15.1 Phase A: audio processing

Use the existing ffmpeg-converter audio/mux preparation path to create an intermediate file while copying the original video track:

```text
Original input
    ↓
ffmpeg-converter audio processing
    ↓
Intermediate file
```

The original source file, not the audio intermediate, is passed to HQ Library for video encoding.

### 15.2 Phase B: HQ video encoding

```text
Original input
+ output root
+ HQ Codec
+ HQ Preset
    ↓
HQ Converter Library
    ↓
HQ encoded video track
```

### 15.3 Phase C: final container assembly

The existing ffmpeg-converter `mux` workflow consumes:

```text
HQ encoded video track
+
intermediate file containing processed/copied audio and other retained streams
```

The `mux` video behavior is copy-only:

```text
-c:v copy
```

The HQ video track must not be re-encoded or filtered by ffmpeg-converter.

### 15.4 Phase D: cleanup

After and only after successful final mux and validation:

```text
Delete the unique HQ session directory recursively.
```

Deletion is mandatory to release disk space before continued queue processing.

---

## 16. Audio Rules

Audio processing remains governed by the existing ffmpeg-converter rules.

For the HQ flow:

| `audio_norm` | `audio_output` | Final audio behavior |
|---|---|---|
| `none` | `copy` | copy all original audio tracks |
| `none` | encoded format | encode the first original audio track only |
| any processing mode | any output | process the first original audio track only |

Selecting `audio_norm=none` together with `audio_output=copy` is the only mode that preserves all original audio tracks.

All other combinations operate on the first original audio track.

This rule is an ffmpeg-converter media-policy decision and is independent of HQ video encoding.

---

## 17. Final Container Selection

The existing mux module remains authoritative for final assembly.

The HQ video track is an externally encoded video source.

The intended output model is:

| HQ video family | HQ track type | Final container |
|---|---|---|
| non-ProRes | `.ts`, `.hevc`, `.mkv` or other supported HQ track | `.mkv` |
| ProRes | `.mov` | `.mov` |

The actual HQ output path and extension come from the authoritative Encoder Orchestrator report.

ffmpeg-converter may probe the original input or use the selected HQ codec family only to choose the supported final container policy. It must not alter HQ encoding behavior.

Raw video-track handling already supported by the mux module must be reused rather than reimplemented.

---

## 18. Cleanup and Diagnostic Retention

### 18.1 Successful final output

When both conditions are true:

```text
HQ completed successfully
AND
final mux completed successfully
```

ffmpeg-converter must delete the complete HQ session directory.

Failure to delete the directory must be reported as a cleanup warning or error according to existing ffmpeg-converter policy, but must not invalidate an already validated final media file unless project policy explicitly requires strict cleanup.

### 18.2 HQ failure, mux failure or cancellation

If HQ processing fails, final mux fails, or the user cancels the job:

- the HQ session directory is retained;
- its full path is reported through the standard message/log mechanism;
- ffmpeg-converter does not attempt to repair the HQ session;
- the current queue item is marked failed or cancelled according to the existing queue contract.

Retained session directories are for diagnostics and possible external HQ inspection. Automatic resume is not part of Phase 3.

---

## 19. Queue Behavior

The ffmpeg-converter queue exists only while the application is running.

HQ integration must preserve the standard per-file queue model:

```text
File A → success, failure or cancellation
File B → success, failure or cancellation
File C → success, failure or cancellation
```

Failure of one HQ item must not terminate processing of later queue items.

After a failed item:

- report the error through existing callbacks;
- retain the failed HQ session directory;
- release the HQ Library handle and other per-file resources;
- continue with the next queue item.

No persistent HQ queue or ffmpeg-converter recovery queue is introduced.

---

## 20. Error Handling

Add or use a dedicated ffmpeg-converter error equivalent to:

```text
ERR_HQ_PIPELINE_FAILED
```

The value must be appended in a backward-compatible way if it is part of a public enum.

HQ errors are determined from:

- the synchronous HQ Library result code;
- the final HQ runtime stage;
- `hqclib_get_last_error` where applicable;
- the authoritative HQ `message` payload.

ffmpeg-converter must preserve the authoritative HQ message in diagnostics.

The following conditions fail only the current queue item:

- unavailable or incompatible HQ release after selection;
- invalid Codec + Preset pair;
- insufficient free space;
- HQ Library load failure;
- HQ processing failure;
- inability to obtain the authoritative output path after reported completion;
- final mux failure.

---

## 21. Platform Scope

Phase 3 supports:

```text
Linux
macOS
```

Native Windows integration is excluded.

HQ support must not be registered by native Windows builds. WSL operation is outside the native ffmpeg-converter integration contract.

Platform-specific loading and packaging must follow native conventions:

- Linux shared-library loading and release-relative runtime resolution;
- macOS `.dylib` loading and application-bundle resource placement.

A macOS HQ release must be built and validated on a macOS host. Linux HQ artifacts must not be repackaged as macOS support.

---

## 22. Packaging Layout

The complete HQ release is packaged next to or inside the ffmpeg-converter distribution as one subtree.

Recommended logical locations include:

```text
build/bin/hq_converter/
AppDir/usr/hq_converter/
MyApplication.app/Contents/Resources/hq_converter/
```

The exact platform path may follow existing packaging conventions, but the internal HQ release structure must remain intact.

The package must include the HQ public C header when required for SDK or development distributions. End-user distributions must include all runtime artifacts required by the integrated library.

Test binaries, mock runtimes, direct-build artifacts and source-tree paths must not be packaged.

---

## 23. Build-System Configuration State

The ffmpeg-converter runtime configuration may record:

```text
HQ available = true|false
HQ installed path = <distribution-relative path>
HQ release version = <reported marker, when available>
```

This state is deployment metadata only.

It must not duplicate:

- the preset catalog;
- HQ runtime component paths from HQ INI files;
- encoder defaults;
- Segmentator parameters;
- HQ validation rules.

At runtime, a recorded `available=true` value does not replace basic checks that the packaged release and library are still accessible.

## 24. UI and CLI Requirements

### 24.1 CLI

The CLI must support an invocation equivalent to:

```text
ffmpeg_converter -c hq_converter --preset x265/Medium input.mkv
```

If no HQ preset is specified:

```text
x264/youtube4k
```

is selected when available.

Codec and preset listing commands must include only pairs discovered from the currently packaged HQ catalog.

### 24.2 Interactive and graphical interfaces

When HQ is available:

1. display `hq_converter` as a codec option;
2. populate the HQ preset selector from the packaged catalog;
3. display the selected pair in the existing summary model;
4. relay HQ stage, progress, FPS, remaining time and messages through existing UI mechanisms;
5. use the standard start and cancel controls.

When HQ is unavailable, all HQ-specific controls are hidden or disabled consistently with existing component-gated codecs.

No UI is added for HQ parameter overrides.

---

## 25. Prohibited Implementations

Phase 3 must not introduce:

- `hq_pipeline_batch` as a second HQ integration layer;
- a separate HQ stdout protocol;
- direct UDS control-channel integration in ffmpeg-converter;
- direct Segmentator process management;
- direct Encoder Orchestrator runner management;
- C-side HQ job creation;
- C-side QP aggregation;
- C-side HDR or color injection;
- C-side session validation or repair;
- a hardcoded HQ codec or preset catalog;
- a second HQ ETA calculation;
- heuristic output-file discovery;
- automatic recovery or resume of retained HQ sessions;
- shared FFmpeg/libav substitution between ffmpeg-converter and HQ runtime stacks.

## 26. Validation Matrix

Phase 3 validation must include at least:

### 26.1 Availability and packaging

- build with no HQ release;
- build with a valid HQ release;
- invalid or incomplete `HQ_CONVERTER_DIR`;
- copied release works without the original source-tree path;
- packaged HQ subtree remains complete;
- runtime configuration records correct availability;
- HQ codec is absent when unavailable.

### 26.2 Presets

- runtime catalog loading;
- Codec validation;
- Preset validation;
- Codec + Preset pair validation;
- default `x264/youtube4k` selection;
- menu refresh from catalog without hardcoded entries.

### 26.3 Runtime behavior

- successful real-media HQ encode;
- progress bar updates;
- FPS display;
- remaining-time display;
- verbatim HQ messages;
- completed output path read from the Encoder Orchestrator report;
- output passed to the existing mux module;
- final media validation.

### 26.4 Queue behavior

- multiple input files;
- one HQ failure followed by successful processing of the next file;
- cancellation of one file followed by continued queue operation;
- per-file handle and resource cleanup.

### 26.5 Disk and directory behavior

- insufficient free-space rejection;
- unique HQ session directory creation inside the selected output root;
- mandatory deletion after successful final mux;
- retention after HQ failure;
- retention after mux failure;
- retention after cancellation;
- diagnostic reporting of retained directory paths.

### 26.6 Media policy

- all-audio copy for `audio_norm=none + audio_output=copy`;
- first-track-only behavior for encoded or processed audio;
- non-ProRes HQ track assembled into MKV;
- ProRes HQ track assembled into MOV;
- HQ video copied without re-encoding.

### 26.7 Runtime isolation

- ffmpeg-converter uses its own configured FFmpeg runtime;
- HQ uses components from its own release configuration;
- HQ does not accidentally resolve ffmpeg-converter FFmpeg/libav components;
- the integrated HQ release fails cleanly if its required configured components are removed;
- no development-machine absolute paths remain in the packaged product.

### 26.8 Platform validation

- Linux release integration;
- macOS release integration on a macOS host;
- GUI and CLI behavior on supported platforms;
- native Windows builds remain unaffected and do not expose HQ.

## 27. Completion Criteria

Phase 3 is complete when:

1. `hq_converter` is registered only when a packaged HQ release is available.
2. The preset UI is built dynamically from the packaged HQ preset catalog.
3. Codec and Preset are passed unchanged to HQ Converter Library.
4. HQ Converter Library is the sole HQ integration boundary.
5. No HQ business logic is duplicated in ffmpeg-converter.
6. The current output directory is passed as the HQ output root.
7. HQ Library creates a unique per-file session directory inside that root.
8. Free space of at least two times the input size is checked before HQ execution.
9. HQ progress, FPS, remaining time and messages are relayed through existing callbacks.
10. User cancellation is forwarded through `hqclib_request_stop`.
11. The final HQ video-track path is read from the authoritative Encoder Orchestrator report after successful completion.
12. The existing mux module assembles the final file without re-encoding HQ video.
13. Audio behavior follows the Phase 3 audio rules.
14. The HQ session directory is deleted after successful final mux.
15. The HQ session directory is retained and reported after failure or cancellation.
16. A failed queue item does not stop later items.
17. ffmpeg-converter and HQ use independent runtime toolchains.
18. The complete HQ release is copied from an explicit build-time path and packaged intact.
19. Runtime configuration records HQ availability without duplicating HQ internal configuration.
20. Linux and macOS integrations pass real-media validation.

## 28. Governing Invariants

```text
HQ Converter Library is the sole integration boundary.

HQ authoritative modules make HQ processing decisions.

ffmpeg-converter owns queueing, audio processing,
final muxing, presentation and successful-session cleanup.

Codec + Preset is the HQ processing identity.

Preset names are discovered dynamically,
but preset semantics remain owned by HQ.

HQ and ffmpeg-converter use independent runtime toolchains.

The packaged HQ release is consumed intact.

HQ progress and messages are transported, not recalculated.

The completed HQ track is copied into the final container,
not encoded again.

A successful final mux requires deletion of the HQ session directory.

A failed or cancelled file does not terminate the live queue.

Business logic is never duplicated across the project boundary.
```
