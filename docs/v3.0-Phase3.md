# Version 3.0 — Phase 3: HQ Converter Integration via HQ Library

**Status:** Final Technical Specification  
**Integration boundary:** HQ Converter Library public C ABI  
**Supported platforms:** Linux and macOS  
**Excluded platform:** Native Windows; WSL is outside the native ffmpeg-converter integration scope

---

## 1. Goal

Integrate HQ Converter into ffmpeg-converter as a first-class high-quality video encoding backend:

```text
hq_converter
```

HQ Converter Library is the sole supported boundary between ffmpeg-converter and HQ Converter.

The processing flow is:

```text
Input file
    ↓
ffmpeg-converter audio processing
    ↓
HQ Converter Library video processing
    ↓
ffmpeg-converter final mux
    ↓
Final media file
```

The user selects only:

```text
ffmpeg-converter codec: hq_converter
HQ codec identifier
HQ preset identifier
```

No HQ processing parameters or overrides are exposed by ffmpeg-converter.

Phase 3 depends on the codec-to-preset model and dynamic preset menus introduced in Phase 1. Phase 2 remains orthogonal.

---

## 2. Governing Integration Contract

HQ Converter Library is a strict black-box integration boundary.

```text
ffmpeg-converter
        ↓
HQ Converter Library public contract
        ↓
HQ Converter internal implementation
```

ffmpeg-converter interacts exclusively through the documented public HQ Converter Library contract.

Any HQ behavior, state, artifact, process, directory structure, runtime component or protocol not explicitly exposed by the public library contract is an implementation detail.

The public library contract is the only permitted integration path.

If an operation cannot be completed through that contract, the current HQ operation fails. ffmpeg-converter must not bypass, extend, supplement or replace the contract.

---

## 3. Prohibited Direct Integration

ffmpeg-converter must not directly:

- invoke Segmentator;
- invoke Encoder Orchestrator v2;
- connect to Encoder Orchestrator control sockets;
- start or manage internal HQ runners;
- create or edit HQ jobs or sessions;
- interpret HQ session status;
- inspect completion records or checksums;
- validate HQ artifacts;
- reconstruct HQ execution queues;
- aggregate QP data;
- implement HDR or color-injection logic;
- interpret HQ preset contents;
- implement HQ recovery or resume logic;
- calculate HQ progress, FPS or ETA;
- infer HQ success from files, reports or internal states;
- duplicate HQ business logic.

Phase 3 must not introduce a second HQ integration layer, a batch controller or a private protocol around HQ internals.

---

## 4. Responsibility Boundaries

### 4.1 ffmpeg-converter owns

- the live application queue;
- user interaction;
- discovery of the packaged HQ release;
- selection and storage of opaque HQ identifiers;
- free-space preflight;
- audio processing;
- final container assembly;
- progress and status presentation;
- per-file success, failure and cancellation handling;
- post-call retention or deletion of the complete HQ working directory;
- continuation with the next queued file.

### 4.2 HQ Converter Library public contract owns

- validation of the supplied HQ codec and preset identifiers;
- execution of the complete HQ processing operation;
- publication of runtime status;
- handling of stop and kill requests according to its documented behavior;
- confirmed successful completion;
- production of the completed encoded video track;
- publication of the information required to locate the confirmed output through the documented HQ session contract.

### 4.3 HQ internal implementation

The structure and behavior behind HQ Converter Library remain private to HQ Converter.

ffmpeg-converter must not depend on which internal HQ component:

- creates the working directory;
- creates or names artifacts;
- performs segmentation;
- creates jobs or sessions;
- starts or controls Encoder Orchestrator;
- validates the assembled video track;
- confirms `Done`;
- releases internal sockets.

## 5. Selection Model and Terminology

The user-facing selection has three presentation levels:

```text
Level 1: ffmpeg-converter codec
         hq_converter

Level 2: HQ codec identifier
         example: x265

Level 3: HQ preset identifier
         example: Medium
```

The first level selects the HQ backend inside ffmpeg-converter.

The second and third levels are opaque exact identifiers passed to HQ Converter Library.

The HQ processing identity supplied to the library is:

```text
HQ codec identifier + HQ preset identifier
```

Examples:

```text
x264 + youtube4k
x265 + Medium
svt-hevc + balanced_4k
svt-av1 + balanced
ffmpeg-prores + standard
ffmpeg-prores_ks + hq
```

The UI or CLI may display a combined form such as:

```text
x265/Medium
```

Internally, ffmpeg-converter must preserve the two exact values separately.

ffmpeg-converter may organize or display the catalog in any appropriate manner, but it must not:

- rename identifiers;
- normalize identifier case;
- translate identifiers;
- derive one identifier from the other;
- infer aliases;
- correct unknown identifiers;
- substitute a fallback pair after rejection.

The values passed to the library must exactly match names present in the packaged HQ preset catalog.

If the pair is not accepted, the library's normative error, including `codec/preset not found`, is final for the current item.

---

## 6. HQ Preset Catalog

The HQ preset catalog is read at runtime from the authoritative preset file in the packaged HQ release:

```text
modules/encoder_orchestrator_v2/config/presets/encoder_presets_v2.json
```

No HQ codec or preset list may be hardcoded in ffmpeg-converter.

ffmpeg-converter reads only the names required for:

- CLI and GUI population;
- selection storage;
- codec and preset listing;
- passing the exact selected pair to HQ Converter Library.

ffmpeg-converter must not:

- interpret preset parameters;
- apply preset fields;
- duplicate preset defaults or overrides;
- validate processing semantics;
- implement another preset engine.

HQ Converter Library remains the final authority for pair validation.

The ffmpeg-converter default pair is:

```text
x264 + youtube4k
```

The default is applied only when that exact pair exists in the packaged catalog and the user has not selected another pair.

---

## 7. HQ Availability

The `hq_converter` backend is available only when a usable HQ runtime package has been included in the ffmpeg-converter distribution and is accessible at runtime.

If HQ is unavailable:

- `hq_converter` is not registered as an available codec;
- HQ selectors are hidden or disabled;
- existing ffmpeg-converter functionality remains available;
- application startup does not fail solely because HQ is absent.

Integration-level availability checks may include:

- presence and readability of the HQ shared library;
- compatibility with the expected public C ABI;
- presence and readability of the preset catalog;
- presence of the packaged HQ runtime subtree;
- successful loading of the shared library.

ffmpeg-converter must not validate HQ internal runtime configuration or component compatibility.

If HQ later rejects execution because an internal component is missing or incompatible, ffmpeg-converter relays the library failure and does not attempt repair.

---

## 8. Build-Time HQ Runtime Input

HQ Converter is a versioned external runtime dependency.

ffmpeg-converter does not build or reconstruct HQ processing components from source. It consumes a runtime package produced from an HQ Converter release.

The build or packaging system must support an explicit input equivalent to:

```text
HQ_CONVERTER_DIR=<path-to-hq-release-or-runtime-tree>
```

The exact option syntax may follow the active build system.

When supplied, the build or packaging process must:

1. verify the required public library, public header, preset catalog, runtime configuration and runtime components;
2. copy the accepted HQ runtime tree into the ffmpeg-converter distribution;
3. preserve the relative structure required by HQ runtime configuration;
4. record HQ availability in ffmpeg-converter deployment metadata;
5. record the installed, distribution-relative HQ runtime path where required;
6. avoid retaining development-machine absolute paths.

The original source path is a build-time input only.

At runtime, ffmpeg-converter uses the packaged HQ runtime inside its own distribution, not the original development-tree location.

If the option is absent, the normal build may continue without HQ support unless a strict packaging mode explicitly requires HQ.

---

## 9. Full Release and Reduced Runtime Packaging

The initial implementation may copy the complete validated HQ release tree.

A later packaging optimization may produce a reduced HQ runtime containing only components required by HQ Converter Library when embedded in ffmpeg-converter.

A reduced runtime is permitted only when:

- it is generated by the build or packaging system from a validated HQ release;
- every component required by the library remains present;
- required relative paths remain valid or are updated consistently in the packaged HQ runtime configuration;
- the public HQ Library contract remains unchanged;
- real-media regression validation passes with the reduced runtime;
- no ffmpeg-converter component is substituted for an HQ component.

The build system may patch copied HQ runtime INI files to reflect the final packaged layout.

Such patching is deployment configuration, not HQ business logic.

The source HQ release must not be modified in place. Only the copied ffmpeg-converter package may be adjusted.

---

## 10. Embedded HQ Project Root

HQ code that derives its runtime root from its host executable cannot rely on the HQ executable path when loaded as a shared library inside ffmpeg-converter.

The packaged integration may therefore use an explicit runtime-root override such as:

```text
HQ_PROJECT_ROOT=<packaged-hq-runtime-root>
```

The build may apply the corresponding HQ-side compatibility patch required for shared-library hosting.

Requirements:

- the override must point to the packaged HQ runtime inside the ffmpeg-converter distribution;
- ffmpeg-converter must set it only for the HQ library invocation scope or restore the previous environment afterward;
- the value must not reference the original build tree;
- the override changes only runtime-root discovery;
- it must not change HQ processing, validation, preset or recovery behavior.

Where possible, this support should be incorporated into the canonical HQ release rather than maintained indefinitely as an external patch.

---

## 11. Independent Runtime Toolchains

ffmpeg-converter and HQ Converter intentionally use independent runtime toolchains.

For example:

```text
ffmpeg-converter runtime → FFmpeg 9.x
HQ production runtime    → FFmpeg 8.x
```

Exact versions are owned independently by the two projects.

This separation is required because HQ native analysis components are built and validated against the FFmpeg and libav components supplied by the HQ runtime.

### 11.1 ffmpeg-converter runtime

ffmpeg-converter uses its own runtime for:

- audio processing;
- normal input probing;
- standard codec backends;
- final mux and output validation.

### 11.2 HQ runtime

HQ processing uses components resolved by the packaged HQ runtime configuration.

ffmpeg-converter must not force HQ to use ffmpeg-converter's FFmpeg, FFprobe, encoder or libav components.

HQ must not replace the components used by normal ffmpeg-converter processing.

A fallback permitted by HQ runtime configuration may operate, but the packaged HQ runtime is the production-validated integration configuration. ffmpeg-converter must not depend on fallback operation as its normal distribution model.

## 12. Public Library Invocation

For each queue item using `hq_converter`, ffmpeg-converter invokes the public HQ Converter Library C ABI shipped with the packaged runtime.

The logical operation is equivalent to:

```text
RunJob(
    InputFile,
    WorkDirectory,
    HQCodecIdentifier,
    HQPresetIdentifier
)
```

Where:

- `InputFile` is the original current source file;
- `WorkDirectory` is the unique per-item HQ working path selected by ffmpeg-converter under the current output root;
- `HQCodecIdentifier` is the exact selected HQ codec name;
- `HQPresetIdentifier` is the exact selected HQ preset name.

The call is synchronous and must run in the existing worker context so the UI remains responsive.

The integration must use the actual public header shipped with the HQ runtime.

The expected operations are equivalent to:

```text
hqclib_create_handle
hqclib_run_job
hqclib_request_stop
hqclib_request_kill
hqclib_get_last_error
hqclib_destroy_handle
```

The implementation must not redeclare, reinterpret or privately extend the ABI.

---

## 13. Working Directory Contract

ffmpeg-converter creates a unique per-item working-path name under the selected output root and passes that exact path to HQ Converter Library.

HQ Converter Library determines the name according to its internal naming algorithm or through a dedicated integration helper if exposed. ffmpeg-converter must use that returned or supplied name unchanged.

The working directory itself is created by the HQ processing implementation. In the current implementation, creation occurs inside the authoritative Segmentator path.

ffmpeg-converter must not create the directory in advance.

It must not:

- populate HQ files or subdirectories;
- assume which internal component creates the directory;
- modify individual HQ artifacts;
- interpret directory contents while HQ is running.

The working path must be known to ffmpeg-converter because it is required for:

- free-space filesystem selection;
- completed-output discovery after library success;
- retention after failure or cancellation;
- complete recursive deletion after successful final mux.

If the public library ABI does not expose a separate work-path generator, ffmpeg-converter may generate a collision-resistant unique path under the output root according to the integration naming policy, but must not create it before calling the library.

The implementation must verify the actual ABI and existing library behavior before choosing either mechanism.

---

## 14. Working Directory Lifecycle

HQ Converter Library does not own the external lifecycle of the working directory.

After the library call, ffmpeg-converter applies only the following whole-directory policy:

```text
HQ success + final mux success
    → recursively delete the complete working directory

HQ failure, cancellation or final mux failure
    → retain the complete working directory
```

ffmpeg-converter must never selectively delete, repair or edit individual HQ artifacts.

The retained path is reported through the normal message or log mechanism.

Automatic resume of retained work is outside Phase 3.

---

## 15. Free-Space Preflight

Before invoking HQ Converter Library, ffmpeg-converter checks free space on the filesystem containing the selected working path.

The minimum required free space is:

```text
input file size × 2
```

If free space is below the threshold:

- HQ processing is not started;
- the current queue item fails with a clear diagnostic;
- the queue continues normally.

This is the only pre-execution HQ storage check required from ffmpeg-converter.

ffmpeg-converter must not estimate individual HQ artifact sizes or inspect prior HQ state.

The system temporary directory may be supported as an explicit user choice, but it is not the default because its capacity and cleanup behavior may be unsuitable for large HQ workloads.

---

## 16. Runtime Status

HQ Converter Library publishes its normative runtime payload through its public callback:

```json
{
  "job_id": "job-identifier",
  "stage": "encoding",
  "progress_percent": 62.5,
  "fps": 184.3,
  "remaining_time_sec": 97.0,
  "message": "encoding"
}
```

ffmpeg-converter relays these values through its existing callback infrastructure.

| Library field | ffmpeg-converter use |
|---|---|
| `stage` | status or stage text |
| `progress_percent` | progress bar |
| `fps` | FPS field when non-null |
| `remaining_time_sec` | remaining-time field when non-null |
| `message` | console or message log, preserved verbatim |

Display mapping may be:

```text
preparing  → HQ preparing
analyzing  → HQ segmentation
encoding   → HQ encoding
completed  → HQ completed
failed     → HQ failed
cancelled  → HQ cancelled
```

ffmpeg-converter must not:

- recalculate HQ progress;
- estimate Segmentator progress;
- calculate another HQ ETA;
- aggregate Encoder FPS again;
- replace HQ messages with generic text;
- parse `message` as structured state;
- interpret internal HQ states.

A UI may compose audio, HQ and mux phases for presentation, but must not alter the semantics of values supplied by the library.

---

## 17. HQ Completion Contract

HQ Converter Library is the sole authority visible to ffmpeg-converter for the result of HQ processing.

HQ processing is successful only when:

```text
hqclib_run_job returns the documented success result
```

The library success result already represents the internally confirmed HQ result.

Inside HQ, Encoder Orchestrator reaches `Done` only after the assembled video track has been created and successfully validated. That internal confirmation must not be repeated by ffmpeg-converter.

ffmpeg-converter must not supplement library success with independent checks of:

- Encoder Orchestrator status;
- control sockets;
- session status;
- task or completion records;
- checksums;
- encoded segments;
- output validity;
- the existence of likely output files.

All other HQ internal states are irrelevant to ffmpeg-converter behavior. They may contribute to the authoritative user-facing message, but ffmpeg-converter must not interpret them.

The only external result categories are those documented by the library, including:

```text
success
failure
cancellation
```

If the library returns failure or cancellation, ffmpeg-converter must not use any partial or apparently complete HQ output, even when files exist.

---

## 18. Completed Output Discovery

After and only after the library returns success, ffmpeg-converter obtains the confirmed output-track path through the documented HQ session-file contract.

The current HQ implementation stores the requested or completed output path in the canonical HQ session data. The Encoder Orchestrator report does not contain that path and must not be used as its source.

ffmpeg-converter may read only the documented output-path field required for final mux.

Reading the session data is output discovery, not success validation.

ffmpeg-converter must not:

- infer success from the session file;
- use session data after failure or cancellation;
- inspect unrelated internal session fields;
- reconstruct HQ state;
- scan the directory for likely outputs;
- infer the output by extension alone;
- select among multiple candidate artifacts.

If the library returns success but the output path cannot be obtained from the documented session field, the current queue item fails safely and no HQ artifact is used.

If the session path is relative, it is resolved against the documented HQ working-directory base. It must not be resolved against the process current directory or the original build tree.

---

## 19. Cancellation and Control

The user-facing control model remains:

```text
run
cancel
```

Cancellation is forwarded through the library contract:

```text
converter_stop()
    ↓
hqclib_request_stop(handle)
```

ffmpeg-converter must not:

- connect to Encoder Orchestrator sockets;
- terminate internal HQ workers directly;
- edit HQ state;
- implement an independent HQ shutdown sequence.

The library's stop semantics are final.

`kill` may be used only for exceptional application shutdown or another behavior explicitly permitted by the public contract. Normal user cancellation uses `stop`.

Cancellation of the current file must not terminate later queue items unless the application-wide queue operation itself is being stopped.

---

## 20. Conversion Flow

For each queue item using `hq_converter`, ffmpeg-converter performs the following phases.

### 20.1 Audio preparation

Use the existing ffmpeg-converter audio path to create an intermediate file while preserving the source video needed by the existing mux workflow.

```text
Original input
    ↓
ffmpeg-converter audio processing
    ↓
Intermediate file
```

HQ Converter Library always receives the original source file, not the audio intermediate.

### 20.2 HQ video processing

```text
Original input
+ unique working path
+ exact HQ codec identifier
+ exact HQ preset identifier
    ↓
HQ Converter Library
    ↓
synchronous success, failure or cancellation
```

### 20.3 Output discovery

After library success:

```text
read the confirmed output path from the documented HQ session field
```

### 20.4 Final mux

The existing ffmpeg-converter mux workflow consumes:

```text
confirmed HQ video track
+
intermediate file containing processed or copied audio
and other retained streams
```

The HQ video track is copied without re-encoding:

```text
-c:v copy
```

### 20.5 Cleanup

After successful final mux and existing ffmpeg-converter output validation:

```text
recursively delete the complete HQ working directory
```

Deletion is mandatory to release space for later queue items.

---

## 21. Audio Rules

Audio processing remains an ffmpeg-converter responsibility.

| `audio_norm` | `audio_output` | Final audio behavior |
|---|---|---|
| `none` | `copy` | copy all original audio tracks |
| `none` | encoded format | encode the first original audio track only |
| any processing mode | any output | process the first original audio track only |

Only `audio_norm=none` together with `audio_output=copy` preserves all original audio tracks.

All other combinations use the first original audio track.

These rules do not affect HQ video processing.

---

## 22. Final Container Assembly

The existing ffmpeg-converter mux module remains authoritative for final assembly.

The intended policy is:

| HQ video family | HQ track type | Final container |
|---|---|---|
| non-ProRes | supported HQ track such as `.ts`, `.hevc` or `.mkv` | `.mkv` |
| ProRes | `.mov` | `.mov` |

The actual HQ track path and extension come from the documented completed-output contract.

ffmpeg-converter may use its existing input probe or the selected HQ identifier only to choose a supported final-container policy. It must not modify HQ encoding behavior.

Existing raw-track handling in the mux module must be reused rather than reimplemented.

---

## 23. Queue Behavior

The ffmpeg-converter queue exists only while the application is running.

The HQ backend follows the standard per-file model:

```text
File A → success, failure or cancellation
File B → success, failure or cancellation
File C → success, failure or cancellation
```

A failed or cancelled HQ item must not terminate later queue items.

After each item, ffmpeg-converter releases:

- the HQ Library handle;
- the callback context;
- per-file integration resources;
- dynamically loaded library references according to the selected lifetime model.

No persistent HQ queue, automatic recovery queue or automatic retry system is introduced.

---

## 24. Error Handling

Add or use a dedicated error equivalent to:

```text
ERR_HQ_PIPELINE_FAILED
```

If part of a public enum, it must be appended without renumbering existing values.

HQ errors are determined only through the public library contract, including:

- the synchronous result code;
- the public final stage where applicable;
- `hqclib_get_last_error`;
- the authoritative `message` payload.

The authoritative message must be preserved.

The following conditions fail only the current queue item:

- HQ unavailable after selection;
- shared-library load or ABI incompatibility;
- invalid HQ codec/preset identifiers;
- insufficient free space;
- library processing failure;
- library cancellation;
- inability to obtain the documented output path after library success;
- final mux or final-output validation failure.

## 25. Platform Scope

Phase 3 supports:

```text
Linux
macOS
```

Native Windows integration is excluded.

HQ must not be registered by native Windows builds. WSL is outside the native ffmpeg-converter contract.

Platform-specific loading and packaging must use native conventions:

- Linux shared-library loading and release-relative runtime paths;
- macOS `.dylib` loading and application-bundle resource placement.

A macOS HQ runtime must be built and validated on a macOS host. Linux artifacts must not be presented as macOS support.

## 26. Packaging Layout

The HQ runtime is packaged as one coherent subtree inside or next to the ffmpeg-converter distribution.

Recommended logical locations include:

```text
build/bin/hq_converter/
AppDir/usr/hq_converter/
MyApplication.app/Contents/Resources/hq_converter/
```

The exact platform location may follow existing packaging conventions.

The relative structure required by HQ runtime configuration must remain valid.

End-user packages must include every runtime artifact required by HQ Converter Library. Development or SDK packages may also include the public C header.

Test binaries, mocks, direct-build outputs and development-machine paths must not be packaged.

## 28. CLI and UI Requirements

### 28.1 CLI

The CLI supports an invocation equivalent to:

```text
ffmpeg_converter -c hq_converter --preset x265/Medium input.mkv
```

The combined representation is split only into the exact pair:

```text
HQ codec identifier = x265
HQ preset identifier = Medium
```

An explicit form may also be supported:

```text
ffmpeg_converter -c hq_converter --encoder x265 --preset Medium input.mkv
```

If no pair is specified, `x264/youtube4k` is used only when present in the packaged catalog.

Listing commands display only identifiers discovered from the current catalog.

### 28.2 Interactive and graphical interfaces

When HQ is available, interfaces must:

1. display `hq_converter` as an ffmpeg-converter codec;
2. populate HQ selections from the packaged catalog;
3. preserve exact identifiers separately from localized or formatted labels;
4. display the selected pair in summaries;
5. relay HQ stage, progress, FPS, remaining time and messages through existing UI mechanisms;
6. use the existing start and cancel controls.

When HQ is unavailable, HQ-specific choices are hidden or disabled consistently with other component-gated backends.

No HQ parameter override controls are introduced.

---

## 29. ABI Adapter Requirements

The ffmpeg-converter HQ adapter must mirror the shipped HQ public header exactly.

It must verify and use the actual signatures for:

- handle creation and destruction;
- callback pointer, byte length and user context;
- run, stop and kill functions;
- last-error retrieval;
- fixed-width length and result types.

The adapter must:

- copy callback payloads using the supplied byte length;
- not assume NUL termination unless stated by the header;
- preserve UTF-8;
- prevent callback buffer retention beyond its documented lifetime;
- protect active-handle access used by cancellation;
- restore temporary environment changes after invocation;
- fail safely when required symbols are absent.

The adapter must not reproduce HQ processing logic.

- a private stdout protocol;
- direct UDS integration;

- identifier normalization or aliasing;
- a second HQ progress, FPS or ETA algorithm;
- heuristic output-file discovery;
- inference of HQ success from session files, reports or output files;
- automatic recovery or resume of retained HQ sessions;
- component substitution between HQ and ffmpeg-converter runtimes;
- dependence on undocumented HQ internals.

## 31. Validation Matrix

### 31.1 Availability and packaging

- build without HQ runtime;
- build with a complete HQ release;
- build with an approved reduced HQ runtime;
- invalid or incomplete `HQ_CONVERTER_DIR`;
- packaged runtime works after the source path is removed;
- deployment metadata records correct availability;
- HQ backend is absent when unavailable;
- no development-machine paths remain.

### 31.2 Identifier handling

- runtime catalog loading;
- exact codec spelling and case preservation;
- exact preset spelling and case preservation;
- valid pair acceptance;
- invalid codec rejection by the library;
- invalid preset rejection by the library;
- invalid pair rejection by the library;
- default pair only when present;
- no hardcoded identifier list.

### 31.3 ABI contract

- shared-library loading;
- all required symbols resolved;
- real signature compatibility;
- callback byte-length handling;
- UTF-8 messages;
- null callback behavior if supported;
- last-error retrieval;
- active-handle stop forwarding;
- environment save and restore;
- missing symbol failure.

### 31.4 Completion semantics

- success accepted only from the documented run result;
- failure never overridden by files or session data;
- cancellation never overridden by partial output;
- no Encoder status or socket inspection;
- output discovery performed only after success.

### 31.5 Runtime presentation

- stage display;
- progress-bar updates;
- FPS display when non-null;
- remaining-time display when non-null;
- null FPS and ETA handling;
- verbatim messages.

### 31.6 Output discovery and mux

- canonical session output field read after success;
- relative output path resolved against the documented HQ working directory;
- no report-path assumption;
- no directory scanning or extension guessing;
- video passed to the existing mux module;
- video copied without re-encoding;
- final media validated by existing ffmpeg-converter logic.

### 31.7 Working-directory behavior

- collision-resistant unique work path;
- ffmpeg-converter does not pre-create the HQ directory;
- HQ runtime creates and fills it;
- success plus final mux deletes the complete directory;
- HQ failure retains it;
- mux failure retains it;
- cancellation retains it;
- retained path is reported;
- no selective artifact deletion.

### 31.8 Queue behavior

- multiple files;
- one HQ failure followed by the next item;
- one cancellation followed by the next item;
- per-file handle and callback cleanup;
- no automatic recovery or retry.

### 31.9 Storage and media policy

- rejection below `2 × input size` free-space threshold;
- all-audio copy for `audio_norm=none + audio_output=copy`;
- first-audio-track behavior in all other modes;
- non-ProRes final MKV policy;
- ProRes final MOV policy.

### 31.10 Runtime isolation

- ffmpeg-converter uses its own runtime components;
- HQ uses its packaged runtime configuration;
- `HQ_PROJECT_ROOT` points to the packaged runtime when required;
- environment is restored after the HQ call;

- missing HQ components produce a library failure.

### 31.11 Platforms

## 32. Completion Criteria

Phase 3 is complete when:

1. HQ Converter Library is the sole HQ integration boundary.
2. `hq_converter` is registered only when a packaged HQ runtime is available.
3. HQ identifiers are discovered dynamically from the packaged catalog.
4. Exact selected codec and preset strings are passed unchanged to the library.
5. No HQ business logic or internal state interpretation exists in ffmpeg-converter.
6. A unique per-item working path is supplied without pre-creating the HQ directory.
7. Free space of at least two times the input size is checked before invocation.
8. Runtime callback values are relayed without recalculation.
9. Normal cancellation is forwarded through the public stop function.
10. HQ success is accepted only from the documented library result.
11. No additional HQ success validation is performed.
12. The output path is read only after success from the documented HQ session field.
13. The existing mux module assembles the final file without video re-encoding.
14. Existing audio rules are preserved.
15. The complete HQ working directory is deleted after successful final mux.
16. The directory is retained and reported after failure or cancellation.
17. One failed or cancelled item does not stop later queue items.
18. ffmpeg-converter and HQ retain independent runtime toolchains.
19. A complete or approved reduced HQ runtime is copied from an explicit build-time path.
20. Embedded shared-library root discovery works through the packaged runtime path.
21. Linux and macOS pass real-media integration validation.

## 33. Governing Invariants

```text
HQ Converter Library is a black box for ffmpeg-converter.

The public HQ Library contract is the only integration path.

Anything not exposed by that contract is an implementation detail.

ffmpeg-converter never interprets HQ internal state.

HQ success is the documented success result from hqclib_run_job.

Internally confirmed Done is already represented by library success.

Session data and files never override a failure or cancellation result.

The session output field is used only to locate a confirmed track after success.

HQ codec and preset names are opaque exact identifiers.

HQ and ffmpeg-converter use independent runtime toolchains.

The packaged HQ runtime remains internally coherent.

HQ callback values are transported, not recalculated.

The completed HQ track is copied into the final container, not encoded again.

ffmpeg-converter owns post-call whole-directory retention or deletion,
but never individual HQ artifacts.

A successful final mux requires deletion of the complete HQ working directory.

A failed or cancelled file does not terminate the live queue.

Business logic is never duplicated across the project boundary.
```
