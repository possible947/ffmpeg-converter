# Version 3.0 - Phase 3: HQ Converter Integration

**Status:** Revised Technical Specification — Phase 3A+B (Audio Orchestrator) complete
**Supported platforms:** Linux and macOS
**Excluded platform:** Native Windows

### Phase 3A+B: Audio Orchestrator extraction — DONE (2026-10-10)

The audio subsystem has been extracted from `converter.c` into
`src/audio/audio_orchestrator.c` and `src/audio/audio_orchestrator.h`.
All existing behavior preserved: 40/40 mode × normalization × genre
combinations verified. `build_ffmpeg_cmd()` remains the sole FFmpeg
command builder. See CHANGELOG.md entry for details.

## 1. Purpose

Integrate the existing HQ Converter Library into the existing ffmpeg-converter product as a new video encoding backend named `hq_converter`.

The architectural model is:

```text
hq_converter = automatic Add Track video source
```

HQ Converter Library produces a prepared external video track. After that track path is obtained, HQ-specific processing ends. The track is passed to the exact existing ffmpeg-converter Add Track processing path, which remains responsible for audio processing, subtitle and chapter handling, metadata and attachment handling, container assembly, and final muxing.

Phase 3 is integration work. It must not create a parallel media-processing architecture.

## 2. Existing Components

The following components already exist and are considered complete and authoritative:

- HQ Converter Library;
- HQ runtime;
- HQ preset catalog;
- ffmpeg-converter manual Add Track workflow;
- ffmpeg-converter audio-processing workflow;
- ffmpeg-converter Mux workflow;
- subtitle, chapter, attachment, tag, and metadata handling;
- container assembly;
- output-path and output-naming logic;
- queue processing;
- Stop policy;
- availability masking;
- packaging infrastructure.

Phase 3 integrates these components. It does not replace or reimplement them.

## 3. Non-Negotiable Architecture Contract

The rules in this section take precedence over all implementation suggestions and local optimizations. A violation of any rule in this section makes the implementation non-compliant with Phase 3, even if the produced output appears correct in some tests.

### 3.1 HQ Converter Produces Only an External Video Track

The only media-processing responsibility added by the HQ integration is producing an external video track path.

The HQ-specific path is:

```text
HQ Library
    -> successful HQ result
    -> canonical HQ session file
    -> artifacts.outputs.video_track.path
```

After `video_track.path` has been obtained, HQ-specific media processing must end.

### 3.2 Mandatory Convergence with Manual Add Track

The two supported paths are:

```text
Manual Add Track
    -> user-selected external video track path
    -> existing Add Track processing entry point
```

```text
HQ Converter
    -> HQ Library
    -> external video track path from canonical session file
    -> the same existing Add Track processing entry point
```

Both paths must converge before any of the following operations occur:

- audio-track selection;
- audio copy or encoding;
- audio-filter application;
- subtitle handling;
- chapter handling;
- attachment handling;
- global-tag or track-tag handling;
- metadata handling;
- container selection and assembly;
- mux command construction;
- final output-path selection;
- final output naming.

The implementation reviewer must be able to identify one exact existing Add Track processing function that receives the external video track path from both flows.

### 3.3 No HQ-Specific Audio Engine

The implementation must not:

- create a new audio engine;
- create an HQ-specific audio-processing path;
- duplicate existing audio processing;
- reproduce equivalent audio behavior in separate code;
- construct HQ-specific commands for PCM, AAC, AC3, audio copy, filtering, or track selection.

All HQ jobs must use the existing ffmpeg-converter audio implementation through the existing Add Track processing path.

### 3.4 No HQ-Specific Mux Engine

The implementation must not:

- create a new mux engine;
- create an HQ-specific mux branch that assembles the final file;
- construct a separate HQ mux command line;
- duplicate existing container, subtitle, chapter, attachment, metadata, tag, or track-handling logic;
- implement behavior that is merely similar to the existing Mux workflow.

The exact existing Mux workflow must be used.

### 3.5 One Runtime HQ Catalog Provider

The HQ preset catalog is the only source of HQ codec and preset identifiers.

One shared runtime catalog provider must load that catalog and serve both CLI and GUI.

The implementation must not:

- hard-code HQ codecs or presets in ffmpeg-converter;
- copy HQ identifiers into `presets.json.in`;
- generate a separate GUI catalog at build time;
- maintain separate CLI and GUI HQ catalogs;
- require rebuilding ffmpeg-converter when only the HQ catalog changes.

After an HQ codec or preset is added to the packaged HQ catalog, restarting ffmpeg-converter must be sufficient for the new identifier to appear in both CLI and GUI.

### 3.6 Working-Directory Ownership

ffmpeg-converter owns the complete lifecycle of the queue-item working directory.

For queue item `N`, the working directory is:

```text
<OutputDirectory>/task_N
```

ffmpeg-converter must:

1. construct the exact `task_N` path;
2. create the directory;
3. validate read and write access;
4. validate required free space;
5. pass that exact directory to HQ Converter Library as `work_dir`;
6. use HQ artifacts from that directory only after documented library success;
7. keep the directory until final Add Track and Mux processing no longer needs the HQ video track;
8. remove the complete directory after the queue item finishes.

HQ Converter Library does not own `task_N` and does not manage its lifecycle.

### 3.7 Direct Use of `work_dir`

HQ Converter Library uses the supplied `work_dir` directly.

The library must not be expected to create, require, or expose an additional HQ-owned job subdirectory inside `work_dir`.

All HQ job artifacts, including the canonical session file, temporary artifacts, logs when applicable, and the produced video track, are written directly into `task_N` or into library-defined paths rooted in that exact supplied directory.

ffmpeg-converter must not add another integration-owned directory layer around or inside `task_N`.

### 3.8 Temporary Workspace and Final Output Isolation

`task_N` is a temporary integration workspace. It is not the destination for the final user-visible output.

The final output path and filename must be determined by the existing ffmpeg-converter output workflow.

The final user-visible output file must never be created inside `task_N` and must never be owned by `task_N`.

Removing `task_N` must never:

- delete the final output;
- move or rename the final output;
- invalidate the final output path;
- damage the final output;
- make the final output inaccessible.

If cleanup of `task_N` affects the final output, the implementation is non-compliant.

### 3.9 No New Ownership or Recovery Model

Phase 3 must not introduce:

- another working-directory owner;
- persistent HQ job directories;
- session recovery;
- resume behavior;
- automatic retry;
- stale-artifact reuse;
- a new queue lifecycle;
- a new orchestration subsystem.

## 4. HQ Integration Boundary

HQ Converter Library is the sole integration boundary with HQ internals.

ffmpeg-converter interacts with HQ only through the public HQ Converter Library ABI.

HQ Converter Library and the packaged HQ runtime are black boxes for ffmpeg-converter. ffmpeg-converter must not:

- invoke Segmentator directly;
- invoke Encoder Orchestrator directly;
- connect to HQ control sockets;
- inspect or modify HQ internal state;
- duplicate HQ validation;
- duplicate HQ recovery logic;
- duplicate HQ processing logic;
- infer success from partial files;
- replace a library failure with its own decision.

The documented library result is final.

## 5. Required New Components

Only the following new components are required.

### 5.1 HQ Library Wrapper

Create a thin wrapper around the real public HQ Converter Library ABI.

Responsibilities:

- load the platform-specific shared library;
- resolve the required public symbols;
- create a library handle;
- run a job synchronously;
- forward a Stop request;
- retrieve the last library error;
- destroy the handle;
- unload the library when appropriate.

The wrapper must use the real public header and exact ABI signatures. It must not contain HQ business logic, media-processing logic, directory ownership logic, audio logic, or mux logic.

On Linux, load the packaged `.so`. On macOS, load the packaged `.dylib` using the bundle-relative runtime location. Platform-specific library naming must be handled explicitly.

### 5.2 Shared HQ Catalog Provider

Load HQ codec and preset identifiers dynamically from:

```text
modules/encoder_orchestrator_v2/config/presets/encoder_presets_v2.json
```

Responsibilities:

- load the catalog at application startup when HQ is available;
- preserve exact codec names;
- preserve exact preset names;
- expose preset names belonging to each HQ codec;
- provide the exact default pair when it exists;
- serve the same in-memory catalog to both CLI and GUI;
- report an explicit catalog-loading error when HQ is selected but the catalog is unavailable or invalid.

The provider must not interpret preset parameters or processing rules.

### 5.3 Progress Bridge

Receive the HQ Library status callback and forward library values to existing ffmpeg-converter presentation endpoints:

- terminal or console output;
- progress bar;
- status line.

The bridge must use library values directly. It must not:

- recalculate progress;
- calculate another ETA;
- aggregate FPS;
- reinterpret HQ stages;
- replace the HQ message;
- convert an unavailable numeric value into zero.

### 5.4 Minimal Integration Adapter

The integration adapter may:

- prepare `task_N`;
- call HQ Converter Library;
- read the canonical session file after success;
- obtain `video_track.path`;
- call the existing manual Add Track processing entry point with that path.

The adapter must not perform any operation owned by the existing Add Track, audio, Mux, container, subtitle, chapter, attachment, metadata, output-path, or output-naming workflows.

## 6. HQ Runtime Location

The packaged HQ runtime is located at:

```text
third_party/hq_converter
```

The runtime is expected to be complete and operational.

ffmpeg-converter must not rebuild the HQ runtime or replace HQ runtime components with ffmpeg-converter components.

If the runtime is missing, cannot be loaded, or does not work, HQ is unavailable or the current HQ operation fails according to the availability rules below.

## 7. Build-Time Availability

CMake detects the packaged HQ release at `third_party/hq_converter` during configure.

The build system must:

- check the required HQ runtime paths listed in `HQ_CONVERTER_REQUIRED_PATHS`;
- validate that the HQ preset catalog exists at the required runtime-relative path;
- set `HQ_CONVERTER_ENABLED` when the release is present and structurally valid;
- embed availability in generated `presets.json` through `features.hq_converter`;
- copy generated `presets.json` next to each built binary;
- copy generated `presets.json` into the macOS application bundle Resources;
- package the complete required HQ runtime subtree without replacing HQ binaries.

At runtime, ffmpeg-converter reads the generated availability flag. No additional startup runtime-probing system is introduced.

The availability flag controls whether `hq_converter` and its fields are exposed. It does not contain or duplicate the HQ codec and preset catalog.

When HQ is not marked available:

- `hq_converter` is not exposed;
- HQ codec and preset fields are hidden or disabled;
- non-HQ functionality continues normally.

When HQ is marked available but the shared library or catalog later cannot be loaded:

- report an explicit HQ error when HQ is selected or started;
- fail only the current HQ queue item;
- do not create another availability-discovery subsystem;
- do not disable unrelated backends.

## 8. Codec and Preset Selection

The user-facing hierarchy is:

```text
ffmpeg-converter codec
    hq_converter

HQ codec
    x264
    x265
    svt-hevc
    svt-av1
    ffmpeg-prores
    ffmpeg-prores_ks
    ... values loaded at runtime

HQ preset
    codec-specific preset name loaded at runtime
```

HQ codec and preset names are opaque identifiers.

The exact strings from the HQ catalog must be passed to the library unchanged.

ffmpeg-converter must not:

- normalize case;
- rename identifiers;
- translate identifiers;
- infer aliases;
- combine codec and preset into a synthetic identifier;
- derive a codec from preset text;
- replace a rejected pair with another pair;
- copy identifiers into a static ffmpeg-converter catalog.

The default pair is:

```text
x264 + youtube4k
```

It is used only when that exact pair exists in the loaded HQ catalog. If it does not exist, no invented substitute is allowed. Existing UI behavior for requiring or selecting a valid value may be used, but the application must not silently manufacture a different default pair.

The library remains the final authority for Codec plus Preset validation.

## 9. CLI and GUI Integration

The existing HQ selection fields must be populated from the shared runtime HQ catalog provider.

Both CLI and GUI must:

- expose `hq_converter` only when `features.hq_converter` is true;
- expose HQ codec values from the runtime catalog;
- update the HQ preset list when the selected HQ codec changes;
- preserve exact identifier spelling and case;
- pass separate `HQCodec` and `HQPreset` values to the converter core;
- hide or disable HQ fields when HQ is unavailable;
- apply identical container and audio restrictions.

CLI and GUI must not use separate catalogs or generated copies of HQ identifiers.

## 10. Queue Working Directory

For queue item `N`, ffmpeg-converter uses:

```text
<OutputDirectory>/task_N
```

Before HQ Library invocation, ffmpeg-converter checks:

- directory creation success;
- read access;
- write access;
- free space of at least `input file size * 2`.

The exact absolute `task_N` path is passed to HQ Converter Library as `work_dir`.

HQ Converter Library writes its job artifacts directly into that supplied working directory. No additional HQ job subdirectory is part of the Phase 3 contract.

The directory must remain present while the existing Add Track and Mux workflow consumes the HQ video track.

After the queue item finishes, ffmpeg-converter removes the complete `task_N` directory. This applies to:

- HQ success followed by successful final assembly;
- HQ failure;
- cancellation;
- Add Track failure;
- audio-processing failure;
- Mux failure;
- final-output failure.

Cleanup must be limited to the current `task_N` directory and must not traverse external symbolic links.

## 11. HQ Library Invocation

For each queue item using `hq_converter`, ffmpeg-converter calls HQ Converter Library with:

```text
InputFile
WorkDirectory
HQCodec
HQPreset
```

The call is synchronous. The active queue item remains blocked until the library returns:

- success;
- failure;
- cancellation.

Only one selected configuration is used for the active queue according to the existing ffmpeg-converter queue model.

No new queue logic is required.

## 12. Runtime Status

HQ Converter Library publishes status through its public callback.

The callback payload provides normative values including:

```text
stage
progress_percent
fps
remaining_time_sec
message
```

Mapping:

- `message` is written to existing terminal or console output;
- `progress_percent` updates the existing progress bar;
- `stage`, `fps`, and `remaining_time_sec` update the existing status line;
- unavailable numeric values remain unavailable and are not displayed as calculated zero values.

No HQ status value is recalculated by ffmpeg-converter.

## 13. HQ Completion and Result Retrieval

HQ processing is successful only when the public library call returns its documented success result.

On success, ffmpeg-converter opens the canonical session file located directly under the supplied `work_dir`:

```text
<work_dir>/job.<codec>.<preset>.eov2.session.json
```

It reads only:

```text
artifacts.outputs.video_track.path
```

Example:

```json
{
  "artifacts": {
    "outputs": {
      "video_track": {
        "path": "/absolute/task_N/x264.youtube4k_final.ts",
        "container": "unknown",
        "state": "ready"
      }
    }
  }
}
```

Requirements:

- the session file is read only after documented library success;
- the path locates an already confirmed HQ result;
- reading the path is not additional HQ validation;
- the session file is not read after failure or cancellation;
- failure and cancellation are never overridden by existing files;
- no callback-schema extension is required;
- no new library getter is required.

ffmpeg-converter must not:

- scan `task_N` for candidate files;
- guess the output track filename;
- select partial output;
- use unrelated HQ session fields;
- move the final user output into `task_N`.

## 14. Transfer to the Existing Add Track Workflow

Immediately after `video_track.path` is obtained, the integration adapter passes that path to the exact existing manual Add Track processing entry point.

From that call onward:

- HQ and manual Add Track use the same code path;
- the original input remains the source for audio and other non-video content according to existing behavior;
- the HQ track is the external replacement video source;
- existing output-path and naming logic remains authoritative;
- the final output is created outside `task_N`.

No HQ-specific final assembly is permitted.

## 15. Container and Audio Policy

These policies must be enforced through the existing ffmpeg-converter UI restrictions and the existing Add Track, audio, and Mux implementation. They must not be implemented by a new HQ-specific audio or mux engine.

### 15.1 HQ ProRes Encoders

For HQ ProRes encoders:

```text
Final container: MOV
Audio mode: PCM
Audio tracks: first input audio track only
```

No other audio mode is available in CLI or GUI for HQ ProRes encoding.

Audio filters may be used according to existing PCM processing behavior.

### 15.2 All Other HQ Encoders

For non-ProRes HQ encoders:

```text
Final container: MKV
```

Available audio modes:

- `copy`;
- `pcm`;
- `aac`;
- `aac+ac3`.

Track rules:

```text
copy
    -> copy all input audio tracks

pcm
    -> use the first input audio track

aac
    -> use the first input audio track

aac+ac3
    -> use the first input audio track
```

Audio filters are available only for:

- `pcm`;
- `aac`;
- `aac+ac3`.

Audio filters are unavailable for:

- `copy`.

These restrictions must be identical in CLI and GUI and must use existing audio-processing behavior.

## 16. Subtitles, Chapters, Attachments, Tags, and Metadata

HQ integration must preserve the behavior of the existing manual Add Track workflow for:

- subtitles;
- chapters;
- attachments;
- global tags;
- track tags;
- metadata;
- non-video tracks and elements handled by the existing workflow.

No HQ-specific implementation or command-line reconstruction is permitted.

## 17. Final Output Path and Lifetime

The final user-visible output path is selected exclusively by the existing ffmpeg-converter output workflow.

The final file must be created outside `task_N`.

The HQ video track may remain inside `task_N` while the existing Add Track and Mux workflow reads it. `task_N` must not be deleted until final assembly has completed or failed and the HQ track is no longer needed.

After successful final assembly:

1. the final output exists at the normal ffmpeg-converter destination;
2. the final output is closed and complete;
3. `task_N` is removed;
4. the final output remains present and valid after cleanup.

## 18. Stop and Cancellation

The existing Stop policy is used.

For an active HQ operation:

```text
converter_stop()
    -> HQ Library stop request
```

ffmpeg-converter must not stop internal HQ processes directly.

After HQ cancellation:

- no HQ result is used;
- the session file is not read;
- existing Add Track and Mux processing is not started for the item;
- HQ resources are released;
- `task_N` is removed;
- standard queue behavior continues.

If cancellation occurs after HQ success while the existing Add Track or Mux workflow is running, existing ffmpeg-converter cancellation behavior remains authoritative.

## 19. Error Handling

An HQ error affects only the current queue item.

After any HQ error, ffmpeg-converter must not:

- start existing Add Track or Mux processing for the current item;
- use a partial HQ result;
- reuse stale files from `task_N`;
- attempt HQ session recovery;
- select an alternate codec or preset;
- choose an alternate processing backend automatically.

The converter must:

- print a message to the console;
- include the current input filename;
- preserve HQ error text when available;
- release HQ resources;
- remove `task_N`;
- continue according to existing queue behavior.

Examples:

```text
movie.mkv - HQ failed
movie.mkv - codec/preset not found
movie.mkv - HQ runtime unavailable
movie.mkv - HQ catalog unavailable
movie.mkv - insufficient free space
movie.mkv - working directory unavailable
movie.mkv - cancelled
```

Errors occurring after the HQ track has been passed into the existing Add Track workflow are handled by the existing Add Track, audio, Mux, output, and queue error paths.

## 20. Cleanup

After the current queue item finishes, ffmpeg-converter removes:

```text
<OutputDirectory>/task_N
```

This applies to every outcome.

The complete temporary directory is removed recursively with all HQ artifacts.

Cleanup must occur only after no active existing workflow still needs the HQ video track.

Cleanup is limited to `task_N` and must not follow external symbolic links.

The final output must never be inside the cleanup tree.

## 21. Queue Behavior

A failed or cancelled HQ item must not terminate processing of unrelated later queue items.

The existing queue model remains authoritative.

No new persistent queue, resume system, recovery system, retry system, or HQ queue is introduced.

## 22. Packaging

HQ packaging is performed through the existing project packaging architecture.

Phase 3 uses the packaged runtime from:

```text
third_party/hq_converter
```

ffmpeg-converter and HQ Converter use separate runtime binary sets.

ffmpeg-converter must not replace HQ FFmpeg, FFprobe, encoders, native-analysis components, shared libraries, or libav components with ffmpeg-converter versions.

The AppImage packaging process must:

- include the required HQ runtime subtree;

- ensure the packaged HQ shared library can be loaded inside the AppImage;
- package the runtime HQ catalog used by both CLI and GUI;

/home/viktor/AppImages/appimagetool

The packaging process must:

<Application>.app/Contents/Resources/hq_converter/

macOS verification must not be claimed from Linux.

## 23. Platform Scope

Supported:

- Linux;
- macOS.

Native Windows HQ integration is not required.

Windows builds must remain unaffected and must not expose `hq_converter`.

## 24. Implementation Scope

Expected new code is limited to:

- a thin HQ Library wrapper;
- runtime path resolution required to load the packaged library and catalog;
- one shared runtime HQ catalog provider;
- a callback-to-presentation bridge;
- an integration adapter that creates `task_N`, runs HQ, reads `video_track.path`, and calls the existing Add Track entry point;
- minimal CLI and GUI binding to the shared catalog provider;
- CMake availability detection;
- packaging adjustments required to include the prepared HQ runtime;
- focused unit, integration, and end-to-end tests.

The implementation must prefer existing ffmpeg-converter functions and data paths over new abstractions.

A large HQ-specific audio, mux, container, output, catalog, lifecycle, or queue implementation is evidence of non-compliance and must be rejected during review.

## 25. Explicitly Prohibited Implementations

The following solutions are prohibited even if they compile or appear to work:

- a second audio engine;
- a second mux engine;
- an HQ-specific final mux command;
- copying original streams by removing or adding command flags in a separate HQ branch;
- a parallel subtitle or chapter implementation;
- a static HQ list in GUI code;
- an HQ group manually copied into `presets.json.in`;
- a build-time script that converts the HQ catalog into a separate GUI catalog;
- requiring a rebuild to discover a new HQ codec or preset;
- creating the final output inside `task_N`;
- deleting `task_N` before existing final assembly stops using the HQ track;
- scanning `task_N` for output candidates;
- guessing filenames;
- introducing another owner for `task_N`;
- redesigning the queue, Add Track, Mux, audio, output, or packaging architecture.

## 26. Required Pre-Implementation Review

Before implementation begins, the developer or coding agent must identify, by exact function and file:

1. the existing manual Add Track processing entry point that will receive the HQ video track;
2. the point before which the HQ and manual flows will converge;
3. the existing audio and Mux path that remains unchanged;
4. the existing output-path and output-naming path that remains unchanged;
5. the GUI mechanism that will consume the shared runtime HQ catalog provider;
6. the files planned for modification.

Implementation must not begin until this mapping demonstrates that no parallel audio, mux, output, catalog, ownership, or lifecycle subsystem is planned.

## 27. Validation

The implementation must verify at least the following.

### 27.1 Availability and Loading

- CMake detects `third_party/hq_converter` during configure.
- Generated `presets.json` contains the correct `features.hq_converter` value.
- `hq_converter` is hidden or disabled when the build does not include HQ.
- Explicit load failure is reported when the build marks HQ available but the platform library cannot load.
- Linux loads the packaged `.so`.
- macOS loads the packaged `.dylib`.

### 27.2 Shared Dynamic Catalog

- HQ codec and preset names are loaded at runtime.
- CLI and GUI use the same catalog provider.
- Exact identifier case and spelling are preserved.
- A valid Codec plus Preset pair reaches the library unchanged.
- An invalid pair produces the library error.
- Adding a test codec or preset to the packaged HQ catalog and restarting the application exposes it in both CLI and GUI without rebuilding ffmpeg-converter.
- No copied or generated second HQ catalog is used.

### 27.3 Working Directory

- ffmpeg-converter creates `task_N`.
- The exact `task_N` path is passed as `work_dir`.
- HQ Library works directly in that directory.
- No additional integration-required HQ job directory is created.
- Insufficient free space prevents HQ startup.
- Read or write failure prevents HQ startup.
- `task_N` remains available while the existing Add Track and Mux workflow consumes the HQ track.

### 27.4 Result Contract

- Successful HQ output is read from the canonical session file directly under `work_dir`.
- Only `artifacts.outputs.video_track.path` is used.
- The session file is not read after failure or cancellation.
- The working directory is not scanned for candidate outputs.

### 27.5 Mandatory Workflow Convergence

- Manual Add Track and HQ Converter call the same existing Add Track processing entry point.
- Their code paths converge before audio, subtitle, chapter, attachment, metadata, container, mux, and output processing.
- No HQ-specific final mux command exists.
- No HQ-specific audio encoder or audio-copy implementation exists.

### 27.6 Existing Audio and Container Behavior

- HQ plus `copy` uses the existing copy behavior and copies all input audio tracks.
- HQ plus `pcm` uses the existing PCM behavior and the first input audio track.
- HQ plus `aac` uses the existing AAC behavior and the first input audio track.
- HQ plus `aac+ac3` uses the existing AAC plus AC3 behavior and the first input audio track.
- Existing audio filters work for PCM, AAC, and AAC plus AC3.
- Audio filters remain unavailable for copy mode.
- HQ ProRes forces MOV, PCM, and the first input audio track through existing behavior.
- Non-ProRes HQ forces MKV and exposes only the allowed audio modes.
- CLI and GUI enforce identical restrictions.

### 27.7 Existing Non-Video Content Behavior

- Subtitles behave the same as with manual Add Track.
- Chapters behave the same as with manual Add Track.
- Attachments behave the same as with manual Add Track.
- Tags and metadata behave the same as with manual Add Track.
- Existing manual Add Track behavior remains unchanged.
- Existing non-HQ codec behavior remains unchanged.

### 27.8 Progress, Stop, and Errors

- Callback messages reach the terminal.
- Callback progress reaches the progress bar.
- Stage, FPS, and remaining time reach the status line.
- Missing FPS or ETA is not displayed as a calculated value.
- Stop is forwarded to HQ Library.
- HQ failure and cancellation do not start Add Track or Mux for that item.
- Failure of one item does not stop later items.

### 27.9 Cleanup and Output Isolation

- Success removes `task_N` only after final output assembly completes.
- HQ failure removes `task_N`.
- Cancellation removes `task_N`.
- Add Track, audio, or Mux failure removes `task_N`.
- The final output is outside `task_N`.
- The final output still exists and is valid after `task_N` is removed.
- Cleanup does not traverse external symbolic links.

### 27.10 Packaging

- Linux works with the packaged HQ runtime.
- macOS works with the packaged HQ runtime.
- AppImage contains the expected HQ subtree.
- AppImage starts outside the source tree with HQ available.
- macOS `.app` starts outside the source tree with HQ available.
- Both packaged GUI and CLI load the same runtime HQ catalog.
- ffmpeg-converter and HQ use separate runtime binary sets.
