# Version 3.0 — Phase 3: HQ Converter Integration (Segmented High-Quality Encoding)

## 1. Goal

Integrate the external **HQ_converter** project (a production-validated segmented
video encoding system, `/home/viktor/LLM/Projects/HQ_converter`, v0.7.x) into
ffmpeg-converter as a new first-class codec:

1. New codec menu item: **`hq_converter`**.
2. Preset catalog is **read at runtime from HQ's preset file**
   (`modules/encoder_orchestrator_v2/config/presets/encoder_presets_v2.json`
   of the bundled release) — no hardcoded preset list. The **preset is chosen
   by the user**; `x264.youtube4k` is the default.
3. The encoded video track is assembled into the final file by the **existing
   `mux` module** (`src/mux/`) — the `mux` mode was originally created and
   debugged precisely for consuming HQ_converter output, so the integration
   reuses the current `mux` logic with small refinements (§4).
4. HQ works in **temporary folders** created and managed by ffmpeg-converter.
5. **Progress and statistics are provided by HQ_converter**; ffmpeg-converter
   relays them through the existing `ConverterCallbacks`.
6. Platforms: **Linux and macOS only** (HQ Pascal runtime is native on these
   two; Windows is excluded — HQ supports Windows only via WSL).

In v3.0 HQ runs in a **simplified mode**: the segmentator uses
`original-baseline` for any non-ProRes input and `prores-normalized` for ProRes
input, both with default parameters; `encoder_orchestrator_v2` uses the
predefined presets with no parameter overrides.

Distribution model: a ready-to-use HQ **release tree** is vendored into the
ffmpeg-converter source tree (`src/platform/linux/hq_converter/`,
`src/platform/macos/hq_converter/`), copied next to the program into
`build/bin/hq_converter/`, and included in the AppImage / macOS `.app` bundle.

Phase 3 depends on **Phase 1** (codec → preset model, `ConvertOptions.preset[32]`,
dynamic menus). Phase 2 is orthogonal and may land before or after.

## 2. HQ Converter Overview (external system)

HQ Converter is a highly optimized, production-debugged **segmented encoding**
system. Two active runtime modules:

| Module | Role |
|---|---|
| `segmentator` | Splits the source video into segments and performs per-frame complexity analysis producing per-frame QP files (`seg_XXXX.mkv` + `seg_XXXX.qp` pairs, `segment_report.txt` with color/HDR metadata). Uses `libseg_native` + libav natively (no ffmpeg-pipe hot path). |
| `encoder_orchestrator_v2` | Autonomous encoding module: encodes all segments in parallel per a selected preset and assembles the final video track. Controlled via a strict **UDS NDJSON control channel** (`run|status|stop|kill|clear|delete|exit`). |

### 2.1 Encoder/preset catalog (v0.7.0, 13 presets)

Source: `encoder_presets_v2.json` → `encoders.<name>.presets`.

| Encoder | Presets | Default | Raw track output |
|---|---|---|---|
| `x264` | `fullhd`, `uhd4k`, `youtube4k` | `fullhd` | `.ts` |
| `x265` | `Medium`, `Slow`, `Music`, `UHD`, `UHD_grain` | `Medium` | `.hevc` (raw Annex B) |
| `svt-hevc` | `balanced_4k`, `balanced_grain` | `balanced_4k` | `.hevc` |
| `svt-av1` | `balanced` | `balanced` | `.mkv` |
| `ffmpeg-prores` | `standard` | `standard` | `.mov` |
| `ffmpeg-prores_ks` | `hq` | `hq` | `.mov` |

All six encoders are software CPU encoders; full color/HDR pipeline validated
(SDR BT.709, HDR10 BT.2020/PQ passthrough and forced SDR conversion).

Note: the "Default" column is HQ's own `default_preset` per encoder.
ffmpeg-converter's own default selection is **`x264.youtube4k`** (§5).

Produced by `HQ_converter/scripts/create_cli_release.sh` (~270 MB, Linux build):

### 2.3 Relevant contracts

- **Control channel** (`docs/contracts/encoder_orchestrator_v2_control_channel_contract_v1.md`):
  UDS + line-delimited NDJSON; statistics only in `status` responses:
  `data.behavior.progress_percent`, `data.behavior.tasks
  {done,pending,running,failed,total}`, `data.behavior.stage_status`
  (`idle|encoding|track_assembly_*|track_ready|...`), `data.runners[].speed_fps`.
  Socket file `<job>.eov2.sock` is owned by the runner.
- **Process isolation** (ADR-0003): all compute stages are separate processes;
  integration only through the management module contract; direct module-to-module
  calls forbidden.
- **Output assembly** (`docs/policies/output_assembly_policy_v1.md`): raw encoder
  outputs per §2.1 table; final track assembled by the orchestrator
  (two-step concat + mkvmerge for HEVC).

### 2.4 Reference implementations for the integration

The two CLI utilities shipped in the release drive the whole pipeline and are
the **reference implementations** for the new batch entry point (Section 3):

- `modules/cli_utility/src/integration/segmentator_api_adapter.pas` — segmentator invocation (linked in-process via `SegmentatorCore`).
- `modules/cli_utility/src/integration/encoder_orchestrator_api_adapter.pas` — v2 artifact building (`BuildV2Artifacts`: preset resolution, color/HDR injection, QP aggregation), runner spawn, UDS command/status loop, runner lifecycle.
- `modules/cli_utility/src/submodules/session_create_wizard.pas` — preset catalog loading and job creation parameters.

### 2.5 Current release gaps (must be closed before Phase 3 ships)

1. **No non-interactive entry point.** `hq_cli_utility`/`_tui` are interactive
   session utilities; there is no batch mode an external program can drive.
2. **No `segmentator` binary in the release** (segmentation is linked
   in-process into `hq_cli_utility`; a standalone `segmentator_runner` exists
   in the source tree at `modules/segmentator/runner/` with a clean
   `[nn%]`/`TERMINAL:`/exit-code protocol, but is not packaged).
3. **No version marker** — nothing to pin compatibility against.
4. **Linux-only release build** — the macOS release (`.dylib` SDK, Mach-O
   binaries) must be produced on a macOS host.

## 3. Integration Architecture

### 3.1 Decision: single batch entry point owned by HQ_converter (Option A)

ffmpeg-converter treats HQ as **one external pipeline tool** (the same way it
treats ffmpeg/mkvmerge) and invokes a new non-interactive batch binary that
HQ_converter adds to its release:

```
ffmpeg-converter ──popen──> hq_pipeline_batch ──> segmentator (in-process)
                                              └──> encoder_orchestrator_v2_runner (UDS)
```

`hq_pipeline_batch` reuses the existing Pascal units (reference implementations,
§2.4) and performs: segmentation → job/artifact building → orchestrator start →
`run` → `status` polling → final track ready. It reports progress/statistics to
stdout and owns all HQ-side error handling and runner shutdown.

**Rejected alternatives:**

- **Option B — C drives every stage** (C launches `segmentator_runner`,
  reimplements `BuildV2Artifacts` with jansson, speaks UDS NDJSON to the
  orchestrator runner): duplicates ~2000 lines of HQ domain logic
  (preset resolution, color vocabulary, HDR metadata extraction, QP
  aggregation, schema validation) inside ffmpeg-converter, with guaranteed
  drift every time HQ contracts change. Violates the spirit of ADR-0003
  (two orchestration points).
- **Option C — shared library (`libhq_pipeline.so`)**: feasible in principle
  (FPC shared libs are used in this ecosystem — `fpc/converter/libconverter_pas.so`),
  but couples memory/runtime policy of two projects into one process and
  forfeits the process-isolation guarantees HQ is designed around.

Option A keeps the two projects decoupled at a versioned text protocol, matches
HQ's process-isolation architecture, and minimizes ffmpeg-converter-side code.

### 3.2 Batch binary contract (to be implemented in HQ_converter)

Invocation:

```
hq_pipeline_batch \
  --input   <source video file> \
  --work-dir <empty directory created by the caller> \
  --encoder <x264|x265|svt-hevc|svt-av1|ffmpeg-prores|ffmpeg-prores_ks> \
  --preset  <preset name from encoder_presets_v2.json> \
  [--output-track <path>]                          # default <work-dir>/final_track.<ext>
```

Simplified-mode rules (v3.0):

- **Segmentation policy is auto-selected**, not passed by the caller:
  `prores-normalized` when the input video codec is `prores`/`prores_ks`,
  otherwise `original-baseline` — both with default parameters.
- **No parameter overrides**: `encoder_orchestrator_v2` runs the selected
  preset exactly as predefined; `hdr=auto`, default QP aggregation.
  `--encoder`/`--preset` are the only user-facing choices.

Stdout protocol (line-oriented NDJSON-free text, UTF-8, flushed per line):

```
HQPIPE 1                          # first line: protocol marker + version
STAGE segmentation|job_prepare|encoding|assembly
PROGRESS <overall%> <stage%> <fps> <tasks_done> <tasks_total>
STATS <single-line JSON>          # optional rich stats (tasks breakdown, workers, cpu)
MESSAGE <text>                    # diagnostics, forwarded to on_message
TRACK <absolute path>             # exactly once, after successful assembly
TERMINAL done|error|fail
```

- `overall%` is computed by the batch binary with fixed stage weights:
  segmentation 0–15 %, job_prepare ≈ 15 %, encoding 15–95 %, assembly 95–100 %.
- `fps` is the sum of `data.runners[].speed_fps` during encoding, `0` otherwise.
- Exit codes: `0` done, `1` error, `2` fail (mirrors `segmentator_runner`
  semantics), `3` stopped by request.
- **Stop semantics**: on SIGTERM/SIGINT the batch binary sends `stop` then
  `exit` over the control channel (per control-channel contract §15: wait
  1500 ms, then SIGTERM/SIGKILL the runner), and exits with code `3`.
- Session files, socket, segments, encoded artifacts — all inside `--work-dir`.

## 4. Conversion Flow Inside ffmpeg-converter

Per input file (multi-file lists are supported; each file gets its own workdir
and HQ session):

```
1. Stage "audio pass"     converter_process_files(codec="copy") → intermediate file
                          (audio processing per user options, -c:v copy) —
                          identical to the existing `mux` mode (src/cli/main.c:240-249)
2. Stage "hq segmentation"┐
   Stage "hq encoding"    ├ hq_pipeline_batch(input=ORIGINAL file, work-dir=tmp,
   Stage "hq assembly"    ┘                  encoder, preset) → TRACK:<encoded video track>
3. Stage "Post-mux"       mux_run_postprocess(intermediate_file=step-1 output,
                          video_track_file=HQ track, output_file=same path) —
                          mkvmerge takes video track 0 from the HQ track and
                          everything else (audio/subs/chapters) from the
                          intermediate file (src/mux/mux.c:249-339)
4. Cleanup                recursive rmtree of the workdir (success only)
```

### 4.0 Audio track rules (refinement of the `mux` flow)

The `audio_norm` + `genre` selection is allowed, but **only the first original
audio track is used**; `audio_output` decides how audio is carried:

| `audio_norm` | `audio_output` | Audio in the final file |
|---|---|---|
| `none` | `copy` | **All original tracks** copied (`-c:a copy`, all `-map 0:a:*`) |
| `none` | `aac` / `ac3` / … | **First original track only**, encoded (`-map 0:a:0`) |
| any (loudnorm/peak/…) | any | **First original track only**, processed (`-map 0:a:0` + filters) |

So copying all original tracks is available **only** with
`audio_norm=none + audio_output=copy`; every other combination uses the first
track. This is the only change relative to the existing `mux` mode, whose
audio handling otherwise stays as-is.

### 4.1 Container selection (refinement of the `mux` flow)

| Input video | HQ track | Final container |
|---|---|---|
| non-ProRes | `.ts` / `.hevc` / `.mkv` | **`.mkv`** (mkvmerge) |
| ProRes (`prores`/`prores_ks`) | `.mov` | **`.mov`** |

Default is **`.mkv`**; ProRes video produces **`.mov`**. The container is
decided by probing the input video codec (`probe_input_video_codec`,
`converter.c:167-212`), matching HQ's own `ffmpeg-prores`/`ffmpeg-prores_ks`
encoders. This replaces the previous "always `.mkv`" rule.

Notes:

- HQ encodes from the **original** input (segments are video-only, `-an`);
  the intermediate file differs only in audio, so this is correct.
- The mux module already handles raw `.hevc/.h264` tracks (forces fps via
  ffprobe, `mux.c:59-65,293-300`) — x265/svt-hevc tracks work as-is;
  `.ts/.mkv/.mov` tracks also work (`--video-tracks 0` is container-agnostic).
- **Single-file restriction of `mux` mode does not apply**: the HQ flow is
  wired per-file, so batch lists work.

### 4.2 Progress and statistics mapping

| HQ signal | ffmpeg-converter callback |
|---|---|
| `STAGE segmentation/job_prepare` | `on_stage("hq segmentation")` |
| `STAGE encoding` | `on_stage("hq encoding")` |
| `STAGE assembly` | `on_stage("hq assembly")` |
| `PROGRESS <overall> <stage> <fps> ...` | `on_progress_encode(overall, fps, eta)` — ETA computed from wall-clock elapsed vs overall% (same method as `run_ffmpeg_encode_with_progress`, `converter.c:1119-1133`) |
| `MESSAGE` / `STATS` | `on_message` |
| mux stage | existing `on_stage("Post-mux (mkvmerge)")` |

Rich statistics (tasks done/total/failed, workers, per-runner speed,
`stage_status`) arrive in `PROGRESS`/`STATS` fields; in v3.0 the CLI shows the
standard progress bar (percent/fps/ETA), full stats are forwarded via
`on_message` and become a GUI stats panel candidate for v3.1+.

### 4.3 Stop handling

`converter_stop()` sets `stop_flag`; the HQ reader loop checks it per line
(same pattern as the ffmpeg progress loop, `converter.c:1135-1138`) and sends
SIGTERM to the **process group** of the batch binary (spawn with `setsid`;
kill `-pgid`) — the batch binary performs the graceful orchestrator shutdown
(§3.2). Result: `ERR_SKIP_FILE` (consistent with stopped ffmpeg encodes).

### 4.4 Error handling

- `TERMINAL:error|fail` + last `MESSAGE` → `on_error` → new error code
  **`ERR_HQ_PIPELINE_FAILED`** (appended to `ConverterError`, `converter.h:13-46`
  — additive, no ABI break; the 8 exported functions unchanged).
- Segmentator fail-fast conditions (e.g. keyframe density too low for
  keyframe-aligned cuts inside `seg_min/seg_max`) surface as `TERMINAL:fail`
  with the actionable `MESSAGE` from HQ.
- Post-mux failure keeps existing mux error paths.

## 5. UX: Codec Menu and Presets

- Codec string: **`hq_converter`** (fits `codec[32]`).
- Preset id: **`<encoder>/<preset>`** — e.g. `x265/Medium`,
  `svt-hevc/balanced_4k`, `ffmpeg-prores_ks/hq`. 13 combinations (§2.1).
- Catalog source: `encoder_presets_v2.json` of the bundled release, parsed with
  the vendored jansson (`third_party/jansson`, already used by loudnorm,
  `converter.c:758-772`). Read `encoders.*.presets` keys + `default_preset`.
- Default preset when unspecified: **`x264.youtube4k`**.
- If the release tree is not found, the codec is silently absent from all menus
  (same probe-gated model as HW codecs).

CLI:

```
ffmpeg_converter -c hq_converter --preset x265/Medium input.mkv
ffmpeg_converter -c hq_converter input.mkv          # → x264.youtube4k
```

Interactive mode: two-level selection matching the Phase 1 model — codec
`hq_converter` → preset submenu built from the JSON (encoder groups, default
preset marked). `--codecs-list` (Phase 1) lists all 13 pairs when available.

GTK4 GUI: `hq_converter` in the codec combo; preset combo populated from the
same reader. Cocoa GUI: same, via the shared C reader.

HQ session parameters beyond the preset are fixed in v3.0 (§3.2 simplified
mode): segmentation policy auto-selected, `hdr=auto`, default QP aggregation.
No parameter overrides are exposed.

## 6. Tool Discovery and Availability

New accessor `hq_get_release_dir()` / `hq_get_batch_bin()` in the new `src/hq/`
module, following the existing discovery pattern:

1. Env var **`HQ_CONVERTER_DIR`** (explicit override).
2. Executable-adjacent: `<exe_dir>/hq_converter/`, `<exe_dir>/bin/hq_converter/`
   → covers `build/bin/hq_converter/` dev builds.
3. AppImage: `$APPDIR/usr/hq_converter/`.
4. macOS bundle: `<exe_dir>/../Resources/hq_converter/`.
5. Dev fallback: `FFMPEG_CONVERTER_SOURCE_DIR/src/platform/<os>/hq_converter`
   (compile-time define, same pattern as the ffmpeg dev fallback,
   `src/platform/linux/runtime_probe.c:103-137`).

Availability gate: directory exists + `hq_pipeline_batch` executable + readable
`encoder_presets_v2.json`. At first use, the batch binary prints `HQPIPE 1`;
the release carries a `VERSION` marker that is logged via `on_message`.

**mkvmerge for the post-mux step**: `mux_run_postprocess` resolves mkvmerge via
`platform_get_mkvmerge_bin()` (`MKVMERGE_BIN` env → bundled → PATH,
`src/converter/platform/converter_linux.c:52-56`). Since the HQ release bundles
its own mkvmerge, the HQ discovery code sets `MKVMERGE_BIN` to it as a fallback
when no system/bundled mkvmerge exists. Side benefit: this also unblocks the
macOS **CLI**, where `platform_run_mux_postprocess` currently returns
`ERR_INVALID_OPTIONS` (`src/cli/platform/cli_macos.c:219-227`) for lack of
mkvmerge packaging — the HQ flow implements its own macOS post-mux path using
the release-bundled mkvmerge.

## 7. Temporary Work Directory

- Created per file with `mkdtemp("/tmp/hqconv_XXXXXX")` — the m4v pattern
  (`src/m4v/platform/m4v_platform_posix.c:56-75` + `posix_rmtree`).
- Contents (owned by HQ): `seg_*.mkv/.qp`, `segment_report.txt`,
  `job.<encoder>.<preset>.json`, `.eov2.*` artifacts, `.eov2.sock`, encoded
  segments, final track.
- **UDS path length**: Unix socket paths are limited to ~108 chars — the
  template sits directly under `/tmp` to keep `<work-dir>/job.*.eov2.sock`
  short regardless of user file names.
- **Cleanup policy**: success → recursive delete; failure or stop → keep the
  directory and report its path via `on_message` (diagnostics/resume), with
  `--hq-keep-workdir` to force retention on success.
- **Disk space preflight**: segments ≈ source size, so the workdir needs
  roughly 2× the input file size free. Check with `statvfs` before starting;
  fail fast with a clear message.
- Optional `--hq-workdir DIR` places workdirs on another disk (recommended by
  HQ's output assembly policy for large files).

   UDS adapter, maps control-channel `status` payloads to the stdout protocol.
2. **Release script changes** (`scripts/create_cli_release.sh`): include
   `hq_pipeline_batch`, add `VERSION` marker file (e.g. `0.7.x-batch.N`),
   keep launcher environment logic.
3. **macOS release build** produced and smoke-tested on a macOS host.
4. **Protocol compatibility**: `HQPIPE 1` marker must change only with
   incompatible protocol revisions; ffmpeg-converter rejects unknown versions
   with a clear error.

## 11. Backward Compatibility

- C ABI unchanged: same 8 exported functions; `ERR_HQ_PIPELINE_FAILED` is an
  appended enum value; `codec[32]`/`preset[32]` accommodate new strings.
- All existing codecs, `mux` mode, m4v pipeline, probing — untouched.
- Windows builds unaffected (codec simply absent).
- Preset catalog is data-driven: HQ adding presets requires **zero**
  ffmpeg-converter changes (menu rebuilds from JSON).
- If Phase 1 is delayed, Phase 3 can land on the current architecture with a
  hardcoded 13-entry preset list; the JSON reader stays and Phase 1 adopts it.
  Merging after Phase 1 is the intended order.

## 13. Risks and Mitigations

| # | Risk | Mitigation |
|---|---|---|
| R1 | ~270 MB × 2 platforms of binaries in git | git-lfs or a CMake-time download script with checksum pinning; decision required before import |
| R2 | macOS release must be built on a macOS host; current artifacts are Linux-only | Schedule macOS build session; release script already platform-aware (Makefile auto-selects Darwin units) |
| R3 | HQ contracts are v0.7.x and evolving | Pin release via `VERSION` marker; `HQPIPE` protocol version check at startup; upgrade releases deliberately |
| R4 | Workdir needs ≈2× source size; `/tmp` may be too small | `statvfs` preflight with clear error; `--hq-workdir` for another disk; documented in user manual |
| R5 | Software encoding is slow (hours for UHD x265/SVT) | Accurate ETA from HQ progress; stats show tasks/speed; set expectations in docs |
| R6 | Stop must kill the whole process tree (batch → runner → N encoders) | `setsid` + kill process group; batch also performs graceful control-channel shutdown; contract §15 bounds runner teardown |
| R7 | UDS path length limit (~108 chars) | Workdir template directly under `/tmp` (`/tmp/hqconv_XXXXXX`), never under long output paths |
| R8 | `LD_LIBRARY_PATH`/dependency conflicts between the two toolchains | Launch only through the self-contained release (its own env setup); never mix HQ libs into ffmpeg-converter process space |
| R9 | Two bundled ffmpeg copies (size, version drift) | Accepted: HQ's toolchain stays isolated by design (its own `toolchain_runtime.ini`); no merging |
| R10 | AppImage grows to ~300+ MB | `ENABLE_HQ_CONVERTER` packaging option; document size trade-off |
| R11 | mkvmerge version difference (HQ-bundled vs system) for post-mux | Explicit resolution order (§6); post-mux validates output with ffprobe (`mux.c:143-180`) |
| R12 | ProRes presets produce `.mov` tracks; mux assembly for `.mov` needs MP4Box/mkvmerge `.mov` handling | Container auto-selected by input codec (§4.1); validate the `.mov` post-mux path with ffprobe (`mux.c:143-180`) during validation (item 11) |
| R13 | Phase 3 depends on Phase 1 preset model | Fallback design in §11 if Phase 1 slips |

## 14. Recommendations

1. **Batch entry point over C-side orchestration** — all HQ domain logic stays
   in HQ_converter; ffmpeg-converter integrates one process + one text protocol.
2. **Reuse the `mux` module unchanged** — HQ track as `video_track_file`,
   audio-processed file as `intermediate_file`; raw-HEVC fps handling already
   exists there. The `mux` mode was built for exactly this purpose.
3. **Follow the existing `mux` flow exactly** for the audio pass
   (`codec="copy"` first), adding only the two refinements of §4.0/§4.1:
   first-audio-track restriction (except `none+copy`) and ProRes→`.mov`
   container auto-detection.
4. **Keep the release an intact relocatable subtree** in every packaging form
   (build/bin, AppImage, `.app`); never split its files.
5. **Default workdir under `/tmp`**, user override via `--hq-workdir`; keep on
   failure, delete on success.
6. **Pin and log the HQ release version** at session start (`on_message`).
7. **Keep HQ in simplified mode for v3.0** — segmentation policy auto-selected
   by input codec, no parameter overrides; the preset is the only user choice.
   Exposing `--hdr`/`--crop`/`--qp-*` is a v3.1+ candidate.
8. **Stats panel for the GUI in v3.1** — the `STATS` JSON (tasks breakdown,
   workers, per-runner speed) is already delivered in v3.0 via `on_message`.
9. **Consider `av1` quality expectations**: `svt-av1/balanced` is the single
   AV1 preset today; more tiers can be added purely on the HQ side.
10. **Phase 4 candidates** unlocked by this integration: resume/retry of failed
    HQ sessions from the GUI (control channel `clear`/`run` supports it),
    per-segment QP visualization, metrics (PSNR/SSIM) via HQ's
    `video-metric` roadmap.
