# Phase 4: Filter Engine — deblock → filter presets, GPU filter catalog

> Version 3.0 roadmap document. Companion to `v3.0-Phase1.md` (codec/preset
> architecture), `v3.0-Phase2.md` (extended codec catalog), `v3.0-Phase3.md`
> (HQ_converter integration).

## 1. Goal

Replace the single hardcoded `deblock` filter with a **data-driven video
filter engine**:

1. **`deblock` becomes a filter preset** — `-d/--deblock <none|weak|strong>`
   is replaced by `-f/--filter <preset_id>` (e.g. `deblock/weak`,
   `libplacebo_deband/medium`).
2. **`filter_presets.json`** — a new JSON preset file for filters, structured
   by `os/interface/filter` (same axis as the Phase 1 codec presets file), so
   filter presets can be defined **independently of program development**.
3. **Dynamic availability** — the filter list is filled at runtime from what
   the current system actually supports (software / Vulkan / OpenCL / CUDA),
   not a hardcoded array; CLI help/menu/validation use the new `--filters-list`
   parameter, the filter counterpart of `--codecs-list`.
4. **New GPU filters** (first batch): `libplacebo_deband`, `nlmeans_opencl`,
   `nlmeans_vulkan`, `bilateral_cuda`, `boxblur_opencl`, and the combined
   `libplacebo_deband+nlmeans_vulkan` chain.
5. **Parameter tuning pass** — a dedicated sub-step that calibrates the preset
   parameter sets for the new filters across content types and use cases.

The phase depends on Phase 1 (JSON preset infrastructure, `ConvertOptions`
refactor) and reuses Phase 2/3 probing infrastructure where applicable.

### 2.2 Structural facts that shape the design

- **No JSON preset infrastructure exists yet** — the Phase 1 codec presets file
  is also still to be built; Phase 4 reuses the Phase 1 loader/validator.
- **No filter-chain abstraction** — the ffmpeg command is one flat string
  (`build_ffmpeg_cmd()`, `src/converter/converter.c:780-1061`). Video filters
  are exactly two mutually exclusive `-vf` producers today: software deblock
  (`:958-969`) and hardware hwupload (`:970-978`).
- **Runtime probe** exists for codecs (`src/platform/linux/runtime_probe.c`,
  VAAPI one-frame encodes, Vulkan device scan `vk:0..vk:7`, NVENC/AMF/QSV
  simple encodes) but **not for filters**.
- **jansson** is already linked (used for loudnorm JSON parsing,
  `src/converter/converter.c:757-760`) — available for preset-file parsing.
- **Pascal mirrors C** — every ABI/CLI/emit change has a Pascal twin.

### 2.3 HQ_converter preset precedent

`encoder_presets_v2.json` (HQ_converter) establishes the working pattern for
this project's preset files:

- top-level `schema_version` + typed sections;
- named presets as **value bundles** (concrete CLI strings, not abstract
  parameter definitions);
- `field_allowed_values` enums per field for fail-fast validation;
- named filter chains (`sdr_filter_chains`) mapping a name → full ffmpeg
  filter-chain string (`encoder_color_injection.json`).

Phase 4 adopts the same value-bundle approach for `filter_presets.json`.

### 3.1 Core concepts

| Concept | Meaning |
|---|---|
| **Filter preset id** | `filter/preset`, e.g. `deblock/weak`, `libplacebo_deband/medium`, `nlmeans_vulkan/light`. The single user-facing value (stored in `ConvertOptions.filter[64]`). |
| **Filter** | One ffmpeg filter family (possibly multi-step). |
| **Preset** | A named parameter bundle → concrete ffmpeg filter-chain string. |
| **Interface** | `software`, `vulkan`, `opencl`, `cuda` — determines probe method and hw-init flags. |
| **OS** | `linux`, `macos`, `windows`, `cross` — `cross` matches any OS. |
| **Chain** | A preset may expand to a comma-joined multi-filter expression (e.g. `hwupload,libplacebo=...` or `hwupload,nlmeans_vulkan=...,libplacebo=...,hwdownload,format=yuv420p`). |

Note: the Vulkan/OpenCL filters live under `os.cross` because the project
ffmpeg 8.1 build includes them on every target OS (Linux and Windows; macOS
additions are deferred — on systems where a filter is absent, the runtime
probe hides it). OS-specific sections (`windows` → `cuda`) add what is unique
to that platform. The schema is `os`-first so future per-OS differences
(preset overrides, extra filters) slot in without schema changes.

The Vulkan/OpenCL chain strings above were validated on the macOS Intel test
host (Appendix B). The `format=` placement rule (after `hwdownload`, never
between `hwupload` and the hw filter) is a schema-level constraint, not a
platform quirk.

### 3.3 Schema rules

1. **Axis**: `os → interface → filter → preset → parameters` — the same
   `os`-first grouping as the Phase 1 codec presets file, with `interface`
   (`software|vulkan|opencl|cuda`) as the middle level.
2. `filter_chain` is a **complete, self-contained** ffmpeg filter expression —
   including the hwupload/hwdownload framing. `format=` belongs **after**
   `hwdownload` (system domain): a `format=<sysfmt>` placed between
   `hwupload` and the hw filter requests a system frame and breaks the hw
   domain (verified failure, Appendix B). Hw-domain chains end in
   `hwdownload,format=yuv420p` — the explicit format is **mandatory**, not
   optional: without it the graph output can negotiate to an unusable format
   (`monow` observed, Appendix B). The engine emits the chain verbatim into
   `-vf`.
3. A filter may declare `encoders` (e.g. `deblock` → only software ProRes
   encoders) — the preset is offered only for those encoders; absent means
   "all encoders".
4. A filter may declare `hdr_support`: `false` (default) — the preset is
   suppressed for HDR inputs (Phase 4 ships defaults; the flag is
   future-proofing, see §7).
5. **OS inheritance**: the `os.cross` layer always applies; a concrete OS
   section (`linux`/`macos`/`windows`) is **merged on top** — new filters are
   added, and same-name filters/presets **override** the `cross` entries. This
   avoids duplicating identical Vulkan/OpenCL filters across every OS section.
6. `interface` is the grouping axis only; the engine derives probe method and
   hw-init flags from it (§4.2).
7. New filters/presets can be added to the JSON **without rebuilding the
   program** — the registry is data-driven. This is the autonomy requirement.

## 4. Dynamic Availability (filter list population)

The filter menu/help/validation must reflect what the current system
supports. Two-level probe per filter preset:

### 4.1 Level 1 — compile-time/os gate

- `os` axis from the JSON (the current OS section, merged over `cross`) vs
  `CMAKE_SYSTEM_NAME` / `#if defined(_WIN32)` / `#if defined(__APPLE__)`.

### 4.2 Level 2 — runtime probe (once per run, cached)

For each candidate filter from the JSON, probe ffmpeg availability:

1. **Generic parse** — run `ffmpeg -hide_banner -filters` once, grep for the
   filter name. Cost: single subprocess per program run (cached in a static,
   like `ffmpeg_encoder_available()` at `src/converter/converter.c:102-154`).
2. **Hardware capability** (per interface):
   - `vulkan` — reuse the Phase 2 Vulkan probe data (`vulkan_working_mask`,
     `vulkan_device_index`, `vulkan_device_count` in
     `src/platform/linux/runtime_probe.h:8-41`). A filter preset is
     available only if `vulkan_working_mask != 0`. On Windows, same via the
     Windows probe.
    - `opencl` — probe **per device**. The device arg is dot-separated
      `platform.device` (e.g. `opencl=ocl:0.1`); the colon form
      (`opencl=ocl:0:1`) parses as platform-only and fails with "More than
      one matching device found" on multi-device platforms. Enumerate
      `0.0, 0.1, ...` via `-init_hw_device opencl=ocl:0.<i>` until device
      creation fails, then run a one-frame probe per discovered device
      (mirrors `probe_simple_encoder` pattern):
      `ffmpeg -hide_banner -init_hw_device opencl=ocl:0.<i>
      -filter_hw_device ocl -f lavfi -i color=size=64x64:rate=1 -frames:v 1
      -vf "hwupload,boxblur_opencl=luma_radius=1:luma_power=2,hwdownload,
      format=yuv420p" -f null -`. A single platform can mix working and
      broken devices (macOS Intel test host: platform 0 = CPU + 2 AMD GPUs;
      the CPU device fails, the GPUs pass — Appendix B), so availability is
      per device, never per platform.
   - `cuda` — same one-frame probe with `-init_hw_device cuda=cuda:0` and
     `bilateral_cuda`; report unavailable on non-NVIDIA systems.
3. **Encoder/container gating** — apply the filter's `encoders` list against
   the selected codec (interactive path: recompute list when codec changes).

### 4.3 Cache and invalidation

- All probe results cached per program run (static struct, same pattern as
  `g_cache` in `src/platform/linux/runtime_probe.c:386-390`).
- `--dry-run` reuses the cache (no re-probe).

### 4.4 CLI changes (identical logic to the Phase 1 codec/preset CLI flow)

#### 4.4.1 Argument parsing

| Old | New |
|---|---|
| `--deblock/-d <none\|weak\|strong>` | `--filter/-f <filter/preset_id>` — e.g. `deblock/weak`, `libplacebo_deband/medium`, `none` |
| fixed 3-value enum | any preset defined in `filter_presets.json` for a filter available on this system |

`--deblock` kept as **deprecated alias** for one release (mapped to
`deblock/weak|strong`; `--deblock none` → `--filter none`). Removed in v3.1.

#### 4.4.2 Help text (`--help`)

Add a notice:

```
IMPORTANT: -c/--codec and -f/--filter must form a valid combination.
Use --filters-list to see available filter presets for your system.
```

#### 4.4.3 Validation

Before executing, the CLI validates that the selected filter preset exists in
the registry **and** is available for the selected codec/encoder (probe +
`encoders` gating). If not → clear error message:

```
Error: filter preset 'libplacebo_deband/heavy' is not available for codec 'h264_vaapi'.
Use --filters-list to see valid combinations.
```

#### 4.4.4 New parameter: `--filters-list`

Prints a structured list of all filter presets available on the current system
(taking probing results into account), grouped by interface — the filter
counterpart of Phase 1's `--codecs-list`:

```
Available filter presets:

  Software:
    deblock/weak                      Deblocking (CPU)
    deblock/strong                    Heavy deblocking (CPU)

  Vulkan:
    libplacebo_deband/light           Subtle band removal, fast
    libplacebo_deband/medium          Balanced debanding
    libplacebo_deband/heavy           Aggressive debanding for banded sources
    nlmeans_vulkan/medium             Balanced denoising
    libplacebo_deband+nlmeans_vulkan/balanced   Deband + moderate denoise

  OpenCL:
    nlmeans_opencl/medium             Balanced denoising
    boxblur_opencl/medium             Balanced blur

  CUDA:
    bilateral_cuda/medium             Balanced denoising
```

Only filters whose ffmpeg filter name **and** hardware interface passed the
runtime probe are shown. Optional argument narrows the output to one filter:
`--filters-list libplacebo_deband` prints only that filter's presets (or an
error if it is unavailable on this system).

#### 4.4.5 Interactive mode

- The filter step replaces the deblock step and follows the Phase 1 preset-step
  pattern: populated dynamically from the registry based on the selected codec.
- The step is offered when at least one filter preset applies to the selected
  codec (the current `entries[codec_idx].needs_deblock` gate generalizes to
  "registry has an applicable filter"); otherwise the step is skipped.
- Items are grouped by interface (`Software / Vulkan / OpenCL / CUDA`) and
  annotated with the preset description; `none` is first and the default.
- A filter with a single preset is auto-selected to that preset (its
  `default_preset`), no extra prompt — same rule as codecs with a single
  preset in Phase 1 §6.5.
- The list is rebuilt when the codec changes (per-filter `encoders` gating).

## 5. Command Emission

### 5.1 `-vf` assembly

`build_ffmpeg_cmd()` gains a single `emit_video_filter()` step that composes
`-vf` from the resolved filter preset:

1. If `opts->filter` is empty/`none` → no `-vf` (as today with `deblock=1`).
2. Else → `-vf "<filter_chain>"` verbatim from the JSON preset.
3. The hwupload path (`platform_get_hw_vfilter`) remains the **default** when
   no user filter is selected and the codec requires hwupload — the user filter
   takes precedence when set.

Ordering constraint: for hardware encoders that already emit hwupload
(VAAPI/Vulkan), a software-domain user filter is applied **before** hwupload:
`-vf "<filter_chain>,format=nv12,hwupload"` (filters run in CPU domain, then
upload). Hardware-domain presets (OpenCL/Vulkan chains that end in
`hwdownload`) need no further wrapping.

### 5.2 Pre-input hw init

- `vulkan` interface presets → reuse Phase 2 pre-input flags
  (`platform_get_preinput_hw_flags`, `converter_linux.c:390-401`).
- `opencl` interface presets → add
  `-init_hw_device opencl=ocl:0 -filter_hw_device ocl` (new hook, mirrors the
  vulkan one).
- `cuda` interface presets → add `-init_hw_device cuda=cuda:0`.
- The pre-input flags are decided **per selected filter**, not per codec.

## 6. Filter Catalog (Phase 4 first batch)

| Filter | Interface | Encoder applicability | Status |
|---|---|---|---|
| `deblock` (weak/strong) | software | `prores`, `prores_ks` (as today) | port to JSON |
| `libplacebo_deband` (light/medium/heavy) | vulkan | all sw encoders | new |
| `nlmeans_opencl` (light/medium/heavy) | opencl | all sw encoders | new |
| `nlmeans_vulkan` (light/medium/heavy) | vulkan | all sw encoders | new |
| `bilateral_cuda` (light/medium/heavy) | cuda | all sw encoders | new |
| `boxblur_opencl` (light/medium/heavy) | opencl | all sw encoders | new |
| `libplacebo_deband+nlmeans_vulkan` (balanced) | vulkan | all sw encoders | new |

Rules for the first batch:

- **Software encoders only.** GPU filters are incompatible with
  VAAPI/Vulkan/NVENC/AMF/QSV hw-encode paths in v3.0 (the hwupload domain
  conflict in §5.1 makes them a v3.1 topic). `deblock` keeps its existing
  ProRes-only gating; other filters are offered for all software encoders.
- Each GPU filter's `filter_chain` self-contains its `hwupload`/`hwdownload`
  framing — the engine never guesses the domain.
- `format=` is explicit wherever the filter needs a specific pix_fmt, placed
  **after** `hwdownload` in hw-domain chains (`yuv420p` for
  `nlmeans_vulkan`/`nlmeans_opencl`/`boxblur_opencl`); `bilateral_cuda` has
  no hwdownload (its `scale_cuda` does the upload) and keeps `format=` as a
  `scale_cuda` argument.
- The values above are **initial estimates** — the tuning pass (§7) finalizes
  them before v3.0 ships.

## 7. Parameter Tuning Pass (dedicated sub-step)

Purpose: calibrate preset parameter sets for the new filters across content
types and use cases; produce final values for `filter_presets.json`.

### 7.1 Test corpus

| Content type | Example source | Why |
|---|---|---|
| Animation/gradients | 4K SDR animated film clip | banding-heavy; deband primary target |
| Live action, clean | 4K HDR clip (no grain) | denoise baseline |
| Noisy/grainy | 1080p low-light clip | denoise + grain preservation trade-off |
| Compressed artifact | 720p highly compressed | deblock + denoise combined |
| Film grain (HDR) | HDR10 clip with grain | grain retention vs denoise aggressiveness |

### 7.2 Evaluation criteria

1. **Visual quality** — side-by-side stills (banding areas, gradients,
   edges); PSNR/SSIM where meaningful (HQ_converter's `video-metric` roadmap
   is a Phase 4+ candidate).
2. **Performance** — encode fps and VRAM usage per preset tier on the test
   system (AMD Vega 20 / RADV; OpenCL via AMDGPU; CUDA unavailable on the
   test system — `bilateral_cuda` presets verified on the NVIDIA CI host or
   deferred to v3.1 with a `windows`-only entry).
3. **Parameter sweep** per filter:

   - `libplacebo_deband`: `deband_iterations` {2,3,4} × `deband_radius`
     {8,10,14} × `deband_threshold` {4.0,5.0,6.0} × `deband_grain` {0,4,6};
   - `nlmeans_opencl`/`nlmeans_vulkan`: `s` {3,4,6,8,10} × `p` {7,9} ×
     `r` {15,21};
   - `bilateral_cuda`: `window_size` {5,9,15} × `sigmaS` {2,3,4} ×
     `sigmaR` {30,50,70};
   - `boxblur_opencl`: `luma_radius` {1,2,4} × `luma_power` {2,3}.

4. **Combined chain** `libplacebo_deband+nlmeans_vulkan`: order
   (denoise→deband vs deband→denoise) and strength balance.
5. **Output**: the final parameter values written back into
   `filter_presets.json` presets; results logged in this document's appendix
   or a separate `docs/v3.0-Phase4-tuning.md`. First recorded results:
   Appendix A (libplacebo deband, macOS Intel host, 2026-08-29).

### 7.3 Known constraints on the test system

- AMD Vega 20 (RADV): Vulkan video-encode unsupported, but Vulkan **compute**
  filters (libplacebo, nlmeans_vulkan) run fine — probing only requires
  compute, not encode.
- OpenCL: AMDGPU OpenCL runtime required (`mesa` ICD or ROCm) — presence
  probed at runtime; if absent, `nlmeans_opencl`/`boxblur_opencl` are simply
  not offered.
- CUDA: no NVIDIA hardware on the primary test system — `bilateral_cuda`
  stays `windows`-gated and is validated on the Windows CI/release host.

## 12. Recommendations

1. **Build Phase 4 on Phase 1's loader**, do not create a second JSON-parsing
   path. `filter_presets.json` and the codec presets file share the same
   `os`-first axis (`os → interface → filter` vs `os → codec → preset`) and
   the same validator/fallback strategy.
2. **Keep chains self-contained** (schema rule 1) — the engine should never
   synthesize hw domain transitions. This is what makes presets authorable
   outside the program.
3. **Ship the tuning pass as a tracked deliverable** — the sweep results and
   final values must be reproducible (fixed corpus + ffmpeg 8.1 pinned), since
   quality presets are the product.
4. **Restrict GPU presets to software encoders in v3.0**; add hw-encoder +
   filter combinations in v3.1 once the ordering rules are proven.
5. **Expose per-interface filter groups in the GUI** (Software / Vulkan /
   OpenCL / CUDA sections) instead of one flat combo — matches the JSON axis
   and keeps the list navigable.
6. **Reuse Phase 2/3 probe caching** for Vulkan device data; add OpenCL/CUDA
   probes in the same file/pattern.
7. **Plan `deband`-only vs `deband+denoise` UX**: the combined chain preset
   (`libplacebo_deband+nlmeans_vulkan`) proves chain presets work; future
   combinations (e.g. deband + boxblur) are then just JSON additions.
8. **Phase 5 candidates** unlocked by this phase: user-defined filter chains
   (compose presets at runtime), per-codec default filter mapping, HW-encoder
   filter support, filter presets for HQ_converter's CPU pipeline.


### B.3 Defects found in the §3.2 draft chains (now fixed)

1. `format=<sysfmt>` between `hwupload` and the hw filter requests a
   **system** frame — the auto-inserted scale then attempts an hw→system
   conversion and the graph fails at init. `format=` must come after
   `hwdownload`.
2. Without an explicit `format=yuv420p` after `hwdownload`, the graph output
   negotiates to `monow` and `hwdownload` fails ("Invalid output format
   monow for hwframe download"). The trailing format is mandatory.
3. `libplacebo` emits system frames directly when nothing hw-domain follows
   it — the draft `hwupload,libplacebo=...,hwdownload` framing needs no
   `hwdownload` for standalone use. The §3.2 `libplacebo_deband` presets now
   use `hwupload,libplacebo=...` (GPU pinned via the §5.2 pre-input flags);
   a bare `libplacebo=...` chain also works (auto-selects GPU0, no hw-init
   flags — Appendix A). Where `hwdownload` is kept (combined chain), the
   trailing `format=yuv420p` is mandatory (item 2).

### B.4 OpenCL device selection

- The device arg is **dot-separated** `platform.device`:
  `-init_hw_device opencl=ocl:0.1`. The colon form (`opencl=ocl:0:1`) parses
  as platform-only and fails with "More than one matching device found" on
  multi-device platforms.
- This host: 1 platform ("Apple") with 3 devices — `0.0` = Intel i9-7900X
  CPU (nlmeans download fails: "Invalid output format yuv420p for hwframe
  download"), `0.1` = AMD Radeon Pro WX 7100, `0.2` = AMD Radeon RX Vega 64
  (both GPUs pass).
- Consequence for §4.2: OpenCL availability is **per device** — the probe
  must enumerate `0.<i>` until device creation fails and run the one-frame
  probe per device; a platform-level probe overpromises.

### B.5 Speed and quality — test_FHD.mkv, ProRes LT output

Full-file runs (219.6 s AV1 1080p source, default params `s=1:p=7:r=15`,
Vega 64, `-c:v prores -profile:v 1`):

| Backend | Speed | Quality verdict |
|---|---|---|
| `nlmeans_vulkan` (`vk:0`) | **0.358x** (10 min 13 s, completed, exit 0) | **Defective** — output very blurred; not usable |
| `nlmeans_opencl` (`ocl:0.2`) | **~0.07–0.1x** (estimate: run stopped at 25 min with ≈ 65% of output written) | Correct — as expected, just very slow |

Findings:

- `nlmeans_vulkan` is fast enough for interactive use but **fails the
  quality bar on this host** (MoltenVK 1.4.2 / Vega 64): the identical
  `s=1:p=7:r=15` parameters that yield a correct result via OpenCL produce

- Consequence for the §6 catalog: `nlmeans_vulkan` presets must not ship as

### C.3 Key Findings and Pipeline Rules

1. **4K `libplacebo` Deband Throughput**:
   On 4K video, `libplacebo_deband` executes at **63–68 fps (2.12x–2.28x realtime)** on the AMD Radeon Pro WX 9100 GPUs via Vulkan shaders under FFmpeg 9.0.
2. **Chained Format Conversion Rule**:
   MoltenVK's `hwdownload` yields `yuv420p`. Subsequent pixel format conversions required by non-yuv420p encoders (such as `nv12` for VideoToolbox or `yuv422p10le` for Apple ProRes) must be chained **after** `hwdownload` in the CPU filter domain (e.g. `hwdownload,format=yuv420p,format=nv12`). Placing non-yuv420p format requests directly inside `hwdownload` causes filter graph initialization errors.
3. **Vulkan Video Encoder Compatibility**:
   Native Vulkan Video encoders (`h264_vulkan`, `hevc_vulkan`, `av1_vulkan`) require `VK_KHR_video_encode_queue`, which MoltenVK does not provide on macOS. The filter engine's design correctly routes Vulkan-filtered frames back through system memory to VideoToolbox, SVT-AV1, or software encoders.
